1. [Код-пазл] Що виведе цей код із замиканням у циклі?

↑ До змісту 
var actions = new List<Action>();

for (int i = 0; i < 3; i++)
{
    actions.Add(() => Console.Write(i + " "));
}

foreach (var action in actions)
{
    action();
}
Результат: Виведе: 3 3 3 (а не 0 1 2 ).

Чому так відбувається:

Компілятор створює один-єдиний екземпляр службового класу (Display Class) для всього циклу for. Локальна змінна i стає єдиним спільним полем цього класу: displayClass.i. Коли цикл завершується, значення displayClass.i дорівнює 3. При послідовному виклику делегатів усі три лямбди звертаються до однієї й тієї ж ділянки пам'яті в купі.

Як виправити: Створити локальну копію всередині тіла циклу: int copy = i; actions.Add(() => Console.Write(copy));. Для кожної ітерації буде виділено свій окремий контекст.

Примітка: У циклі foreach у C# 5.0+ це виправили автоматично — там компілятор сам створює новий скоуп на кожну ітерацію.

2. [Код-пазл] Виклик `virtual` методу з конструктора базового класу. Що виведе?

↑ До змісту 
public class Parent
{
    public Parent()
    {
        PrintMessage();
    }

    public virtual void PrintMessage() => Console.WriteLine("Parent message");
}

public class Child : Parent
{
    private string _msg = "Child message";

    public Child()
    {
        // Конструктор нащадка
    }

    public override void PrintMessage() => Console.WriteLine(_msg ?? "null");
}

// Виклик:
new Child();
Результат: Виведе: Child message, АЛЕ якщо прибрати ініціалізатор поля і задати його в тілі конструктора — виведе null!

Підступний механізм CLR (Порядок ініціалізації):

  1. Спочатку ініціалізуються інлайн-поля нащадка (_msg = "Child message").
  2. Викликається конструктор базового класу Parent().
  3. Конструктор Parent() викликає віртуальний метод PrintMessage(). Оскільки тип об'єкта в таблиці віртуальних методів уже Child, викликається саме перевизначений метод Child.PrintMessage()!
  4. Якщо поле _msg ініціалізувалося всередині конструктора Child: 
    public Child() { _msg = "Child message"; }
    Тоді в момент виклику з базового класу конструктор Child ще НЕ починав виконуватися, і поле _msg дорівнює дефолтному null!

Золоте правило C#: Ніколи не викликайте віртуальні методи з конструктора, тому що нащадок виконуватиме свій код у напівініціалізованому стані.

3. [Код-пазл] Поведінка `try-finally` при зміні змінної. Що поверне метод?

↑ До змісту 
public int GetNumber()
{
    int x = 10;
    try
    {
        return x;
    }
    finally
    {
        x = 20;
        Console.Write("Finally! ");
    }
}

// Виклик:
Console.WriteLine(GetNumber());
Результат: Виведе: Finally! 10 (значення 10, а НЕ 20).

Чому так відбувається:

Коли виконання доходить до return x; у блоці try, значення змінної x (число 10) обчислюється та копіюється в стек виконання (або регістр процесора) як значення, що повертається. Після цього обов'язково виконується блок finally, де локальна змінна x перезаписується на 20, проте значення на стеку повернення залишається незмінним. Метод повертає початкові 10.

4. [Код-пазл] Інтернування рядків: що поверне `ReferenceEquals`?

↑ До змісту 
string s1 = "hello world";
string s2 = "hello " + "world";

string part = "world";
string s3 = "hello " + part;

Console.WriteLine(object.ReferenceEquals(s1, s2)); // ???
Console.WriteLine(object.ReferenceEquals(s1, s3)); // ???
Результат: Перший виклик поверне True, другий — False.

Розгорнута відповідь:

  • s1 == s2 (True): Рядок "hello " + "world" складається з двох строкових літералів. Компілятор Roslyn на етапі збірки виконує оптимізацію Constant Folding (згортання констант) і перетворює це на "hello world". Обидва посилання вказують на один і той самий об'єкт із глобальної таблиці інтернування рядків CLR.
  • s1 == s3 (False): Оскільки part є змінною, конкатенація відбувається динамічно в рантаймі через виклик string.Concat(). Створюється абсолютно новий об'єкт у купі, тому посилання в пам'яті різні. (Зробити посилання однаковими можна було б лише явним викликом string.Intern(s3)).

5. [Код-пазл] Модифікація колекції під час ітерації в `foreach`. Що станеться?

↑ До змісту 
var list = new List<int> { 1, 2, 3, 4, 5 };

foreach (var item in list)
{
    if (item == 3)
    {
        list.Remove(item);
    }
}
Результат: Аварія в runtime: InvalidOperationException: Collection was modified; enumeration operation may not execute.

Внутрішня механіка:

Клас List<T> має внутрішнє приватне цілочисельне поле _version. Будь-яка операція додавання або видалення (Add, Remove, Clear) інкрементує лічильник: _version++.

Коли ви запускаєте foreach, створюється структура-ітератор List<T>.Enumerator, яка запам'ятовує версію списку в момент старту: this.version = list._version. При кожному наступному кроці MoveNext() ітератор перевіряє: if (this.version != list._version) throw .... Це захищає від читання пошкоджених зміщених індексів.

Як правильно видаляти:

  • Використовувати вбудований метод: list.RemoveAll(x => x == 3);
  • Або звичайний цикл for з кінця до початку: for (int i = list.Count - 1; i >= 0; i--).

6. [Код-пазл] Мутація структури через інтерфейс (Boxing пастка). Що виведе?

↑ До змісту 
public interface ICounter
{
    void Increment();
}

public struct Counter : ICounter
{
    public int Value { get; private set; }
    public void Increment() => Value++;
}

// Виклик:
Counter c = new Counter();
c.Increment();
Console.WriteLine(c.Value); // 1

ICounter ic = c; // Boxing!
ic.Increment();
Console.WriteLine(c.Value);  // ???
Console.WriteLine(((Counter)ic).Value); // ???
Результат: Виведе: 1, а потім 2.

Чому значення c.Value не змінилося:

Присвоєння ICounter ic = c; запаковує (boxing) структуру c у новий об'єкт у купі. Виклик ic.Increment() змінює поле всередині об'єкта в купі, тоді як оригінальна локальна структура c на стеку залишається незмінною зі значенням 1.

Висновок: Мутабельні структури (Mutable Structs) — це антипатерн. Структури в C# завжди повинні бути незмінними: readonly struct.

7. Що відбувається під капотом, коли ви вводите `https://google.com` у браузері і натискаєте Enter?

↑ До змісту
Коротка суть: Повний шлях: DNS резолвінг (IP) → TCP 3-Way Handshake (SYN, SYN-ACK, ACK) → TLS Handshake (обмін ключами) → відправка HTTP GET → маршрутизація через Reverse Proxy на веб-сервер Kestrel → генерація HTML/JSON → рендеринг у DOM.

Покроковий ланцюжок:

  1. Парсинг URL: Браузер відокремлює протокол (HTTPS), хост (google.com) та порт (443 за замовчуванням).
  2. DNS Резолвінг (Пошук IP): Браузер шукає IP-адресу по черзі: у власному кеші → кеші ОС → файлі hosts → запит до DNS-сервера провайдера або 8.8.8.8.
  3. TCP Handshake (Встановлення з'єднання на транспортному рівні L4):
    • Клієнт відправляє SYN.
    • Сервер відповідає SYN-ACK.
    • Клієнт підтверджує ACK. З'єднання відкрито.
  4. TLS Handshake (Криптографічний захист L5): Клієнт і сервер домовляються про версію TLS, шифр (Cipher Suite), сервер надає SSL-сертифікат, перевіряється ланцюжок довіри (CA), генерується спільний симетричний ключ.
  5. HTTP Запит: Клієнт відправляє текстовий шифрований запит: GET / HTTP/1.1\r\nHost: google.com....
  6. Обробка на сервері: Запит приймає Reverse Proxy (Nginx/Cloudflare/Envoy) → передає на Kestrel (.NET) → прохід через конвеєр Middleware → повернення HTTP 200 OK з контентом.
  7. Рендеринг у браузері: Парсинг HTML → побудова DOM-дерева → завантаження CSS/JS → виконання скриптів.

8. Як під капотом влаштований HTTPS? Симетричне vs Асиметричне шифрування.

↑ До змісту
Коротка суть: HTTPS використовує гібридне шифрування: важке асиметричне (RSA / ECC з відкритим та закритим ключами) використовується ЛИШЕ на старті для безпечної передачі спільного сесійного ключа. Далі весь потік даних шифрується надшвидким симетричним алгоритмом (AES-GCM).

Чому не шифрувати все асиметрично?

Асиметричне шифрування (з публічним і приватним ключами) вимагає складних математичних операцій з гігантськими простими числами і працює у сотні разів повільніше за симетричне. Воно б миттєво перевантажило процесори серверів.

Роль цифрового сертифіката X.509: Сертифікат підтверджує, що публічний ключ дійсно належить саме компанії Google, а не зловмиснику посередині (захист від Man-in-the-Middle атаки). Справжність сертифіката підтверджується цифровим підписом акредитованого Центру Сертифікації (Certificate Authority — Let's Encrypt, DigiCert), кореневі сертифікати яких вшиті прямо в операційну систему.

9. Docker: Чим контейнери відрізняються від віртуальних машин? Що таке Multi-stage збірка в .NET?

↑ До змісту
Коротка суть: Віртуальна машина віртуалізує апаратне залізо і несе всередині окрему повноцінну гостьову ОС (гіпервізор). Контейнер — це просто ізольований процес, що використовує спільне ядро хостової Linux ОС через cgroups та namespaces.

Порівняння:

  • Віртуальна машина (VM): Важка (гігабайти на диску), повільний старт (хвилини), дублювання ядра ОС, значні накладні витрати оперативної пам'яті.
  • Docker Контейнер: Легкий (мегабайти), стартує за мілісекунди, використовує ресурси та ядро хоста напряму без прошарку гіпервізора.

Multi-stage builds у .NET Dockerfile:

Дозволяє розділити важке середовище збірки (SDK) від середовища виконання (Runtime), зменшуючи фінальний образ з 800 МБ до 100 МБ:

# Етап 1: Збірка проекту у важкому SDK образі (містить компілятор Roslyn)
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish

# Етап 2: Фінальний образ (містить лише легкий ASP.NET Runtime без SDK!)
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApi.dll"]

10. Git для розробника: у чому принципова різниця між `git merge` та `git rebase`?

↑ До змісту
Коротка суть: `git merge` створює новий коміт злиття (merge commit) і зберігає реальну історію відгалужень. `git rebase` переносить ваші коміти на верхівку цільової гілки, створюючи ідеально чисту лінійну історію без додаткових комітів злиття.

Порівняння:

  • git merge feature:
    • Безпечна неруйнівна операція: історія комітів гілки залишається недоторканою.
    • Створює спеціальний «Merge commit» із двома батьками.
    • Мінус: при великій кількості розробників історія перетворюється на заплутаний «вузол спагеті».
  • git rebase main:
    • Бере ваші коміти з feature-гілки, тимчасово відкладає їх, оновлює гілку до останнього коміту main і накладає ваші коміти поверх по одному.
    • Історія стає красивою, строго послідовною та лінійною.
    • Золоте правило Rebase: Ніколи не робіть rebase у публічних гілках (наприклад, main/develop)! Оскільки rebase змінює хеші комітів (створює нові об'єкти комітів), це зламає роботу іншим колегам, які встигли затягнути старі коміти.

11. Що таке `CancellationToken`? Як організувати коректне скасування операцій (Graceful Shutdown)?

↑ До змісту
Коротка суть: Структура для кооперативного (добровільного) скасування асинхронних задач. `CancellationTokenSource` ініціює скасування, а викликаний метод регулярно перевіряє токен через `ThrowIfCancellationRequested()` і звільняє ресурси.

Розгорнута відповідь:

У .NET потік не можна просто грубо «вбити» посеред виконання (це призведе до блокувань у пам'яті та незакритих файлів). Скасування завжди є кооперативним: метод повинен сам погодитися завершити роботу.

public async Task ProcessDataAsync(CancellationToken ct)
{
    while (hasMoreData)
    {
        // 1. Швидка перевірка: викидає OperationCanceledException, якщо надійшов сигнал відміни
        ct.ThrowIfCancellationRequested(); 

        // 2. Прокидання токена у всі внутрішні асинхронні виклики
        await _httpClient.GetAsync(url, ct);
    }
}

Використання в ASP.NET Core: Кожен метод контролера або ендпоінт може приймати CancellationToken ct. Якщо користувач у браузері закрив вкладку або обірвав з'єднання до того, як бекенд відповів, ASP.NET Core автоматично надсилає сигнал скасування. Завдяки цьому важкий SQL-запит у базі миттєво анулюється, заощаджуючи ресурси сервера.

12. Методи розширення (Extension Methods): як влаштовані під капотом? Чи впаде виклик на `null`?

↑ До змісту
Коротка суть: Методи розширення — це чистий синтаксичний цукор компілятора. Під капотом вони перетворюються на звичайний виклик статичного методу. Виклик екстеншена на `null` об'єкті НЕ викликає NullReferenceException автоматично!

Розгорнута відповідь:

public static class StringExtensions
{
    public static bool IsNullOrEmpty(this string str)
    {
        return string.IsNullOrEmpty(str); // Безпечна перевірка!
    }
}

// Виклик:
string name = null;
bool result = name.IsNullOrEmpty(); // НЕ ВПАДЕ з NullReferenceException!

Чому код не падає: Компілятор Roslyn перетворює рядок name.IsNullOrEmpty() на прямий статичний виклик:

bool result = StringExtensions.IsNullOrEmpty(name); // Звичайний виклик, куди передано аргумент null!

Помилка NullReferenceException виникне лише тоді, коли ви всередині самого методу розширення спробуєте звернутися до властивостей або методів аргументу (str.Length) без попередньої перевірки на null.

13. Upcasting vs Downcasting: у чому різниця? Оператори `as` та `is`.

↑ До змісту
Коротка суть: Upcasting — приведення нащадка до базового типу (завжди безпечне, неявне). Downcasting — приведення базового типу до нащадка (небезпечне, вимагає явного касту або операторів `as`/`is`).

Порівняння способів приведення:

  • Upcasting: Animal a = new Dog(); Завжди успішний, компілятор дозволяє виконувати неявно.
  • Downcasting (Спосіб 1 — Явний каст): 
    Dog d = (Dog)a; // Якщо 'a' насправді Cat, вилетить InvalidCastException!
  • Downcasting (Спосіб 2 — Оператор `as`): 
    Dog d = a as Dog; // Якщо привести не вдалося, повертає null (не кидає виняток). Працює ТІЛЬКИ для nullable/reference types!
  • Downcasting (Спосіб 3 — Сучасний оператор `is`): 
    if (a is Dog dog)
{
    dog.Bark(); // Змінна 'dog' доступна одразу всередині if (найбезпечніший підхід)
}

14. Що таке чисті функції (Pure Functions) та побічні ефекти (Side Effects)?

↑ До змісту
Коротка суть: Чиста функція є строго детермінованою (для однакових вхідних аргументів ЗАВЖДИ повертає однаковий результат) і не створює жодних побічних ефектів (не змінює глобальні змінні, не пише в БД, консоль чи файл).

Приклади:

// ЧИСТА ФУНКЦІЯ: Ідеальна для Unit-тестів, легко кешується (Memoization), потокобезпечна
public int Add(int a, int b) => a + b;

// НЕЧИСТА ФУНКЦІЯ (має Side Effect: запис у консоль та залежність від поточного часу)
public int AddAndLog(int a, int b)
{
    Console.WriteLine(DateTime.Now); // Побічний ефект
    return a + b;
}

Переваги чистих функцій: Не викликають Race Conditions у багатопотоковому середовищі, для них не потрібні Mock-об'єкти в тестах, їх виконання можна безпечно розпаралелювати на будь-яку кількість ядер процесора.

15. Формати серіалізації: JSON (`System.Text.Json`) vs Protocol Buffers (Protobuf) vs MessagePack.

↑ До змісту
Коротка суть: JSON — текстовий, зручний для вебу і налагодження, але повільний і об'ємний. Protobuf та MessagePack — двійкові, компактні та в рази швидші, ідеальні для внутрішньої мікросервісної взаємодії та високих навантажень.

Порівняльна таблиця:

  • JSON (`System.Text.Json`): Стандарт для Public Web API. У сучасному .NET 8/9 підтримує Source Generators (генерація серіалізаторів під час компіляції без використання повільної рефлексії через [JsonSerializable]).
  • Protocol Buffers (Protobuf): Бінарний контрактний формат від Google. Використовує суворі файли .proto, стискає цілі числа за алгоритмом Varint. Не передає назви полів у повідомленні (тільки числові теги 1, 2, 3), що робить пейлоад у 3–5 разів меншим за JSON. Стандарт для gRPC.
  • MessagePack: «Бінарний JSON». Не вимагає обов'язкових контрактних proto-файлів, може серіалізувати довільні C# об'єкти на льоту, забезпечуючи швидкість, близьку до Protobuf. Популярний для кешування великих об'єктів у Redis.
