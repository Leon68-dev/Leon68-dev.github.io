1. Основні принципи ООП. Як вони реалізовані в C#? Від якого класу неявно успадковуються всі типи? Чи дозволено множинне успадкування?

↑ До змісту
Коротка суть: 4 принципи (Інкапсуляція, Успадкування, Поліморфізм, Абстракція). Усі типи походять від System.Object. Множинне успадкування класів заборонено, але дозволено множинну реалізацію інтерфейсів.

Розгорнута відповідь:

  • Інкапсуляція: Приховування внутрішнього стану об'єкта та надання контрольованого доступу через публічний інтерфейс (модифікатори private, public, властивості { get; set; }).
  • Успадкування: Механізм створення нового класу на основі існуючого з повторним використанням коду (class Dog : Animal).
  • Поліморфізм: Здатність одного інтерфейсу представляти різні форми поведінки (перевантаження методів або перевизначення через virtual/override).
  • Абстракція: Відокремлення концептуального контракту («що об'єкт робить») від його конкретної реалізації («як саме») за допомогою interface та abstract class.

Базовий тип: Абсолютно всі типи в .NET (як класи, так і структури через ланцюжок ValueType) прямо або неявно успадковуються від класу System.Object (аліас у C# — object).

Множинне успадкування: C# не підтримує множинне успадкування класів (щоб уникнути «проблеми ромба» — Diamond Problem). Але клас може реалізовувати будь-яку кількість інтерфейсів.

2. Що таке інкапсуляція та як її реалізувати в C#? Навіщо потрібні властивості (Properties)?

↑ До змісту
Коротка суть: Захист інваріанту даних об'єкта від некоректних змін ззовні. Властивості — це «синтаксичний цукор» над парою методів get_X() та set_X().

Розгорнута відповідь:

Замість відкриття приватних полів назовні (що ламає контроль), поле роблять private, а доступ надають через публічні методи або властивості, де можна додати валідацію:

public class BankAccount
{
    private decimal _balance; // Приватне поле

    public decimal Balance   // Властивість з інкапсульованою логікою
    {
        get => _balance;
        private set
        {
            if (value < 0) throw new ArgumentException("Баланс не може бути від'ємним!");
            _balance = value;
        }
    }
}

Автоматичні властивості: public string Name { get; set; } автоматично генерують приховане анонімне поле компілятора (Backing Field).

3. Що таке поліморфізм? У чому різниця між статичним та динамічним поліморфізмом?

↑ До змісту
Коротка суть: Статичний (compile-time) — це перевантаження методів (Overloading). Динамічний (run-time) — перевизначення методів через віртуальні таблиці (Overriding).

Розгорнута відповідь:

  • Статичний поліморфізм (Compile-time): Компілятор визначає потрібний метод ще на етапі збірки за сигнатурою (назвою та типами аргументів). Приклад: перевантаження методів: 
    public int Add(int a, int b) => a + b;
public double Add(double a, double b) => a + b;
  • Динамічний поліморфізм (Run-time): Який саме метод викликати, вирішується в момент виконання програми на основі реального типу об'єкта в пам'яті (через механізм vtable — таблиці віртуальних методів). Реалізується через ключові слова virtual, override або інтерфейси.

4. Що дає ключове слово `virtual`? Різниця між `override` та приховуванням через `new`?

↑ До змісту
Коротка суть: `override` змінює поведінку у віртуальній таблиці об'єкта (поліморфізм). `new` розриває зв'язок і приховує метод базового класу, виклик залежить від типу посилання.

Розгорнута відповідь:

public class BaseClass
{
    public virtual void MethodA() => Console.WriteLine("Base A");
    public void MethodB() => Console.WriteLine("Base B");
}

public class DerivedClass : BaseClass
{
    public override void MethodA() => Console.WriteLine("Derived A");
    public new void MethodB() => Console.WriteLine("Derived B"); // Приховування
}

// Перевірка поведінки:
BaseClass obj = new DerivedClass();
obj.MethodA(); // Виведе: "Derived A" (поліморфізм відпрацював)
obj.MethodB(); // Виведе: "Base B" (бо тип змінної — BaseClass, new розірвав віртуальність!)

5. Що таке абстрактний клас і чим він відрізняється від інтерфейсу?

↑ До змісту
Коротка суть: Клас може успадкувати лише один абстрактний клас (визначає сутність IS-A), але реалізувати багато інтерфейсів (визначає контракт/здатність CAN-DO).

Порівняльна таблиця:

  • Успадкування: Абстрактний клас — одиничне успадкування; Інтерфейси — множинна реалізація.
  • Стан (Fields): Абстрактний клас може містити власні нестатичні поля стану (private int _id;). Інтерфейс не може містити стан екземпляра (поля).
  • Конструктори: Абстрактний клас має конструктор (викликається нащадками через base()). Інтерфейс конструкторів мати не може.
  • (Починаючи з C# 8): В інтерфейсах з'явилися Default Interface Methods (дефолтні реалізації), проте вони призначені для еволюції API без ламання клієнтів і не роблять інтерфейс повноцінним класом.

6. Що дають модифікатори `sealed` та `static`? Особливості статичних класів.

↑ До змісту
Коротка суть: `sealed` забороняє успадкування класу або перевизначення методу. `static` клас не може мати екземплярів, містить лише статичні члени та не успадковується.

Розгорнута відповідь:

  • sealed (запечатаний):
    • Для класу: забороняє будь-яке успадкування від нього (наприклад, public sealed class String). Це оптимізує виклики методів (JIT-девіртуалізація).
    • Для методу: забороняє подальше перевизначення у нащадках (public sealed override void DoWork()).
  • static клас:
    • Не можна створити через new.
    • Не може містити нестатичних конструкторів, полів або методів.
    • Завжди неявно є sealed і успадковується напряму від System.Object.
    • Має статичний конструктор, який викликається автоматично CLR рівно один раз перед першим зверненням до класу.

7. Які модифікатори доступу є в C#?

↑ До змісту
Коротка суть: 6 основних рівнів видимості: public, private, protected, internal, protected internal, private protected.

Розгорнута відповідь:

  • private: Доступний лише всередині того ж класу/структури (за замовчуванням для членів класу).
  • protected: Доступний у поточному класі та у всіх його нащадках.
  • internal: Доступний усім класам у межах тієї ж збірки (Assembly / .dll).
  • public: Доступний звідусіль без обмежень.
  • protected internal: Доступний нащадкам АБО будь-якому коду в тій самій збірці (логічне АБО).
  • private protected: Доступний нащадкам, але ТІЛЬКИ якщо вони знаходяться в тій самій збірці (логічне І).

8. Value Types vs Reference Types: у чому різниця? Де зберігаються (Stack vs Heap)?

↑ До змісту
Коротка суть: Значущі типи копіюються за значенням. Посилальні — копіюють лише посилання на об'єкт. Стек швидкий, але пам'ять виділяється також у купі, якщо value-тип є полем класу!

Розгорнута відповідь:

  • Value Types (типи-значення): struct, примітиви (int, bool, double), enum. Змінна містить самі дані.
    • Якщо оголошені локально всередині методу — живуть на стеку (Stack).
    • Увага підступне питання: Якщо структура чи примітив є полем класу (reference type), вони зберігаються разом із класом у купі (Managed Heap)!
  • Reference Types (типи-посилання): class, interface, delegate, string, масиви.
    • Сам об'єкт із даними завжди живе в купі (Heap) і очищується Garbage Collector'ом.
    • Змінна містить лише посилання (адресу в пам'яті розміром 4 або 8 байт), яке лежить на стеку.

9. `string` — це Reference чи Value тип? Чому рядки незмінні (immutable)?

↑ До змісту
Коротка суть: Рядок — це повноцінний Reference Type, який веде себе як Value Type через перевизначені оператори порівняння. Незмінність забезпечує потокобезпечність та інтернування.

Розгорнута відповідь:

Рядок є посилальним типом (живе в купі). Але він має особливості:

  • Незмінність (Immutability): Після створення рядок не можна змінити в пам'яті. Будь-яка операція (наприклад, s += "abc" або s.Replace(...)) насправді створює новий об'єкт рядка у купі.
  • Навіщо це зроблено:
    • Потокобезпечність (Thread-safety): Незмінні об'єкти можна безпечно читати з кількох потоків без синхронізації/блокувань.
    • Інтернування рядків (String Interning): CLR тримає таблицю унікальних літералів. Якщо в коді 100 разів написати "hello", у пам'яті буде лише один екземпляр.
  • При частій конкатенації (наприклад, у циклі) слід використовувати StringBuilder, щоб не засмічувати купу десятками проміжних рядків.

10. Що таке Boxing та Unboxing? Який їхній оверхед?

↑ До змісту
Коротка суть: Boxing — запакування значення зі стеку в об'єкт у купі. Unboxing — розпакування назад. Створює додаткове навантаження на Garbage Collector.

Розгорнута відповідь:

int x = 42;
object obj = x;        // Boxing (алокація пам'яті в Heap + копіювання даних)
int y = (int)obj;      // Unboxing (перевірка типу в runtime + копіювання значення на стек)

Оверхед упаковки:

  1. Виділяється пам'ять у купі (розмір даних + заголовок об'єкта 8/16 байт під TypeHandle та SyncBlockIndex).
  2. Витрачається час процесора на копіювання байтів.
  3. Збільшується навантаження на Garbage Collector, який змушений чистити ці тимчасові об'єкти в Gen 0.

11. Різниця між `const` та `readonly`?

↑ До змісту
Коротка суть: `const` — compile-time константа (жорстко вшивається в код). `readonly` — runtime константа (може задаватися в конструкторі).

Порівняння:

  • const:
    • Значення має бути відоме на момент компіляції (числа, рядки, булеві).
    • Неявно є статичним (звернення через ClassName.ConstField).
    • Значення «вшивається» напряму в IL-код виклику (якщо змінити константу в одній бібліотеці без перекомпіляції клієнта — буде старе значення!).
  • readonly:
    • Може бути ініціалізоване під час виконання програми (наприклад, прочитане з конфігурації в конструкторі).
    • Може бути як статичним (ініціалізується в static конструкторі), так і належати екземпляру.

12. Як працюють параметри `ref`, `out` та `in`?

↑ До змісту
Коротка суть: Усі три передають аргумент за посиланням (адресою пам'яті). `ref` — на читання і запис, `out` — тільки на запис усередині методу, `in` — тільки для читання.

Розгорнута відповідь:

  • ref: Змінна має бути ініціалізована до виклику методу. Метод може як читати її, так і записувати нове значення.
  • out: Змінна може бути неініціалізованою до виклику, але викликаний метод зобов'язаний присвоїти їй значення перед завершенням (використовується для повернення кількох значень, як у int.TryParse(s, out int res)).
  • in (додано в C# 7.2): Передає аргумент за посиланням, але забороняє його зміну всередині методу (read-only reference). Використовується для оптимізації продуктивності: передача великих структур без їх копіювання в стек.

13. Що таке Records (`record`) та Record Structs? Чим вони відрізняються від звичайних класів?

↑ До змісту
Коротка суть: Records (C# 9+) — типи даних з автоматичним Value-based порівнянням, незмінністю (init-only) та зручним копіюванням за допомогою оператора `with`.

Розгорнута відповідь:

За замовчуванням record компілюється як звичайний посилальний клас (Reference Type), проте з унікальними фічами:

  • Порівняння за значенням: Два різних об'єкти record з однаковими полями повернуть true при Equals() та ==.
  • Короткий синтаксис: public record Person(string Name, int Age); сам генерує конструктор, властивості { get; init; }, методи Equals, GetHashCode і ToString().
  • Non-destructive mutation: створення зміненої копії через with: 
    var p1 = new Person("Олексій", 25);
var p2 = p1 with { Age = 26 }; // новий об'єкт із тим самим ім'ям
  • record struct (C# 10): дозволяє отримати ті самі переваги порівняння та оператора with, але у вигляді структури на стеку (Value Type).

14. Що таке Nullable-типи (`Nullable` та `T?`)? Nullable Reference Types.

↑ До змісту
Коротка суть: Для Value Types — це структура `Nullable`, яка дозволяє приймати `null`. Для Reference Types (C# 8+) — це статичний аналіз компілятора для запобігання NRE.

Розгорнута відповідь:

  • Nullable Value Types (int?): Структури за замовчуванням не можуть містити null. Запис int? є синтаксичним цукром для структури System.Nullable<int>, яка містить значення та булевий прапорець HasValue.
  • Nullable Reference Types (C# 8+): Якщо ввімкнено <Nullable>enable</Nullable>, посилальні типи за замовчуванням вважаються такими, що не можуть містити null (string name). Якщо поле може бути порожнім, його треба явно позначити знаком питання: string? middleName.
    Важливо: Це підказка для компілятора та попередження під час збірки (Warnings), в IL-коді тип string? залишається звичайним string.
