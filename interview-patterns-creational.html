Породжувальні патерни GoF на C#

Відповідають за гнучке й безпечне створення об'єктів без жорсткого зв'язування з конкретними класами

Швидкий перехід по розділу

  • 1. Singleton* (Одинак)
  • 2. Factory Method* (Фабричний метод)
  • 3. Abstract Factory* (Абстрактна фабрика)
  • 4. Builder* (Будівельник)
  • 5. Prototype (Прототип)

* Патерни з зірочкою містять розгорнутий аналіз архітектури та покрокове виконання коду.

Патерн 1: Singleton (Одинак)*

Породжувальний (Creational)
↑ До змісту

1. Призначення

Гарантує, що клас має лише один екземпляр у межах усієї програми, і надає глобальну точку доступу до цього екземпляра.

2. Коли застосовувати

  • Потрібен єдиний спільний ресурс: підключення до апаратного пристрою, кеш, пул з'єднань або конфігурація.
  • Необхідно суворо виключити можливість створення кількох екземплярів об'єкта.
Примітка для .NET: У сучасному C# замість ручного написання канонічного класу найчастіше використовують механізм DI-контейнера: services.AddSingleton<IConfigurationManager, ConfigurationManager>(). Проте розуміння внутрішнього влаштування Singleton на рівні CLR обов'язкове на технічних інтерв'ю.

3. Реалізація на C#

using System;

// 'sealed' prevents derivation, which could break the singleton invariant
public sealed class ConfigurationManager
{
    // Lazy<T> ensures thread-safety and creates the instance on first access
    private static readonly Lazy<ConfigurationManager> _instance = 
        new Lazy<ConfigurationManager>(() => new ConfigurationManager());

    // 1. Private constructor prevents instantiation via 'new ConfigurationManager()' from outside
    private ConfigurationManager()
    {
        Console.WriteLine("--> Initializing ConfigurationManager (happens only once).");
    }

    // 2. Global access point to the singleton instance
    public static ConfigurationManager Instance => _instance.Value;

    // Service state
    public string AppName { get; set; } = "MyApplication";

    public void PrintSettings()
    {
        Console.WriteLine($"App Name: {AppName}");
    }
}

class Program
{
    static void Main()
    {
        // First access: instance is created lazily
        ConfigurationManager config1 = ConfigurationManager.Instance;
        config1.PrintSettings();

        // Mutating state via the first reference
        config1.AppName = "UpdatedApplication";

        // Second access: uses already created instance
        ConfigurationManager config2 = ConfigurationManager.Instance;
        config2.PrintSettings();

        // Reference equality check
        bool areSame = ReferenceEquals(config1, config2);
        Console.WriteLine($"Are instances equal? {areSame}");
    }
}

/* Результат виконання: **************************************/

--> Initializing ConfigurationManager (happens only once).
App Name: MyApplication
App Name: UpdatedApplication
Are instances equal? True

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн будується на чотирьох ключових механізмах платформи .NET:

  • Модифікатор sealed забороняє успадкування.
  • Приватний конструктор private ConfigurationManager() блокує пряме створення через new.
  • Статичне поле Lazy<ConfigurationManager> забезпечує ліниве створення та потокобезпечність (thread-safety).
  • Публічна статична властивість Instance є єдиною точкою доступу.
2. Розбираємо код по частинах

Модифікатор sealed: Якщо дозволити нащадкам успадковувати цей клас, клас-нащадок зміг би викликати конструктор базового класу через base(), що призвело б до створення другого екземпляра і зламало б логіку Одинака.

Поле Lazy<ConfigurationManager> _instance: Найбільш надійний та ідіоматичний підхід у .NET. За замовчуванням Lazy<T> використовує режим блокування LazyThreadSafetyMode.ExecutionAndPublication. Це гарантує: навіть якщо 100 потоків одночасно звернуться до властивості в першу мілісекунду, конструктор виконається лише один-єдиний раз без написання громіздкого блоку подвійної перевірки (Double-Checked Locking).

Приватний конструктор: Робить неможливим виклик new ConfigurationManager() ззовні. Створити об'єкт дозволено лише лямбда-виразу всередині ініціалізатора Lazy.

Властивість Instance: Повертає значення _instance.Value. Поки до цієї властивості ніхто не звертається, конструктор класу навіть не викликається, заощаджуючи оперативну пам'ять процесу.

3. Що відбувається в Main() по кроках
Крок 1: Перше звернення через config1
Викликається ConfigurationManager.Instance. Внутрішній об'єкт Lazy ще не ініціалізований, тому запускається фабричний делегат: друкується "--> Initializing..." і створюється об'єкт. Метод config1.PrintSettings() виводить дефолтне ім'я "MyApplication".
Крок 2: Зміна стану
Рядок config1.AppName = "UpdatedApplication" модифікує значення властивості в єдиному створеному екземплярі на купі (heap).
Крок 3: Друге звернення через config2
Виклик ConfigurationManager.Instance повертає вже створений раніше екземпляр. Конструктор більше не викликається. Метод PrintSettings() підтверджує оновлені дані: "UpdatedApplication".
Крок 4: Перевірка адреси посилань
Функція ReferenceEquals(config1, config2) перевіряє фізичні адреси вказівників у керованій пам'яті. Вона повертає True, підтверджуючи, що обидві змінні посилаються на один і той самий об'єкт.
4. У чому головна суть патерну?

Singleton централізує спільний стан програми та усуває хаос багаторазового створення ресурсномістких сервісів. Завдяки Lazy<T> досягається максимальна продуктивність читання без накладних витрат на постійні блокування lock при повторних викликах.

4. Плюси та мінуси

  • Переваги: гарантована наявність лише одного об'єкта; економія ресурсів процесора та пам'яті.
  • Недоліки: порушує SRP; ускладнює unit-тестування через наявність спільного мутабельного стану.

Патерн 2: Factory Method (Фабричний метод)*

Породжувальний (Creational)
↑ До змісту

1. Призначення

Визначає спільний інтерфейс для створення об'єкта в базовому класі, але делегує вибір конкретного типу створюваного продукту класам-нащадкам за допомогою поліморфізму.

Важливий нюанс для інтерв'ю: Не плутайте Factory Method з ідіомою «Проста фабрика» (клас зі статичним методом та конструкцією switch/case). Класичний патерн GoF будується саме на успадкуванні класів-творців, що дозволяє підтримувати Open/Closed Principle без модифікації базового класу.

2. Коли застосовувати

  • Заздалегідь невідомо, які саме типи продуктів знадобляться системі в майбутньому.
  • Необхідно надати розробникам бібліотеки чи фреймворку можливість розширювати її новими типами сутностей.

3. Реалізація на C#

using System;

// 1. General product contract
public interface INotification
{
    void Send(string message);
}

// 2. Concrete products
public class EmailNotification : INotification
{
    public void Send(string message)
    {
        Console.WriteLine($"[Email] Sent email: \"{message}\"");
    }
}

public class SmsNotification : INotification
{
    public void Send(string message)
    {
        Console.WriteLine($"[SMS] Sent text message: \"{message}\"");
    }
}

// 3. Base creator class
public abstract class NotificationService
{
    // The Factory Method
    public abstract INotification CreateNotification();

    public void SendAlert(string message)
    {
        INotification notification = CreateNotification();
        notification.Send(message);
    }
}

// 4. Concrete creators
public class EmailNotificationService : NotificationService
{
    public override INotification CreateNotification()
    {
        return new EmailNotification();
    }
}

public class SmsNotificationService : NotificationService
{
    public override INotification CreateNotification()
    {
        return new SmsNotification();
    }
}

// 5. Client usage
class Program
{
    static void Main()
    {
        NotificationService service;
        string notificationType = "email";

        if (notificationType == "email")
            service = new EmailNotificationService();
        else
            service = new SmsNotificationService();

        service.SendAlert("Server restarted!");
    }
}

/* Результат виконання: **************************************/

[Email] Sent email: "Server restarted!"

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн складається з двох паралельних гілок ієрархії:

  • Гілка продуктів: Інтерфейс INotification та його реалізації: EmailNotification і SmsNotification.
  • Гілка творців (Creators): Абстрактний клас NotificationService і підкласи EmailNotificationService та SmsNotificationService.
2. Розбираємо код по частинах

Контракт продукту INotification: Визначає метод Send(string message). Кожен конкретний канал сповіщень зобов'язаний реалізувати цю поведінку.

Базовий сервіс NotificationService:
Метод public abstract INotification CreateNotification(); позначений як abstract — базовий клас не знає, як саме конструюється об'єкт.
Метод SendAlert(string message) задає загальний каркас логіки: викликає фабричний метод CreateNotification(), отримує екземпляр продукту й викликає Send(). Базовий клас ізольований від конкретних конструкторів.

Підкласи-творці: EmailNotificationService перевизначає метод через override та повертає new EmailNotification(). Аналогічно SmsNotificationService повертає new SmsNotification().

3. Що відбувається в Main() по кроках
Крок 1: Вибір творця
Змінна notificationType дорівнює "email". Код інстанціює service = new EmailNotificationService() та зберігає посилання в змінній базового типу NotificationService.
Крок 2: Виклик високорівневого методу
Викликається метод service.SendAlert("Server restarted!").
Крок 3: Поліморфний виклик фабричного методу
Всередині SendAlert викликається CreateNotification(). Оскільки фактичним типом об'єкта є EmailNotificationService, за таблицею віртуальних методів викликається саме його перевизначений метод, який повертає EmailNotification.
Крок 4: Виконання дії продукту
Об'єкт сповіщення викликає метод Send(...), друкуючи в консоль: [Email] Sent email: "Server restarted!".
4. У чому перевага над звичайним switch?

Якщо необхідно додати новий тип сповіщень (наприклад, Telegram), не потрібно змінювати код базового класу NotificationService. Достатньо лише створити два нових незалежних класи:

  • public class TelegramNotification : INotification
  • public class TelegramNotificationService : NotificationService

Існуючий код залишається повністю закритим для модифікації, але відкритим для розширення (принцип OCP).

4. Плюси та мінуси

  • Переваги: усуває жорстке зачеплення (Loose Coupling); дозволяє легко додавати нові типи продуктів.
  • Недоліки: призводить до розростання ієрархії класів через створення підкласу-фабрики під кожен новий продукт.

Патерн 3: Abstract Factory (Абстрактна фабрика)*

Породжувальний (Creational)
↑ До змісту

1. Призначення

Надає інтерфейс для створення цілих сімейств взаємопов'язаних або взаємозалежних об'єктів, не прив'язуючись до їхніх конкретних класів.

2. Коли застосовувати

  • Система повинна підтримувати кілька платформ, тем або рушіїв (наприклад, Windows, macOS, Linux).
  • Об'єкти всередині одного сімейства обов'язково мають бути сумісними і не повинні випадково змішуватися.

3. Реалізація на C#

using System;

// 1. Abstract products
public interface IButton
{
    void Render();
}

public interface ICheckbox
{
    void Render();
}

// 2. Concrete products for Windows
public class WindowsButton : IButton
{
    public void Render() => Console.WriteLine("Rendering button in Windows style.");
}

public class WindowsCheckbox : ICheckbox
{
    public void Render() => Console.WriteLine("Rendering checkbox in Windows style.");
}

// 3. Concrete products for macOS
public class MacButton : IButton
{
    public void Render() => Console.WriteLine("Rendering button in macOS style.");
}

public class MacCheckbox : ICheckbox
{
    public void Render() => Console.WriteLine("Rendering checkbox in macOS style.");
}

// 4. Abstract factory contract
public interface IGuiFactory
{
    IButton CreateButton();

    ICheckbox CreateCheckbox();
}

// 5. Concrete factories
public class WindowsFactory : IGuiFactory
{
    public IButton CreateButton() => new WindowsButton();

    public ICheckbox CreateCheckbox() => new WindowsCheckbox();
}

public class MacFactory : IGuiFactory
{
    public IButton CreateButton() => new MacButton();

    public ICheckbox CreateCheckbox() => new MacCheckbox();
}

// 6. Client application
public class Application
{
    private readonly IButton _button;
    private readonly ICheckbox _checkbox;

    public Application(IGuiFactory factory)
    {
        _button = factory.CreateButton();
        _checkbox = factory.CreateCheckbox();
    }

    public void Paint()
    {
        _button.Render();
        _checkbox.Render();
    }
}

class Program
{
    static void Main()
    {
        string osName = "mac";
        IGuiFactory factory = osName == "win" ? new WindowsFactory() : new MacFactory();

        var app = new Application(factory);
        app.Paint();
    }
}

/* Результат виконання: **************************************/

Rendering button in macOS style.
Rendering checkbox in macOS style.

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

У патерні виділяються дві взаємопов'язані частини:

  • Продукти: Інтерфейси IButton та ICheckbox із конкретними реалізаціями під кожну платформу.
  • Фабрики: Інтерфейс IGuiFactory та його конкретні реалізації WindowsFactory і MacFactory.
  • Клієнт Application: Працює виключно через інтерфейси й ніколи не посилається на конкретні класи платформ.
2. Розбираємо код по частинах

Контракти продуктів: Визначають операції над UI-елементами (метод Render()). Клієнтський код не знає нічого про конкретну розмітку чи стиль відмальовування.

Інтерфейс IGuiFactory: Описує контракт на створення повної лінійки сумісних елементів (кнопка + чекбокс). Фабрика гарантує, що неможливо отримати кнопку від однієї ОС, а чекбокс — від іншої.

Клас Application: Отримує фабрику через конструктор (впровадження залежностей). Він викликає методи створення та делегує малювання елементам:

_button = factory.CreateButton();
_checkbox = factory.CreateCheckbox();
3. Що відбувається в Main() по кроках
Крок 1: Вибір фабрики платформи
Умова osName == "win" повертає MacFactory. Посилання зберігається в змінній інтерфейсного типу IGuiFactory.
Крок 2: Передача фабрики в клієнтський код
Викликається new Application(factory). Конструктор створює взаємосумісну пару: MacButton та MacCheckbox.
Крок 3: Рендеринг інтерфейсу
Виклик app.Paint() викликає .Render() для кожного елемента:
Rendering button in macOS style.
Rendering checkbox in macOS style.
4. У чому головна користь патерну?

Патерн гарантує 100% сумісність продуктів. Клієнтський код захищений від випадкового змішування компонентів різних стилів на етапі компіляції.

4. Плюси та мінуси

  • Переваги: гарантована сумісність усіх створюваних сутностей родини; ізоляція клієнта від конкретних реалізацій.
  • Недоліки: складно додавати нові типи продуктів у родину (вимагає змін у інтерфейсі IGuiFactory та всіх його реалізаціях).

Патерн 4: Builder (Будівельник)*

Породжувальний (Creational)
↑ До змісту

1. Призначення

Відокремлює процес конструювання складного об'єкта від його представлення, дозволяючи покроково створювати різні конфігурації за допомогою зрозумілого ланцюжкового виклику методів (Fluent API).

2. Коли застосовувати

  • Конструктор класу розрісся до 8+ параметрів, більшість з яких опціональні («Телескопічний конструктор»).
  • Перед поверненням об'єкта клієнту потрібно провести сувору валідацію цілісності стану.
Де зустрічається в .NET: StringBuilder, WebApplication.CreateBuilder(), налаштування маршрутизації в Program.cs.

3. Реалізація на C#

using System;

// 1. Complex product
public class Computer
{
    public string CPU { get; set; }
    public string RAM { get; set; }
    public string Storage { get; set; }
    public string GPU { get; set; }
    public bool HasWaterCooling { get; set; }

    public void DisplayInfo()
    {
        Console.WriteLine("PC Configuration:");
        Console.WriteLine($" - CPU: {CPU}");
        Console.WriteLine($" - RAM: {RAM}");
        Console.WriteLine($" - Storage: {Storage}");
        Console.WriteLine($" - GPU: {GPU ?? "Integrated"}");
        Console.WriteLine($" - Water Cooling: {(HasWaterCooling ? "Yes" : "No")}\n");
    }
}

// 2. Fluent Builder
public class ComputerBuilder
{
    private Computer _computer = new Computer();

    public ComputerBuilder SetCPU(string cpu)
    {
        _computer.CPU = cpu;
        return this;
    }

    public ComputerBuilder SetRAM(string ram)
    {
        _computer.RAM = ram;
        return this;
    }

    public ComputerBuilder SetStorage(string storage)
    {
        _computer.Storage = storage;
        return this;
    }

    public ComputerBuilder SetGPU(string gpu)
    {
        _computer.GPU = gpu;
        return this;
    }

    public ComputerBuilder EnableWaterCooling()
    {
        _computer.HasWaterCooling = true;
        return this;
    }

    public Computer Build()
    {
        if (string.IsNullOrEmpty(_computer.CPU) || string.IsNullOrEmpty(_computer.RAM))
        {
            throw new InvalidOperationException("CPU and RAM are required!");
        }

        Computer result = _computer;
        _computer = new Computer();
        return result;
    }
}

// 3. Director (optional helper)
public class ComputerDirector
{
    public void BuildGamingPC(ComputerBuilder builder)
    {
        builder.SetCPU("Intel Core i9")
               .SetRAM("32GB DDR5")
               .SetStorage("2TB NVMe SSD")
               .SetGPU("NVIDIA RTX 4090")
               .EnableWaterCooling();
    }

    public void BuildOfficePC(ComputerBuilder builder)
    {
        builder.SetCPU("Intel Core i3")
               .SetRAM("8GB DDR4")
               .SetStorage("512GB SSD");
    }
}

class Program
{
    static void Main()
    {
        var builder = new ComputerBuilder();

        // Custom PC via Fluent API
        Computer customPC = builder
            .SetCPU("AMD Ryzen 7")
            .SetRAM("16GB DDR5")
            .SetStorage("1TB SSD")
            .SetGPU("AMD Radeon RX 7800")
            .Build();

        customPC.DisplayInfo();

        // Standard build via Director
        var director = new ComputerDirector();
        director.BuildGamingPC(builder);
        Computer gamingPC = builder.Build();
        gamingPC.DisplayInfo();
    }
}

🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн розділяє обов'язки між трьома сутностями:

  • Продукт Computer: Складний об'єкт із багатьма характеристиками.
  • Будівельник ComputerBuilder: Надає методи покрокового заповнення параметрів і повертає this.
  • Директор ComputerDirector: Інкапсулює типові шаблони збирання готових продуктів.
2. Розбираємо код по частинах

Концепція Fluent API: Кожен конфігураційний метод закінчується інструкцією return this;. Завдяки цьому виклики вибудовуються в зручний ланцюжок: builder.SetCPU(...).SetRAM(...).Build().

Метод Build(): Фінальна точка створення. Перевіряє наявність обов'язкових полів (CPU та RAM). Якщо умови порушено, викидається виняток InvalidOperationException. Обнулення _computer = new Computer(); готує будівельник до наступного збирання.

Клас ComputerDirector: Допоміжний клас для позбавлення дублювання коду, коли потрібні стандартизовані пресети конфігурацій (Office PC, Gaming PC).

3. Що відбувається в Main() по кроках
Крок 1: Кастомне збирання через Fluent API
Клієнт передає потрібні компоненти по черзі. Метод Build() валідує поля та повертає сконфігурований екземпляр.
Крок 2: Типове збирання через Директора
Директор викликає попередньо налаштований набір викликів на тому самому екземплярі будівельника.
Крок 3: Отримання другого екземпляра
Виклик builder.Build() повертає топовий ігровий ПК. Результати підтверджують повну ізоляцію двох створених машин.
4. У чому головна користь патерну?

Будівельник усуває помилки під час передачі аргументів однакових типів у довгий конструктор та гарантує, що неможливо отримати некоректно сконфігурований об'єкт.

4. Плюси та мінуси

  • Переваги: покрокове конструювання; читабельний Fluent-синтаксис; централізована валідація в Build().
  • Недоліки: створення додаткового класу будівельника збільшує загальний обсяг коду.

Патерн 5: Prototype (Прототип)

Породжувальний (Creational)
↑ До змісту

1. Призначення

Дозволяє копіювати існуючі об'єкти, не прив'язуючись до деталей їхніх конкретних класів і без повторного виклику їхніх конструкторів.

2. Коли застосовувати

  • Створення об'єкта через new є ресурсомістким (важкі обчислення, запити в БД).
  • Необхідно створювати копії об'єктів, тип яких відомий клієнту лише через інтерфейс.
Порада для C#: Інтерфейс ICloneable вважається застарілим через нетипізованість (object). Рекомендується оголошувати типізований інтерфейс IPrototype<T> або застосовувати record with { ... } у сучасному C#.

3. Реалізація на C#

using System;

public interface IPrototype<T>
{
    T Clone();
}

public class Author
{
    public string Name { get; set; }

    public Author(string name) => Name = name;
}

public class Document : IPrototype<Document>
{
    public string Title { get; set; }
    public string Content { get; set; }
    public Author Author { get; set; }

    public Document(string title, string content, Author author)
    {
        Title = title;
        Content = content;
        Author = author;
    }

    public Document Clone()
    {
        Document clone = (Document)this.MemberwiseClone();
        // Deep copy of reference type
        clone.Author = new Author(this.Author.Name);
        return clone;
    }

    public void DisplayInfo()
    {
        Console.WriteLine($"Document: '{Title}', Author: {Author.Name}, Content: '{Content}'");
    }
}

class Program
{
    static void Main()
    {
        var originalDoc = new Document("Template", "Standard content...", new Author("Alex"));
        Document clonedDoc = originalDoc.Clone();

        clonedDoc.Title = "Q3 Report";
        clonedDoc.Author.Name = "Iryna";

        Console.WriteLine("Clone:");
        clonedDoc.DisplayInfo();

        Console.WriteLine("Original:");
        originalDoc.DisplayInfo();
    }
}

/* Результат виконання: **************************************/

Clone:
Document: 'Q3 Report', Author: Iryna, Content: 'Standard content...'
Original:
Document: 'Template', Author: Alex, Content: 'Standard content...'

/*************************************************************/

4. Плюси та мінуси

  • Переваги: швидке дублювання об'єктів у рантаймі; уникнення повторної важкої ініціалізації.
  • Недоліки: глибоке копіювання складних об'єктів із циклічними посиланнями вимагає додаткових зусиль.
