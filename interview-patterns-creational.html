Відповідають за гнучке й безпечне створення об'єктів без жорсткого зв'язування з конкретними класами

Швидкий перехід по розділу

  • 1. Singleton* (Одинак)

Патерн 1: Singleton (Одинак)*

Породжувальний (Creational)
↑ До змісту

1. Призначення

Гарантує, що клас має лише один екземпляр у межах усієї програми, і надає глобальну спільну точку доступу до нього.

2. Коли застосовувати

  • Потрібен спільний ресурс, який має існувати в єдиному екземплярі: кеш у пам'яті, конфігурація додатка, пул з'єднань з апаратним портом.
  • Необхідно повністю заблокувати створення дублікатів через випадковий виклик new.
Примітка для .NET: У сучасних вебдодатках класичний ручний Singleton зазвичай замінюють реєстрацією в DI-контейнері: builder.Services.AddSingleton<IConfigurationManager, ConfigurationManager>(). Проте розуміти канонічну реалізацію в пам'яті на рівні CLR обов'язково для кожної співбесіди.

3. Реалізація на C#

using System;

// 'sealed' prevents derivation, which could break the singleton invariant
public sealed class ConfigurationManager
{
    // Lazy<T> ensures thread-safety and creates the instance on first access
    private static readonly Lazy<ConfigurationManager> _instance = 
        new Lazy<ConfigurationManager>(() => new ConfigurationManager());

    // 1. Private constructor prevents instantiation via 'new ConfigurationManager()' from outside
    private ConfigurationManager()
    {
        Console.WriteLine("--> Initializing ConfigurationManager (happens only once).");
    }

    // 2. Global access point to the singleton instance
    public static ConfigurationManager Instance => _instance.Value;

    // Service state
    public string AppName { get; set; } = "MyApplication";

    public void PrintSettings()
    {
        Console.WriteLine($"App Name: {AppName}");
    }
}

class Program
{
    static void Main()
    {
        // First access: instance is created lazily
        ConfigurationManager config1 = ConfigurationManager.Instance;
        config1.PrintSettings();

        // Mutating state via the first reference
        config1.AppName = "UpdatedApplication";

        // Second access: uses already created instance
        ConfigurationManager config2 = ConfigurationManager.Instance;
        config2.PrintSettings();

        // Reference equality check
        bool areSame = ReferenceEquals(config1, config2);
        Console.WriteLine($"Are instances equal? {areSame}");
    }
}

/* Результат виконання: **************************************/

--> Initializing ConfigurationManager (happens only once).
App Name: MyApplication
App Name: UpdatedApplication
Are instances equal? True

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви офіс, у якому стоїть один спільний мережевий принтер. Кожен співробітник, коли йому треба надрукувати звіт, звертається до цього конкретного принтера. Було б абсурдом і марнотратством, якби кожен співробітник під кожну сторінку купував собі власний новенький принтер. Singleton робить саме це: тримає один спільний об'єкт на весь додаток.

1. Як влаштований код
ConfigurationManager (sealed — заборонено успадковувати) │ ├── Lazy<ConfigurationManager> _instance ──► Спить у пам'яті до першого виклику ├── private ConfigurationManager() ──► Двері замкнені: 'new' ззовні заборонено └── Instance (public static) ──► Єдине віконце доступу до екземпляра

Головна ідея: ніхто ззовні не може створити об'єкт самостійно. Клас сам контролює власне народження і роздає одне й те саме посилання усім охочим.

2. Розбираємо код по частинах

Частина 1. Модифікатор sealed

Чому цей рядок настільки важливий?

public sealed class ConfigurationManager

Слово sealed забороняє будь-якому іншому класу успадкувати ConfigurationManager. Якби ми цього не зробили, якийсь підклас міг би викликати конструктор базового класу через base() і створити другий екземпляр у пам'яті, зламавши всю гарантію Одинака.

Частина 2. Поле Lazy<ConfigurationManager>

Ось цей рядок — найбільш елегантний та ідіоматичний спосіб реалізувати Singleton у сучасному .NET:

private static readonly Lazy<ConfigurationManager> _instance = 
    new Lazy<ConfigurationManager>(() => new ConfigurationManager());

Зверни увагу на три ключові моменти:

  • Лінивість (Lazy): Об'єкт не займає пам'ять при старті програми. Якщо за весь час роботи додатка ніхто так і не звернувся до конфігурації, конструктор взагалі ніколи не виконається.
  • Повна потокобезпечність (Thread-safety): За замовчуванням Lazy<T> використовує режим блокування CLR ExecutionAndPublication. Навіть якщо 50 фонових потоків одночасно в одну наносекунду постукають у конфігурацію, об'єкт створиться строго один раз без жодних race conditions і без потреби вручну городити громіздкий код lock (lockObj).
  • readonly: Посилання на фабрику неможливо випадково перезаписати чи обнулити з іншого методу.

Частина 3. Приватний конструктор

private ConfigurationManager() { ... }

Конструктор оголошений із модифікатором private. Спроба написати в будь-якому місці програми var cfg = new ConfigurationManager(); викличе помилку компіляції: «Inaccessible due to its protection level». Доступ до створення є лише у внутрішнього лямбда-виразу () => new ConfigurationManager().

Частина 4. Точка доступу Instance

public static ConfigurationManager Instance => _instance.Value;

Публічна статична властивість. Саме через звернення до .Value клас Lazy «прокидається», конструює об'єкт при першому виклику і віддає його назад. При всіх наступних зверненнях воно просто миттєво повертає вже готовий результат.

3. Що відбувається в Main() крок за кроком
Крок 1 — Перший виклик (config1):
Код викликає ConfigurationManager.Instance. Об'єкт Lazy бачить, що екземпляра на купі (heap) ще немає, тому викликає конструктор. На екран друкується:
--> Initializing ConfigurationManager (happens only once).
Після цього config1.PrintSettings() друкує початкове значення: App Name: MyApplication.
Крок 2 — Зміна значення:
Ми змінюємо властивість через змінну config1.AppName = "UpdatedApplication";. Зміна відбувається безпосередньо в комірці пам'яті цього об'єкта.
Крок 3 — Другий виклик (config2):
Ми знову звертаємося до ConfigurationManager.Instance, але вже через змінну config2. Конструктор більше не викликається! Ми отримуємо те саме посилання, і виклик config2.PrintSettings() одразу бачить змінені дані: App Name: UpdatedApplication.
Крок 4 — Перевірка через ReferenceEquals:
Метод ReferenceEquals(config1, config2) перевіряє не просто однаковість полів, а чи збігаються фізичні адреси вказівників у RAM. Результат True на 100% доводить, що це один і той самий об'єкт.
4. У чому саме полягає суть Singleton та чому це краще?

Без патерну: Кожен новий сервіс, якому потрібна конфігурація, викликав би new ConfigurationManager(). Додаток 20 разів перечитував би важкі файли з диска, забивав би пам'ять дублікатами налаштувань, а зміна налаштування в одному місці ніколи не дійшла б до іншого.

З Singleton: Дані конфігурації завжди синхронізовані в усій програмі, пам'ять витрачається лише на один екземпляр, а доступ до нього швидкий і глобальний.

4. Плюси та мінуси

  • Переваги: сувора гарантія одного екземпляра; безпечне відкладене завантаження (економія пам'яті); глобальний доступ.
  • Недоліки: приховує залежності класів; ускладнює unit-тести (тести можуть впливати один на одного через спільний мутабельний стан).

Патерн 2: Factory Method (Фабричний метод)*

Породжувальний (Creational)
↑ До змісту

1. Призначення

Визначає загальний інтерфейс для створення об'єкта в базовому класі, але дозволяє підкласам змінювати тип створюваного продукту за допомогою поліморфізму.

2. Коли застосовувати

  • Заздалегідь невідомо, які конкретно типи об'єктів знадобляться вашій системі в майбутньому.
  • Потрібно дотримуватися принципу відкритості/закритості (Open/Closed Principle): легко додавати нові продукти без модифікації існуючого коду.

3. Реалізація на C#

using System;

// 1. General product contract
public interface INotification
{
    void Send(string message);
}

// 2. Concrete products
public class EmailNotification : INotification
{
    public void Send(string message)
    {
        Console.WriteLine($"[Email] Sent email: \"{message}\"");
    }
}

public class SmsNotification : INotification
{
    public void Send(string message)
    {
        Console.WriteLine($"[SMS] Sent text message: \"{message}\"");
    }
}

// 3. Base creator class
public abstract class NotificationService
{
    // The Factory Method
    public abstract INotification CreateNotification();

    public void SendAlert(string message)
    {
        INotification notification = CreateNotification();
        notification.Send(message);
    }
}

// 4. Concrete creators
public class EmailNotificationService : NotificationService
{
    public override INotification CreateNotification()
    {
        return new EmailNotification();
    }
}

public class SmsNotificationService : NotificationService
{
    public override INotification CreateNotification()
    {
        return new SmsNotification();
    }
}

// 5. Client usage
class Program
{
    static void Main()
    {
        NotificationService service;
        string notificationType = "email";

        if (notificationType == "email")
            service = new EmailNotificationService();
        else
            service = new SmsNotificationService();

        service.SendAlert("Server restarted!");
    }
}

/* Результат виконання: **************************************/

[Email] Sent email: "Server restarted!"

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви логістичну компанію. Головний офіс знає бізнес-правило: «Щоб виконати доставку, треба взяти транспортний засіб і відправити вантаж». Але офіс у Києві перевозить вантажі вантажівками, а філія в Одесі — морськими суднами. Головному офісу байдуже, що це за транспорт — головне, щоб він умів доставляти. Класичний Factory Method якраз і дозволяє перенести вибір транспорту на рівень конкретних підрозділів.

1. Як влаштований код
NotificationService (базовий сервіс: знає ЯК сповіщати, але не знає ЩО створювати) ├── SendAlert(message) ──► Загальний бізнес-алгоритм └── abstract CreateNotification() ──► ФАБРИЧНИЙ МЕТОД (дірка в коді під нащадків) ▲ │ успадковують ┌─────────┴─────────────────────┐ │ │ EmailNotificationService SmsNotificationService │ (перевизначає) │ (перевизначає) ▼ ▼ EmailNotification SmsNotification ──► (реалізують INotification)

Головна ідея: базовий клас керує процесом відправки, але делегує саме створення об'єкта підкласам через поліморфний метод.

2. Розбираємо код по частинах

Частина 1. Інтерфейс продукту INotification

public interface INotification
{
    void Send(string message);
}

Це спільний знаменник. Будь-яке сповіщення — хоч пошта, хоч SMS, хоч поштовий голуб — зобов'язане мати метод Send.

Частина 2. Конкретні продукти EmailNotification та SmsNotification

Кожен клас містить власну унікальну логіку доставки. Email пише в поштовий протокол SMTP, а SMS шле команди на GSM-модем.

Частина 3. Базовий клас-творець NotificationService

Зверни увагу на дві ключові речі всередині цього класу:

public abstract INotification CreateNotification();

1. Метод позначений як abstract. Це означає: «Я поняття не маю, як створювати конкретне сповіщення, це робота моїх дітей-підкласів».

public void SendAlert(string message)
{
    INotification notification = CreateNotification();
    notification.Send(message);
}

2. Метод SendAlert містить реальну роботу! Він не створює об'єкт через new. Він викликає власний фабричний метод, отримує абстрактний інтерфейс і викликає Send. Базовий клас повністю захищений від деталей конкретних реалізацій.

Частина 4. Конкретні творці

public class EmailNotificationService : NotificationService
{
    public override INotification CreateNotification() => new EmailNotification();
}

Ось і вся фабрика! Підклас лише каже: «Коли в мене попросять сповіщення, я створю саме EmailNotification».

3. Що відбувається в Main() крок за кроком
Крок 1 — Вибір сервісу:
Змінна notificationType = "email". Програма створює new EmailNotificationService() і зберігає його в змінній абстрактного типу NotificationService.
Крок 2 — Виклик бізнес-методу:
Клієнт викликає service.SendAlert("Server restarted!").
Крок 3 — Магія поліморфізму:
Всередині SendAlert викликається CreateNotification(). Завдяки таблиці віртуальних методів CLR викликає версію з EmailNotificationService. Створюється екземпляр EmailNotification.
Крок 4 — Відправка:
Створений об'єкт відправляє лист і виводить у консоль:
[Email] Sent email: "Server restarted!".
4. Чому це краще за звичайний switch/case (Simple Factory)?
Пастка на інтерв'ю: Часто новачки пишуть один клас зі статичним методом Create(string type) і конструкцією switch (type). Це антипатерн щодо Open/Closed Principle!

Уяви, що треба додати сповіщення через Telegram.
• Зі switch: тобі доведеться відкривати старий клас і лізти в робочий перевірений код, ризикуючи зламати існуючі сценарії.
• З Factory Method: ти просто створюєш два новенькі класи: TelegramNotification : INotification та TelegramNotificationService : NotificationService. Старий код навіть не перекомпільовується! Він відкритий до розширення, але закритий до змін.

4. Плюси та мінуси

  • Переваги: усуває жорстке зв'язування між бізнес-логікою та конкретними типами; чисте дотримання Open/Closed Principle.
  • Недоліки: розмноження класів: під кожен новий продукт доводиться створювати власний підклас творця.

Патерн 3: Abstract Factory (Абстрактна фабрика)*

Породжувальний (Creational)
↑ До змісту

1. Призначення

Надає інтерфейс для створення цілих родин взаємопов'язаних або сумісних об'єктів, не прив'язуючись до їхніх конкретних класів.

2. Коли застосовувати

  • Програма повинна працювати з різними сімействами продуктів, які категорично не можна змішувати між собою (наприклад, елементи UI для Windows і macOS, або набір драйверів під PostgreSQL і Oracle).
  • Потрібно гарантувати, що клієнт отримає сумісний комплект компонентів від початку й до кінця.

3. Реалізація на C#

using System;

// 1. Abstract products
public interface IButton
{
    void Render();
}

public interface ICheckbox
{
    void Render();
}

// 2. Concrete products for Windows
public class WindowsButton : IButton
{
    public void Render() => Console.WriteLine("Rendering button in Windows style.");
}

public class WindowsCheckbox : ICheckbox
{
    public void Render() => Console.WriteLine("Rendering checkbox in Windows style.");
}

// 3. Concrete products for macOS
public class MacButton : IButton
{
    public void Render() => Console.WriteLine("Rendering button in macOS style.");
}

public class MacCheckbox : ICheckbox
{
    public void Render() => Console.WriteLine("Rendering checkbox in macOS style.");
}

// 4. Abstract factory contract
public interface IGuiFactory
{
    IButton CreateButton();

    ICheckbox CreateCheckbox();
}

// 5. Concrete factories
public class WindowsFactory : IGuiFactory
{
    public IButton CreateButton() => new WindowsButton();

    public ICheckbox CreateCheckbox() => new WindowsCheckbox();
}

public class MacFactory : IGuiFactory
{
    public IButton CreateButton() => new MacButton();

    public ICheckbox CreateCheckbox() => new MacCheckbox();
}

// 6. Client application
public class Application
{
    private readonly IButton _button;
    private readonly ICheckbox _checkbox;

    public Application(IGuiFactory factory)
    {
        _button = factory.CreateButton();
        _checkbox = factory.CreateCheckbox();
    }

    public void Paint()
    {
        _button.Render();
        _checkbox.Render();
    }
}

class Program
{
    static void Main()
    {
        string osName = "mac";
        IGuiFactory factory = osName == "win" ? new WindowsFactory() : new MacFactory();

        var app = new Application(factory);
        app.Paint();
    }
}

/* Результат виконання: **************************************/

Rendering button in macOS style.
Rendering checkbox in macOS style.

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви, що ти замовляєш комплект меблів для вітальні. Якщо ти обрав стиль «Хай-тек», тобі потрібні скляний стіл і хромований стілець. Якщо обрав «Вікторіанський стиль» — масивний дубовий стіл і різьблене крісло з оксамитом. Якщо ти поставиш різьблене вікторіанське крісло до скляного хай-тек столу, це виглядатиме жахливо. Абстрактна фабрика гарантує: клієнт завжди отримає меблі виключно з однієї дизайнерської лінійки.

1. Як влаштований код
IGuiFactory (Абстрактна фабрика: фабрикує ЦІЛУ РОДИНУ) ├── CreateButton() └── CreateCheckbox() ▲ │ реалізують ┌─────┴──────────────────┐ │ │ WindowsFactory MacFactory ├── WindowsButton ├── MacButton └── WindowsCheckbox └── MacCheckbox ▲ ▲ │ │ (Родина Windows) (Родина macOS)

Головна ідея: фабрика створює не один ізольований предмет, а повний гарнітур сумісних предметів.

2. Розбираємо код по частинах

Частина 1. Інтерфейси продуктів

У нас є два незалежні типи інтерфейсних елементів: кнопки (IButton) та чекбокси (ICheckbox). Кожен із них вміє малюватися через Render().

Частина 2. Конкретні продукти

Ми маємо класи WindowsButton, WindowsCheckbox, а також MacButton, MacCheckbox. Вони відрізняються стилем відмальовки під відповідну операційну систему.

Частина 3. Контракт абстрактної фабрики IGuiFactory

public interface IGuiFactory
{
    IButton CreateButton();
    ICheckbox CreateCheckbox();
}

Цей інтерфейс зобов'язує будь-яку конкретну фабрику постачати обидва елементи. Компілятор фізично не дозволить створити фабрику, яка вміє робити кнопку, але забула про чекбокс.

Частина 4. Клієнтський клас Application

public Application(IGuiFactory factory)
{
    _button = factory.CreateButton();
    _checkbox = factory.CreateCheckbox();
}

Поглянь на конструктор додатку: він приймає лише інтерфейс IGuiFactory. Всередині додатка немає жодного слова про Windows чи macOS! Додаток бере фабрику, викликає методи й отримує гарантовано узгоджені між собою компоненти.

3. Що відбувається в Main() крок за кроком
Крок 1 — Вибір фабрики за конфігурацією:
Змінна osName = "mac". Програма обирає new MacFactory().
Крок 2 — Створення додатку:
Ми передаємо цю фабрику в new Application(factory). Конструктор викликає створення кнопки й чекбокса. Фабрика повертає MacButton і MacCheckbox.
Крок 3 — Відображення UI:
Виклик app.Paint() виводить у консоль узгоджений інтерфейс macOS:
Rendering button in macOS style.
Rendering checkbox in macOS style.
4. У чому різниця між Factory Method та Abstract Factory?

Це найпопулярніше питання на будь-якому технічному інтерв'ю з C#:

  • Factory Method: створює один конкретний продукт за допомогою механізму успадкування (один абстрактний метод у базовому класі сервісу).
  • Abstract Factory: створює цілі родини взаємопов'язаних продуктів за допомогою механізму композиції (окремий об'єкт-фабрика з багатьма методами створення).

4. Плюси та мінуси

  • Переваги: залізобетонна сумісність усіх створених продуктів; легка заміна стилів чи платформ в один рядок конфігурації.
  • Недоліки: важко додавати нові типи продуктів (якщо додати в родину третій елемент ISlider, доведеться переписати інтерфейс фабрики та всі створені класи фабрик).

Патерн 4: Builder (Будівельник)*

Породжувальний (Creational)
↑ До змісту

1. Призначення

Відокремлює процес покрокового конструювання складного об'єкта від його представлення, дозволяючи за допомогою однакового коду створювати різні конфігурації об'єктів (Fluent API).

2. Коли застосовувати

  • Позбавлення антипатерну «Телескопічний конструктор»: коли конструктор має 10 параметрів, більшість із яких необов'язкові або null.
  • Створення об'єкта вимагає багатьох послідовних кроків або попередньої суворої валідації сумісності параметрів.
Приклади у .NET: StringBuilder, WebApplication.CreateBuilder(), конфігурація маршрутів у Program.cs.

3. Реалізація на C#

using System;

// 1. Complex product
public class Computer
{
    public string CPU { get; set; }
    public string RAM { get; set; }
    public string Storage { get; set; }
    public string GPU { get; set; }
    public bool HasWaterCooling { get; set; }

    public void DisplayInfo()
    {
        Console.WriteLine("PC Configuration:");
        Console.WriteLine($" - CPU: {CPU}");
        Console.WriteLine($" - RAM: {RAM}");
        Console.WriteLine($" - Storage: {Storage}");
        Console.WriteLine($" - GPU: {GPU ?? "Integrated"}");
        Console.WriteLine($" - Water Cooling: {(HasWaterCooling ? "Yes" : "No")}\n");
    }
}

// 2. Fluent Builder
public class ComputerBuilder
{
    private Computer _computer = new Computer();

    public ComputerBuilder SetCPU(string cpu)
    {
        _computer.CPU = cpu;
        return this;
    }

    public ComputerBuilder SetRAM(string ram)
    {
        _computer.RAM = ram;
        return this;
    }

    public ComputerBuilder SetStorage(string storage)
    {
        _computer.Storage = storage;
        return this;
    }

    public ComputerBuilder SetGPU(string gpu)
    {
        _computer.GPU = gpu;
        return this;
    }

    public ComputerBuilder EnableWaterCooling()
    {
        _computer.HasWaterCooling = true;
        return this;
    }

    public Computer Build()
    {
        if (string.IsNullOrEmpty(_computer.CPU) || string.IsNullOrEmpty(_computer.RAM))
        {
            throw new InvalidOperationException("CPU and RAM are required!");
        }

        Computer result = _computer;
        _computer = new Computer();
        return result;
    }
}

// 3. Director (optional helper)
public class ComputerDirector
{
    public void BuildGamingPC(ComputerBuilder builder)
    {
        builder.SetCPU("Intel Core i9")
               .SetRAM("32GB DDR5")
               .SetStorage("2TB NVMe SSD")
               .SetGPU("NVIDIA RTX 4090")
               .EnableWaterCooling();
    }

    public void BuildOfficePC(ComputerBuilder builder)
    {
        builder.SetCPU("Intel Core i3")
               .SetRAM("8GB DDR4")
               .SetStorage("512GB SSD");
    }
}

class Program
{
    static void Main()
    {
        var builder = new ComputerBuilder();

        // Custom PC via Fluent API
        Computer customPC = builder
            .SetCPU("AMD Ryzen 7")
            .SetRAM("16GB DDR5")
            .SetStorage("1TB SSD")
            .SetGPU("AMD Radeon RX 7800")
            .Build();

        customPC.DisplayInfo();

        // Standard build via Director
        var director = new ComputerDirector();
        director.BuildGamingPC(builder);
        Computer gamingPC = builder.Build();
        gamingPC.DisplayInfo();
    }
}

PC Configuration:
 - CPU: AMD Ryzen 7
 - RAM: 16GB DDR5
 - Storage: 1TB SSD
 - GPU: AMD Radeon RX 7800
 - Water Cooling: No

PC Configuration:
 - CPU: Intel Core i9
 - RAM: 32GB DDR5
 - Storage: 2TB NVMe SSD
 - GPU: NVIDIA RTX 4090
 - Water Cooling: Yes

🔍 Детальний розбір: як влаштований і працює цей код

Уяви збирання бургера в ресторані. Тобі не дають 100 готових коробок на вибір. Ти сам кажеш: «Мені булку з кунжутом, яловичу котлету, подвійний сир, без цибулі, соус тар-тар». Ти береш лише те, що хочеш, у потрібній комбінації. Builder дає таку саму свободу конструювання складних об'єктів у коді.

1. Як влаштований код
ComputerBuilder (Будівельник з Fluent API) ├── SetCPU(...) ──► повертає 'this' (секрет виклику через крапку) ├── SetRAM(...) ──► повертає 'this' ├── SetGPU(...) ──► повертає 'this' ├── EnableWater...() ──► повертає 'this' └── Build() ──► Перевіряє валідність та повертає готовий Computer ▲ │ (опціонально керує процесом) ComputerDirector (Директор: знає рецепти готових збірок — Gaming, Office)
2. Розбираємо код по частинах

Частина 1. Складний клас Computer

У класі є 5 різних характеристик. Деякі з них обов'язкові (процесор, пам'ять), а деякі опціональні (відеокарта, водяне охолодження).

Частина 2. Секрет Fluent API (return this;)

Поглянь на метод будівельника:

public ComputerBuilder SetCPU(string cpu)
{
    _computer.CPU = cpu;
    return this; // Повертаємо сам екземпляр будівельника!
}

Завдяки поверненню this ми можемо викликати наступні методи «паровозиком» через крапку: builder.SetCPU(...).SetRAM(...).Build(). Це робить код кришталево чистим і самодокументованим.

Частина 3. Метод Build() — точка валідації

Саме тут відбувається перевірка правил цілісності об'єкта перед тим, як віддати його клієнту:

if (string.IsNullOrEmpty(_computer.CPU) || string.IsNullOrEmpty(_computer.RAM))
{
    throw new InvalidOperationException("CPU and RAM are required!");
}

Ніхто не зможе отримати неробочий комп'ютер без процесора чи пам'яті. Також рядок _computer = new Computer(); очищує стан будівельника, тому його можна використовувати повторно.

Частина 4. Роль Директора (ComputerDirector)

Директор не обов'язковий, але дуже корисний, коли по всій програмі потрібно часто створювати стандартні збірки (наприклад, типовий офісний ПК або топовий геймерський ПК). Він просто зберігає готовий «рецепт» викликів будівельника в одному місці.

3. Що відбувається в Main() крок за кроком
Крок 1 — Кастомне збирання:
Клієнт бере будівельник і через ланцюжок задає Ryzen 7, 16GB, 1TB SSD, RX 7800. Відеокарту задано явно, а водяне охолодження не викликалося (воно залишилося за замовчуванням false). Метод Build() валідує і повертає перший ПК.
Крок 2 — Збирання через Директора:
Клієнт передає той самий будівельник у метод director.BuildGamingPC(builder). Директор викликає пресет (i9, 32GB, RTX 4090, водяне охолодження).
Крок 3 — Отримання результату:
Виклик builder.Build() повертає готовий геймерський комп'ютер із водяним охолодженням.
4. Чому це значно краще за звичайний конструктор?

Без Будівельника тобі довелося б писати монструозний конструктор:

var pc = new Computer("Intel i5", "16GB", null, null, false); // Що означають ці null і false?

Коли в конструкторі йдуть поруч 4 параметри типу string або bool, розробники постійно плутають їх місцями (наприклад, випадково передають назву накопичувача замість відеокарти). Будівельник унеможливлює таку помилку, бо кожен параметр має чітке ім'я методу.

4. Плюси та мінуси

  • Переваги: покрокове читабельне створення (Fluent Interface); централізована валідація цілісності перед віддачею об'єкта; ізоляція складного конструювання.
  • Недоліки: збільшення коду через необхідність писати окремий клас-будівельник.

Патерн 5: Prototype (Прототип)

Породжувальний (Creational)
↑ До змісту

1. Призначення

Дозволяє копіювати існуючі об'єкти, не вдаючись у деталі їхніх конкретних класів і без повторного виконання важкої логіки конструкторів.

2. Коли застосовувати

  • Створення об'єкта через new є занадто ресурсомістким (важкі обчислення, довгі запити в БД чи файлову систему).
  • Необхідно тиражувати складні налаштовані об'єкти-шаблони.
Порада для C#: Інтерфейс ICloneable вважається застарілим, оскільки повертає нетипізований object. Краще оголошувати типізований інтерфейс IPrototype<T> або використовувати record with { ... } у сучасному C#.

3. Реалізація на C#

using System;

public interface IPrototype<T>
{
    T Clone();
}

public class Author
{
    public string Name { get; set; }

    public Author(string name) => Name = name;
}

public class Document : IPrototype<Document>
{
    public string Title { get; set; }
    public string Content { get; set; }
    public Author Author { get; set; }

    public Document(string title, string content, Author author)
    {
        Title = title;
        Content = content;
        Author = author;
    }

    public Document Clone()
    {
        Document clone = (Document)this.MemberwiseClone();
        // Deep copy of reference type
        clone.Author = new Author(this.Author.Name);
        return clone;
    }

    public void DisplayInfo()
    {
        Console.WriteLine($"Document: '{Title}', Author: {Author.Name}, Content: '{Content}'");
    }
}

class Program
{
    static void Main()
    {
        var originalDoc = new Document("Template", "Standard content...", new Author("Alex"));
        Document clonedDoc = originalDoc.Clone();

        clonedDoc.Title = "Q3 Report";
        clonedDoc.Author.Name = "Iryna";

        Console.WriteLine("Clone:");
        clonedDoc.DisplayInfo();

        Console.WriteLine("Original:");
        originalDoc.DisplayInfo();
    }
}

/* Результат виконання: **************************************/

Clone:
Document: 'Q3 Report', Author: Iryna, Content: 'Standard content...'
Original:
Document: 'Template', Author: Alex, Content: 'Standard content...'

/*************************************************************/

4. Плюси та мінуси

  • Переваги: швидке дублювання готових складних об'єктів у рантаймі; уникнення повторної ініціалізації.
  • Недоліки: глибоке копіювання складних об'єктів із циклічними посиланнями вимагає підвищеної уваги.
