5 Принципів SOLID на C#

Фундаментальні принципи об'єктно-орієнтованого проєктування з розбором антипатернів та рішень

Швидка навігація

  • S — Single Responsibility (Єдиний обов'язок)
  • O — Open/Closed (Відкритість / Закритість)
  • L — Liskov Substitution (Підстановка Лісков)
  • I — Interface Segregation (Розділення інтерфейсу)
  • D — Dependency Inversion (Інверсія залежностей)

S: Single Responsibility Principle (SRP)

Принцип єдиного обов'язку
↑ До змісту

1. Суть принципу

«Клас повинен мати одну і лише одну причину для зміни» (Роберт С. Мартін).
Кожен клас має відповідати лише за одну конкретну частину функціональності програми.

2. Порушення принципу (Антипатерн)

Проблема: Клас Invoice одночасно рахує підсумкову вартість (бізнес-логіка), зберігає дані в базу даних (персистентність) та формує PDF-звіт (відображення). Будь-яка зміна структури бази або дизайну звіту змушує редагувати цей клас. 
// ПОГАНО: Клас має 3 різні причини для змін!
public class Invoice
{
    public decimal Amount { get; set; }

    public decimal CalculateTotal() => Amount * 1.2m; // 1. Бізнес-розрахунок

    public void SaveToDatabase()                     // 2. Робота з БД
    {
        Console.WriteLine("Збереження рахунку в SQL базі...");
    }

    public void PrintPdfReport()                     // 3. Форматування / Друк
    {
        Console.WriteLine("Формування PDF звіту...");
    }
}

3. Правильне рішення на C#

Рішення: Розбиваємо обов'язки на окремі незалежні класи: сутність рахунку, репозиторій для бази даних та генератор звітів. 
// ДОБРЕ: Кожен клас має лише одну зону відповідальності

// 1. Відповідає виключно за дані та бізнес-правила рахунку
public class Invoice
{
    public int Id { get; set; }
    public decimal Amount { get; set; }

    public decimal CalculateTotal() => Amount * 1.2m;
}

// 2. Відповідає виключно за збереження даних
public class InvoiceRepository
{
    public void Save(Invoice invoice)
    {
        Console.WriteLine($"Рахунок #{invoice.Id} збережено в БД.");
    }
}

// 3. Відповідає виключно за відображення / звітність
public class InvoiceReportPrinter
{
    public void PrintPdf(Invoice invoice)
    {
        Console.WriteLine($"PDF звіт для рахунку #{invoice.Id} на суму: {invoice.CalculateTotal():C}");
    }
}

4. Ознаки порушення (Code Smells)

  • Клас називають Manager, Processor, Handler і він містить 1000+ рядків коду («Божественний об'єкт»).
  • Клас імпортує одночасно простори імен для роботи з БД, GUI, відправки пошти та бізнес-моделей.
  • Зміна формату дати в інтерфейсі призводить до падіння unit-тестів роботи з базою даних.

O: Open/Closed Principle (OCP)

Принцип відкритості / закритості
↑ До змісту

1. Суть принципу

«Програмні сутності повинні бути відкриті для розширення, але закриті для модифікації».
Поведінку системи слід розширювати додаванням нового коду (нових класів), а не переписуванням уже перевіреного та протестованого коду.

2. Порушення принципу (Антипатерн)

Проблема: Додавання нового типу клієнта змушує змінювати існуючий метод CalculateDiscount, додаючи нові гілки switch/case або if-else. Це створює ризик поламати існуючу логіку і вимагає повторного тестування всього класу. 
// ПОГАНО: Щоб додати клієнта "VIP", доведеться модифікувати вже протестований код
public class DiscountCalculator
{
    public decimal CalculateDiscount(string customerType, decimal amount)
    {
        if (customerType == "Regular")
            return amount * 0.05m;
        else if (customerType == "Premium")
            return amount * 0.10m;
        // Додавання "VIP" вимагає втручання в цей метод!
        return 0;
    }
}

3. Правильне рішення на C#

Рішення: Використовуємо поліморфізм та інтерфейс стратегії. Щоб додати новий тип клієнта, ми просто створюємо новий клас — старий код не чіпається взагалі. 
// ДОБРЕ: Поліморфна система знижок, закрита для модифікації, відкрита для розширення

public interface IDiscountStrategy
{
    decimal Calculate(decimal amount);
}

public class RegularCustomerDiscount : IDiscountStrategy
{
    public decimal Calculate(decimal amount) => amount * 0.05m;
}

public class PremiumCustomerDiscount : IDiscountStrategy
{
    public decimal Calculate(decimal amount) => amount * 0.10m;
}

// Новий тип додається просто створенням нового класу:
public class VipCustomerDiscount : IDiscountStrategy
{
    public decimal Calculate(decimal amount) => amount * 0.20m;
}

// Калькулятор залишається незмінним назавжди:
public class DiscountCalculator
{
    public decimal CalculateDiscount(IDiscountStrategy strategy, decimal amount)
    {
        return strategy.Calculate(amount);
    }
}

4. Ознаки порушення (Code Smells)

  • Каскади умовних операторів if (type == ...) або довгі switch-case за типом сутності.
  • Кожна нова вимога бізнесу змушує відкривати ті самі центральні сервісні файли та дописувати логіку.

L: Liskov Substitution Principle (LSP)

Принцип підстановки Лісков
↑ До змісту

1. Суть принципу

«Підкласи повинні бути взаємозамінними зі своїми базовими класами без порушення коректності програми» (Барбара Лісков).
Клієнтський код не повинен ламатися чи поводитися несподівано, якщо йому замість базового класу передати будь-якого з його нащадків.

2. Порушення принципу (Антипатерн)

Проблема: Класичний приклад зі страусом або пінгвіном. Якщо базовий клас Bird має метод Fly(), а нащадок Ostrich викидає виняток NotSupportedException або нічого не робить, контракт базового класу ламається. 
// ПОГАНО: Нащадок порушує контракт батьківського класу
public class Bird
{
    public virtual void Fly() => Console.WriteLine("Птах летить у небі.");
}

public class Ostrich : Bird
{
    public override void Fly()
    {
        // Страуси не літають! Викидання винятку ламає клієнтський цикл
        throw new NotSupportedException("Страус не вміє літати!");
    }
}

// Клієнтський код впаде з помилкою під час виконання:
// foreach (var bird in birds) bird.Fly();

3. Правильне рішення на C#

Рішення: Не наділяти базовий клас поведінкою, якої немає у всіх його нащадків. Літальні можливості виносяться в окремий інтерфейс IFlyable. 
// ДОБРЕ: Правильна ієрархія та інтерфейси здатності

// Базовий клас містить лише те, що роблять абсолютно всі птахи
public abstract class Bird
{
    public abstract void Eat();
}

public interface IFlyable
{
    void Fly();
}

// Горобець і їсть, і літає
public class Sparrow : Bird, IFlyable
{
    public override void Eat() => Console.WriteLine("Горобець дзьобає зерно.");
    public void Fly() => Console.WriteLine("Горобець летить.");
}

// Страус тільки їсть
public class Ostrich : Bird
{
    public override void Eat() => Console.WriteLine("Страус їсть траву.");
}

// Клієнт викликає Fly() лише для тих, хто гарантовано реалізує IFlyable:
// foreach (IFlyable flyingBird in flyingFlock) flyingBird.Fly();

4. Ознаки порушення (Code Smells)

  • Перевизначені методи підкласів кидають NotImplementedException або NotSupportedException.
  • Клієнтський код містить перевірки типу перед викликом методу: if (bird is not Ostrich) bird.Fly();.
  • Підклас послаблює вихідні умови (повертає несподіваний null) або посилює вхідні умови.

I: Interface Segregation Principle (ISP)

Принцип розділення інтерфейсу
↑ До змісту

1. Суть принципу

«Клієнти не повинні залежати від методів, якими вони не користуються».
Краще створити багато вузькоспеціалізованих інтерфейсів, ніж один універсальний «товстий» (Fat Interface).

2. Порушення принципу (Антипатерн)

Проблема: Інтерфейс IMachine об'єднує функції друку, сканування та факсу. Простий домашній принтер змушений реалізовувати порожні методи або кидати помилки для методів сканування та факсу. 
// ПОГАНО: "Товстий" інтерфейс змушує реалізовувати непотрібне
public interface IMachine
{
    void Print(string text);
    void Scan();
    void Fax();
}

public class BasicPrinter : IMachine
{
    public void Print(string text) => Console.WriteLine($"Друк: {text}");

    public void Scan() => throw new NotImplementedException("Не підтримується!");
    public void Fax()  => throw new NotImplementedException("Не підтримується!");
}

3. Правильне рішення на C#

Рішення: Дробимо інтерфейс на незалежні контракти (ролі). Простий принтер бере лише друк, а потужний офісний МФУ реалізує всі необхідні інтерфейси одночасно. 
// ДОБРЕ: Маленькі спеціалізовані інтерфейси

public interface IPrinter
{
    void Print(string text);
}

public interface IScanner
{
    void Scan();
}

public interface IFax
{
    void Fax();
}

// 1. Простий принтер залежить лише від того, що реально вміє робити
public class BasicPrinter : IPrinter
{
    public void Print(string text) => Console.WriteLine($"Друк: {text}");
}

// 2. Багатофункціональний пристрій (МФУ) комбінує потрібні інтерфейси
public class MultiFunctionCenter : IPrinter, IScanner, IFax
{
    public void Print(string text) => Console.WriteLine($"МФУ Друк: {text}");
    public void Scan()             => Console.WriteLine("МФУ Сканування...");
    public void Fax()              => Console.WriteLine("МФУ Відправка факсу...");
}

4. Ознаки порушення (Code Smells)

  • Інтерфейси містять десятки різноманітних методів на всі випадки життя.
  • Класи реалізують методи інтерфейсу порожніми блоками { /* нічого */ } або кидають NotImplementedException.

D: Dependency Inversion Principle (DIP)

Принцип інверсії залежностей
↑ До змісту

1. Суть принципу

1. Модулі високих рівнів не повинні залежати від модулів низьких рівнів. Обидва типи мають залежати від абстракцій.
2. Абстракції не повинні залежати від деталей. Деталі мають залежати від абстракцій.
Це фундамент архітектури Dependency Injection (DI) та написання тестованого коду.

2. Порушення принципу (Антипатерн)

Проблема: Високорівневий клас бізнес-логіки OrderService напряму створює через new екземпляри низькорівневих класів SqlDatabase та SmtpEmailSender. Тепер підмінити базу даних або протестувати сервіс через mock-об'єкти без реальної бази неможливо. 
// ПОГАНО: Пряма жорстка залежність від конкретних реалізацій
public class SqlDatabase
{
    public void Save(string data) => Console.WriteLine("Запис у SQL...");
}

public class SmtpEmailSender
{
    public void Send(string to, string body) => Console.WriteLine("Відправка по SMTP...");
}

public class OrderService
{
    // Жорстко зашиті конкретні залежності через 'new'
    private readonly SqlDatabase _db = new SqlDatabase();
    private readonly SmtpEmailSender _mail = new SmtpEmailSender();

    public void ProcessOrder(string orderData)
    {
        _db.Save(orderData);
        _mail.Send("client@test.com", "Замовлення оформлено");
    }
}

3. Правильне рішення на C#

Рішення: Вводимо інтерфейси-абстракції IOrderRepository та INotificationService. Сервіс приймає залежності через конструктор (Constructor Injection). 
// ДОБРЕ: Обидва рівні залежать від спільних абстракцій

// 1. Абстракції
public interface IOrderRepository
{
    void Save(string data);
}

public interface INotificationService
{
    void Send(string to, string message);
}

// 2. Конкретні реалізації (деталі)
public class SqlOrderRepository : IOrderRepository
{
    public void Save(string data) => Console.WriteLine($"[SQL] Збережено: {data}");
}

public class EmailNotificationService : INotificationService
{
    public void Send(string to, string message) => Console.WriteLine($"[Email] Надіслано до {to}: {message}");
}

// 3. Високорівневий модуль залежить ЛИШЕ від абстракцій
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly INotificationService _notificationService;

    // Впровадження залежностей через конструктор (Dependency Injection)
    public OrderService(IOrderRepository repository, INotificationService notificationService)
    {
        _repository = repository;
        _notificationService = notificationService;
    }

    public void ProcessOrder(string orderData, string customerEmail)
    {
        _repository.Save(orderData);
        _notificationService.Send(customerEmail, "Ваше замовлення успішно оброблено!");
    }
}

// Використання (або конфігурація у Program.cs через builder.Services):
class Program
{
    static void Main()
    {
        IOrderRepository repo = new SqlOrderRepository();
        INotificationService mailer = new EmailNotificationService();

        var service = new OrderService(repo, mailer);
        service.ProcessOrder("Замовлення #1042", "alex@example.com");
    }
}

4. Ознаки порушення (Code Smells)

  • Використання оператора new для створення екземплярів сервісів доступу до даних, пошти чи сторонніх API прямо всередині бізнес-класів.
  • Неможливість написати швидкий модульний тест (unit-test) без підключення реальної бази даних або мережі.
  • Використання глобального стану через класичні одинаки (Singleton).
