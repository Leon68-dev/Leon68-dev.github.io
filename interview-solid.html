Головне меню Принципи SOLID

5 Принципів SOLID на C#

Фундаментальні принципи чистої архітектури: антипатерни, живі розбори та рішення на C#

Швидка навігація по принципах

  • S — Single Responsibility (Єдиний обов'язок)
  • O — Open/Closed (Відкритість / Закритість)
  • L — Liskov Substitution (Підстановка Лісков)
  • I — Interface Segregation (Розділення інтерфейсу)
  • D — Dependency Inversion (Інверсія залежностей)

S: Single Responsibility Principle (SRP)

Єдиний обов'язок
↑ До змісту

1. Суть принципу

«Клас повинен мати одну і лише одну причину для зміни» (Роберт С. Мартін).
Кожен клас має відповідати лише за одну конкретну частину функціональності програми.

2. Порушення принципу (Антипатерн)

Проблема: Клас Invoice одночасно рахує підсумкову вартість (бізнес-логіка), зберігає дані в базу даних (персистентність) та формує PDF-звіт (відображення). Будь-яка зміна структури бази або дизайну звіту змушує редагувати один і той самий файл. 
// BAD: Class has 3 different reasons to change!
public class BadInvoice
{
    public decimal Amount { get; set; }

    public decimal CalculateTotal() => Amount * 1.2m; // 1. Business logic calculation

    public void SaveToDatabase()
    {
        Console.WriteLine("Saving invoice to SQL database..."); // 2. Persistence / DB
    }

    public void PrintPdfReport()
    {
        Console.WriteLine("Generating PDF report..."); // 3. Presentation formatting
    }
}

3. Правильне рішення на C#

Рішення: Розбиваємо обов'язки на три окремі класи: сутність рахунку, репозиторій для бази даних та генератор звітів. 
using System;

// 1. Responsible purely for invoice data and business rules
public class Invoice
{
    public int Id { get; set; }
    public decimal Amount { get; set; }

    public Invoice(int id, decimal amount)
    {
        Id = id;
        Amount = amount;
    }

    public decimal CalculateTotal() => Amount * 1.2m;
}

// 2. Responsible purely for database persistence
public class InvoiceRepository
{
    public void Save(Invoice invoice)
    {
        Console.WriteLine($"Invoice #{invoice.Id} saved to SQL database.");
    }
}

// 3. Responsible purely for presentation and formatting
public class InvoiceReportPrinter
{
    public void PrintPdf(Invoice invoice)
    {
        Console.WriteLine($"PDF report generated for invoice #{invoice.Id} with total: {invoice.CalculateTotal():C}");
    }
}

class Program
{
    static void Main()
    {
        var invoice = new Invoice(101, 1000m);
        var repository = new InvoiceRepository();
        var printer = new InvoiceReportPrinter();

        Console.WriteLine($"Invoice #{invoice.Id} total: {invoice.CalculateTotal():C}");
        repository.Save(invoice);
        printer.PrintPdf(invoice);
    }
}

/* Результат виконання: **************************************/

Invoice #101 total: 1 200,00 ₴
Invoice #101 saved to SQL database.
PDF report generated for invoice #101 with total: 1 200,00 ₴

(Формат валюти залежить від системної локалі, наприклад: 1 200,00 ₴ або $1,200.00)

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви співробітника компанії, який одночасно є головним бухгалтером, системним адміністратором і прибиральником. Якщо він ламає швабру, компанія не може здати податковий звіт, бо бухгалтер зайнятий ремонтом швабри. Це абсурд. У професійній команді бухгалтер рахує фінанси, сисадмін налаштовує сервери, а клінінг прибирає приміщення. SRP вимагає від класів такого самого чіткого розподілу обов'язків.

1. Як влаштований код
Invoice (Тільки бізнес-правила: ставка ПДВ, підсумок) │ ├── InvoiceRepository ──► Відповідає виключно за SQL/БД └── InvoiceReportPrinter ──► Відповідає виключно за генерацію PDF

Головна ідея: якщо бухгалтер змінює формулу податку — ми міняємо лише Invoice. Якщо сисадмін переносить базу з SQL Server у PostgreSQL — ми міняємо лише InvoiceRepository. Якщо дизайнер оновив шрифт PDF-шаблону — ми міняємо лише InvoiceReportPrinter.

2. Розбираємо код по частинах

Клас Invoice: Зберігає ID та вартість, а метод CalculateTotal() рахує підсумок із ПДВ. Він не знає, як створювати PDF, і не знає, чи взагалі існує якась база даних.

Клас InvoiceRepository: Має один метод Save(Invoice invoice). Його єдина турбота — зберегти дані в таблицю.

Клас InvoiceReportPrinter: Має один метод PrintPdf(Invoice invoice). Його єдина турбота — розмітка та візуалізація.

3. Чому це краще за змішування в одному класі?

У "поганому" класі зміна дизайну звіту змушувала перетестовувати методи роботи з базою даних, бо вони ділили один спільний стан усередині класу. Розбиття на три класи дає змогу трьом розробникам працювати над рахунком, базою та звітами одночасно без конфліктів у Git.

4. Ознаки порушення (Code Smells)

  • Клас називається узагальнено: Manager, Processor, Helper і містить понад 500–1000 рядків коду («Божественний об'єкт» / God Object).
  • Клас одночасно підключає простори імен для роботи з БД (Microsoft.EntityFrameworkCore), графікою (SkiaSharp) та відправкою листів (System.Net.Mail).
  • Зміна кольору кнопки в інтерфейсі несподівано ламає збереження даних у базу.

O: Open/Closed Principle (OCP)

Відкритість / Закритість
↑ До змісту

1. Суть принципу

«Програмні сутності повинні бути відкриті для розширення, але закриті для модифікації».
Нова функціональність повинна додаватися створенням нових класів, а не переписуванням уже перевіреного та протестованого коду.

2. Порушення принципу (Антипатерн)

Проблема: Додавання нового типу клієнта змушує змінювати існуючий метод CalculateDiscount, додаючи нові гілки switch/case або if-else. Кожне редагування старого класу створює ризик внести регресійний баг. 
// BAD: Adding a "VIP" customer requires modifying existing, tested code
public class BadDiscountCalculator
{
    public decimal CalculateDiscount(string customerType, decimal amount)
    {
        if (customerType == "Regular")
            return amount * 0.05m;
        else if (customerType == "Premium")
            return amount * 0.10m;
        // Adding "VIP" forces us to open and edit this method!
        return 0;
    }
}

3. Правильне рішення на C#

Рішення: Застосовуємо поліморфізм та інтерфейс стратегії (патерн Strategy). Новий тип знижки — це просто новий клас, а калькулятор залишається незмінним назавжди. 
using System;

// 1. Strategy contract
public interface IDiscountStrategy
{
    decimal Calculate(decimal amount);
}

// 2. Concrete strategies
public class RegularCustomerDiscount : IDiscountStrategy
{
    public decimal Calculate(decimal amount) => amount * 0.05m;
}

public class PremiumCustomerDiscount : IDiscountStrategy
{
    public decimal Calculate(decimal amount) => amount * 0.10m;
}

// New discount type added WITHOUT modifying existing classes:
public class VipCustomerDiscount : IDiscountStrategy
{
    public decimal Calculate(decimal amount) => amount * 0.20m;
}

// 3. Calculator is closed for modification, but open for extension:
public class DiscountCalculator
{
    public decimal CalculateDiscount(IDiscountStrategy strategy, decimal amount)
    {
        return strategy.Calculate(amount);
    }
}

class Program
{
    static void Main()
    {
        var calculator = new DiscountCalculator();
        decimal amount = 1000m;

        decimal regularDiscount = calculator.CalculateDiscount(new RegularCustomerDiscount(), amount);
        Console.WriteLine($"Regular discount: {regularDiscount:C}");

        decimal vipDiscount = calculator.CalculateDiscount(new VipCustomerDiscount(), amount);
        Console.WriteLine($"VIP discount: {vipDiscount:C}");
    }
}

/* Результат виконання: **************************************/

Regular discount: 50,00 ₴
VIP discount: 200,00 ₴

(Формат валюти залежить від системної локалі, наприклад: 50,00 ₴ або $50.00)

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви смартфон із портом USB-C або магазин додатків App Store. Коли ти хочеш додати в телефон тепловізор, додаткову пам'ять або нову гру, ти не розбираєш корпус викруткою і не перепаюєш мікросхеми на материнській платі. Телефон закритий для модифікації (плата запаяна на заводі), але відкритий для розширення через універсальний порт і магазин додатків. OCP перетворює твій код на такий самий модульний смартфон.

1. Як влаштований код
DiscountCalculator (Калькулятор: закритий від змін, не має жодного switch) │ викликає strategy.Calculate(amount) ▼ IDiscountStrategy (Інтерфейс: відкритий для будь-яких нових класів) ▲ ┌──┴─────────────────────────┐ │ │ RegularCustomerDiscount VipCustomerDiscount (додали без зміни калькулятора)
2. Чому це краще за перемикач switch?

Якщо у великому інтернет-магазині діє 15 видів акцій, метод зі switch розростається на сотні рядків. Будь-яка помилка в одній гілці може випадково зламати знижки для інших покупців. З OCP кожна знижка живе у своєму ізольованому класі: її можна протестувати окремим модульним тестом, видалити або замінити без найменшого страху зламати сусідні розрахунки.

4. Ознаки порушення (Code Smells)

  • Каскади операторів if (type == "VIP") ... else if (...) або розлогі конструкції switch-case за переліками типів.
  • Кожна поява нової бізнес-фічі змушує відкривати ті самі 2–3 центральні файли ядра й дописувати нові умови.

L: Liskov Substitution Principle (LSP)

Підстановка Лісков
↑ До змісту

1. Суть принципу

«Підкласи повинні бути вільно взаємозамінними зі своїми базовими класами без порушення очікуваної коректності програми» (Барбара Лісков).
Клієнтський код не повинен ламатися, викидати несподівані винятки чи вимагати додаткових перевірок типів, якщо замість базового класу йому підсунули нащадка.

2. Порушення принципу (Антипатерн)

Проблема: Класичний приклад зі страусом. Якщо базовий клас Bird декларує метод Fly(), а підклас Ostrich (страус) викидає NotSupportedException (бо страуси не літають), контракт базового класу ламається. Цикл обробки птахів неочікувано впаде в рантаймі. 
// BAD: Subclass breaks parent's contract!
public class BadBird
{
    public virtual void Fly() => Console.WriteLine("Bird is flying.");
}

public class BadOstrich : BadBird
{
    public override void Fly()
    {
        // Ostriches cannot fly! Throwing exception crashes client code unexpectedly!
        throw new NotSupportedException("Ostriches cannot fly!");
    }
}

3. Правильне рішення на C#

Рішення: Не наділяти базовий клас поведінкою, якої немає у 100% його нащадків. Здатність літати виноситься в окремий інтерфейс IFlyable. 
using System;
using System.Collections.Generic;

// 1. Base class contains only what ALL birds truly do
public abstract class Bird
{
    public abstract void Eat();
}

// 2. Separate capability contract for flying
public interface IFlyable
{
    void Fly();
}

// Sparrow eats and flies:
public class Sparrow : Bird, IFlyable
{
    public override void Eat() => Console.WriteLine("Sparrow is eating seeds.");

    public void Fly() => Console.WriteLine("Sparrow is flying in the sky.");
}

// Ostrich only eats:
public class Ostrich : Bird
{
    public override void Eat() => Console.WriteLine("Ostrich is eating grass.");
}

class Program
{
    static void Main()
    {
        var birds = new List<Bird> { new Sparrow(), new Ostrich() };

        // Safe polymorphism: ALL birds can Eat without crashes
        foreach (var bird in birds)
        {
            bird.Eat();
        }

        // Only flying birds are commanded to fly
        var flyingFlock = new List<IFlyable> { new Sparrow() };
        foreach (var flyer in flyingFlock)
        {
            flyer.Fly();
        }
    }
}

/* Результат виконання: **************************************/

Sparrow is eating seeds.
Ostrich is eating grass.
Sparrow is flying in the sky.

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви бездротову комп'ютерну мишку. Якщо стара мишка зламалася, ти йдеш у магазин і купуєш нову іншої моделі. Ти очікуєш, що підключивши її в USB-порт, курсор рухатиметься по екрану. Якби нова мишка замість руху курсора вибивала пробки у всій квартирі зі словами: «Я нова супермодель, я не підтримую рух по столу!» — це і було б грубим порушенням принципу Лісков. Підклас зобов'язаний повноцінно виконувати обіцянки базового класу.

1. Як влаштований код
Bird (Базовий клас: декларує лише Eat()) ▲ ├── Ostrich (Страус: реалізує Eat() і чесно каже, що не літає) └── Sparrow (Горобець: реалізує Eat()) ▲ └── IFlyable (Окремий контракт: здатність літати)
2. Чому це краще за наївне успадкування?

Клієнтський код ніколи не повинен писати сором'язливі перевірки на кшталт if (bird is not Ostrich) bird.Fly();. Це головний маркер порушення LSP. Якщо базовий клас оголосив метод, будь-який нащадок повинен виконувати його безпечно та без сюрпризів.

4. Ознаки порушення (Code Smells)

  • Перевизначені методи підкласів кидають NotImplementedException або NotSupportedException.
  • Клієнтський код рясніє перевірками типів перед викликом: if (obj is SubClass) ....
  • Підклас повертає null там, де базовий клас гарантовано повертав дійсний об'єкт.

I: Interface Segregation Principle (ISP)

Розділення інтерфейсу
↑ До змісту

1. Суть принципу

«Клієнти не повинні залежати від методів, якими вони не користуються».
Краще створити багато невеликих вузькоспеціалізованих інтерфейсів, ніж один універсальний «товстий» монстр-інтерфейс (Fat Interface).

2. Порушення принципу (Антипатерн)

Проблема: Інтерфейс IMachine об'єднує друк, сканування та факс. Дешевий домашній принтер змушений реалізовувати непотрібні методи сканера й факсу пустишками або викидати винятки. 
// BAD: Fat interface forces implementors to carry dead weight
public interface IBadMachine
{
    void Print(string text);
    void Scan();
    void Fax();
}

public class BadBasicPrinter : IBadMachine
{
    public void Print(string text) => Console.WriteLine($"Printing: {text}");

    public void Scan() => throw new NotImplementedException("Scanner not available!");
    public void Fax() => throw new NotImplementedException("Fax not available!");
}

3. Правильне рішення на C#

Рішення: Дробимо один масивний інтерфейс на три незалежні ролі: IPrinter, IScanner, IFax. 
using System;

// 1. Segregated, narrow role interfaces
public interface IPrinter
{
    void Print(string text);
}

public interface IScanner
{
    void Scan();
}

public interface IFax
{
    void Fax();
}

// 2. Simple printer implements ONLY what it can do
public class BasicPrinter : IPrinter
{
    public void Print(string text) => Console.WriteLine($"BasicPrinter: Printing {text}");
}

// 3. Multi-function center (MFP) combines all three interfaces
public class MultiFunctionCenter : IPrinter, IScanner, IFax
{
    public void Print(string text) => Console.WriteLine($"MFP: Printing {text}");

    public void Scan() => Console.WriteLine("MFP: Scanning document to cloud.");

    public void Fax() => Console.WriteLine("MFP: Sending fax over phone line.");
}

class Program
{
    static void Main()
    {
        IPrinter simplePrinter = new BasicPrinter();
        simplePrinter.Print("document.pdf");

        MultiFunctionCenter mfp = new MultiFunctionCenter();
        mfp.Print("contract.pdf");
        mfp.Scan();
    }
}

/* Результат виконання: **************************************/

BasicPrinter: Printing document.pdf
MFP: Printing contract.pdf
MFP: Scanning document to cloud.

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви ресторанне меню. Якщо ти зайшов у кав'ярню випити одну чашку еспресо, офіціант не повинен змушувати тебе підписувати контракт на комплексний банкет із 7 страв (салат, перше, стейк, десерт, пляшка вина). Ти замовляєш лише те, що споживаєш. Інтерфейси в коді повинні давати таку саму свободу: клас підписується лише на ті методи, якими реально володіє.

1. Як влаштований код
IPrinter IScanner IFax ▲ ▲ ▲ │ └──────┬──────┘ BasicPrinter MultiFunctionCenter (бере тільки друк) (комбінує всі три інтерфейси)
2. Чому це краще за універсальний інтерфейс?

Якщо завтра в інтерфейс IScanner знадобиться додати метод ScanToPdf(), клас простого принтера BasicPrinter навіть не відчує цих змін і не потребуватиме перекомпіляції, адже він залежить лише від IPrinter.

4. Ознаки порушення (Code Smells)

  • Інтерфейси з десятками методів на всі випадки життя («товсті» контракти).
  • Класи реалізують методи інтерфейсу порожніми дужками { /* empty */ } або кидають NotImplementedException.

D: Dependency Inversion Principle (DIP)

Інверсія залежностей
↑ До змісту

1. Суть принципу

1. Модулі високих рівнів не повинні залежати від модулів низьких рівнів. Обидва типи мають залежати від абстракцій.
2. Абстракції не повинні залежати від деталей. Деталі мають залежати від абстракцій.
Це фундамент архітектури Dependency Injection (DI) та написання тестованого коду.

2. Порушення принципу (Антипатерн)

Проблема: Високорівневий клас бізнес-логіки OrderService напряму створює через оператор new низькорівневі інфраструктурні класи SqlDatabase та SmtpEmailSender. Тепер підмінити базу даних або протестувати сервіс через mock-об'єкти без реальної бази неможливо. 
// BAD: Direct hardcoded dependency via 'new'
public class BadSqlDatabase
{
    public void Save(string data) => Console.WriteLine("Writing to SQL...");
}

public class BadOrderService
{
    // Hardcoded low-level dependency: impossible to unit test or swap!
    private readonly BadSqlDatabase _db = new BadSqlDatabase();

    public void ProcessOrder(string orderData)
    {
        _db.Save(orderData);
    }
}

3. Правильне рішення на C#

Рішення: Вводимо інтерфейси-абстракції IOrderRepository та INotificationService. Сервіс приймає залежності через конструктор (Constructor Injection). 
using System;

// 1. Abstractions (contracts)
public interface IOrderRepository
{
    void Save(string data);
}

public interface INotificationService
{
    void Send(string to, string message);
}

// 2. Low-level details implementing abstractions
public class SqlOrderRepository : IOrderRepository
{
    public void Save(string data) => Console.WriteLine($"[SQL] Order saved: {data}");
}

public class EmailNotificationService : INotificationService
{
    public void Send(string to, string message) => Console.WriteLine($"[Email] Sent to {to}: {message}");
}

// 3. High-level business service depends ONLY on abstractions
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly INotificationService _notifier;

    // Dependency Injection via constructor
    public OrderService(IOrderRepository repository, INotificationService notifier)
    {
        _repository = repository;
        _notifier = notifier;
    }

    public void ProcessOrder(string orderData, string customerEmail)
    {
        _repository.Save(orderData);
        _notifier.Send(customerEmail, "Your order was successfully processed!");
    }
}

class Program
{
    static void Main()
    {
        // Composition root: wire up dependencies (or use builder.Services in ASP.NET Core)
        IOrderRepository repo = new SqlOrderRepository();
        INotificationService mailer = new EmailNotificationService();

        var service = new OrderService(repo, mailer);
        service.ProcessOrder("Order #1042", "alex@example.com");
    }
}

🔍 Детальний розбір: як влаштований і працює цей код

Уяви настільну лампу та електричну розетку на стіні. Твоя лампа не припаює свої мідні дроти напряму до турбіни Дніпровської ГЕС. І лампа, і гідроелектростанція погоджуються на спільну абстракцію — стандартну настінну розетку 220V. Завдяки розетці ти можеш вимкнути лампу й підключити зарядку для телефону або тостер. DIP робить класи в програмі такими самими взаємозамінними приладами.

1. Як влаштований код
OrderService (Високий рівень: чиста бізнес-логіка) │ залежить ЛИШЕ від інтерфейсів ▼ IOrderRepository & INotificationService (Абстракції-розетки) ▲ │ реалізують деталі SqlOrderRepository & EmailNotificationService (Низький рівень: конкретні драйвери)
2. Чому це краще за створення через new?

Коли сервіс викликає new SqlDatabase() всередині себе, його неможливо протестувати ізольовано. Щоб запустити найпростіший тест, доведеться піднімати реальний сервер SQL Server у Docker.
З інверсією залежностей у unit-тесті замість реальної бази передається легкий фейк: new Mock<IOrderRepository>(), і 500 тестів проходять за 0.2 секунди в оперативній пам'яті.

4. Ознаки порушення (Code Smells)

  • Використання оператора new для створення екземплярів репозиторіїв, HTTP-клієнтів або сервісів логування всередині бізнес-класів.
  • Неможливість написати модульний тест без підключення до живої бази даних чи інтернету.
  • Використання глобального статичного стану замість впровадження залежностей (Dependency Injection).
