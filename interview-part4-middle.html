1. Як влаштований конвеєр Middleware в ASP.NET Core? Різниця між Middleware та Action Filters?

↑ До змісту
Коротка суть: Middleware обробляє кожен HTTP-запит глобально за патерном Chain of Responsibility і має доступ лише до `HttpContext`. Action Filters є частиною MVC-конвеєра і мають доступ до моделі, контролера та аргументів конкретного Action.

Розгорнута відповідь:

  • Middleware: Двосторонній конвеєр. Запит іде вперед через next(), а відповідь повертається назад у зворотному порядку: 
    app.Use(async (context, next) =>
{
    // Логіка ДО наступного middleware
    await next(); // Передача запиту далі
    // Логіка ПІСЛЯ завершення запиту
});
    Short-circuiting (коротке замикання): Middleware може не викликати next(), а повернути відповідь одразу (наприклад, перевірка статичних файлів або відхилення через відсутність токена).
  • Action Filters: Спрацьовують значно пізніше — лише після того, як Middleware маршрутизації (Routing) знайшов відповідний Controller і Action. Фільтри можуть маніпулювати параметрами методу (ActionExecutingContext.ActionArguments) та результатом IActionResult.
Підступні питання на співбесіді:
П: У чому різниця між `app.Use()` та `app.Run()`?

В: Метод `Use()` приймає делегат `next` і може передавати керування далі по конвеєру. Метод `Run()` є термінальним (Terminal Middleware) — він не приймає делегат `next`, завершує пайплайн і повертає HTTP-відповідь назад клієнту.

П: Чому глобальний Exception Handling Middleware має реєструватися першим у списку `app.Use...`?

В: Оскільки конвеєр працює за принципом матрьошки (вхід і вихід), перше зареєстроване middleware огортає виклик усіх інших у свій блок `try/catch`. Якщо зареєструвати його пізніше, винятки, викинуті в попередніх middleware (наприклад, під час аутентифікації), не будуть перехоплені.

2. Що таке Captive Dependency у DI-контейнері? Як виникає і як від неї захиститися?

↑ До змісту
Коротка суть: Коли довгоживучий сервіс (Singleton) захоплює короткоживучий сервіс (Scoped або Transient) через конструктор. Захоплений сервіс не вмирає вчасно, що викликає витоки пам'яті та баги конкурентного доступу (наприклад, у `DbContext`).

Розгорнута відповідь:

Класичний приклад катастрофи: SingletonService приймає через конструктор AppDbContext (який є Scoped):

public class CacheManager // Зареєстрований як Singleton!
{
    private readonly AppDbContext _db; // Scoped залежність потрапила в полон!

    public CacheManager(AppDbContext db) => _db = db;
}

Чому це ламає систему:

  1. AppDbContext не є потокобезпечним (thread-safe). Якщо 10 паралельних запитів звернуться до Singleton'а, виникне аварія InvalidOperationException: A second operation was started on this context before a previous operation completed.
  2. Change Tracker контексту ніколи не очиститься, що роздує споживання RAM до гігабайтів.

Захист: Вмикати валідацію скоупів при створенні хоста (у Development режимі ASP.NET Core це ввімкнено за замовчуванням): builder.Host.UseDefaultServiceProvider(o => o.ValidateScopes = true);. Якщо Singleton'у дійсно потрібен Scoped сервіс, створюйте явний скоуп через IServiceScopeFactory.

Підступні питання на співбесіді:
П: Як правильно використовувати `DbContext` або інший Scoped сервіс усередині фонового `BackgroundService`?

В: Не можна інжектувати Scoped сервіс напряму в конструктор `BackgroundService` (бо він живе як Singleton). Потрібно інжектувати `IServiceScopeFactory`, створювати скоуп вручну у виклику `ExecuteAsync` за допомогою `using var scope = _scopeFactory.CreateScope();` і діставати `scope.ServiceProvider.GetRequiredService<AppDbContext>()`, очищуючи ресурси на кожній ітерації фонового циклу.

3. Options Pattern: у чому різниця між `IOptions`, `IOptionsSnapshot` та `IOptionsMonitor`?

↑ До змісту
Коротка суть: `IOptions` читає конфігурацію 1 раз при старті (Singleton). `IOptionsSnapshot` перечитує зміни `appsettings.json` на кожен HTTP-запит (Scoped). `IOptionsMonitor` підтримує сповіщення про зміни в реальному часі без перестворення сервісів (Singleton).

Порівняльна таблиця:

  • IOptions<TOptions>: Реєструється як Singleton. Читає налаштування один раз під час першого звернення. Не реагує на зміну файлу appsettings.json без перезапуску сервісу. Найшвидший за продуктивністю.
  • IOptionsSnapshot<TOptions>: Реєструється як Scoped. Перевіряє зміни конфігурації для кожного окремого HTTP-запиту. Гарантує стабільність налаштувань протягом обробки одного запиту. Не можна інжектувати в Singleton!
  • IOptionsMonitor<TOptions>: Реєструється як Singleton. Дозволяє читати актуальні дані будь-коли через .CurrentValue та підтримує подію OnChange(opt => ...) для підписки на гарячу зміну конфігурації без перезапуску додатку.
Підступні питання на співбесіді:
П: Чому спроба заінжектувати `IOptionsSnapshot` у Singleton призводить до помилки ще під час запуску додатку?

В: Оскільки `IOptionsSnapshot` зареєстровано як Scoped-сервіс, впровадження його в Singleton-сервіс є класичною Captive Dependency. Вбудована перевірка `ValidateScopes` в ASP.NET Core викидає `InvalidOperationException` при збірці контейнера.

4. JWT авторизація: структура токена, різниця між Access та Refresh токенами, що таке Claims?

↑ До змісту
Коротка суть: JWT складається з 3 частин (Header, Payload, Signature), закодованих у Base64Url. Access токен короткоживучий (15 хв) для доступу до API. Refresh токен довгоживучий (дні/тижні) у базі даних для безшовного поновлення Access токена.

Розгорнута відповідь:

  • Анатомія JWT:
    • Header: Алгоритм підпису (наприклад, HMAC-SHA256 або RSA).
    • Payload (Корисне навантаження): Набір тверджень (Claims) — це пари ключ/значення з даними користувача: sub (User Id), email, roles, термін придатності exp. Важливо: дані в Payload НЕ зашифровані, їх може прочитати будь-хто!
    • Signature (Підпис): Хеш від Header + Payload, підписаний секретним ключем сервера. Сервер не ходить у БД для валідації токена — він лише математично перевіряє підпис своїм секретом.
  • Access vs Refresh: Якщо вкрадуть Access-токен, він протухне за 15 хвилин. Refresh-токен зберігається у захищених `HttpOnly, Secure` куках або в базі даних клієнта, і при його компрометації адміністратор може миттєво відкликати запис із бази даних.
Підступні питання на співбесіді:
П: Як відкликати скомпрометований JWT Access-токен до настання його `exp`, якщо він повністю stateless?

В: Оскільки сервер перевіряє токен криптографічно без бази даних, відкликати його нативно неможливо. Рішення: 1) Робити час життя токена мінімальним (5-15 хв); 2) Вести Blacklist відкликаних ідентифікаторів токенів (`jti`) у швидкій in-memory пам'яті (Redis) і перевіряти його через кастомний `OnTokenValidated` івент у JwtBearer Middleware.

5. Як працює Change Tracker в Entity Framework Core? Чому `.AsNoTracking()` дає приріст швидкості?

↑ До змісту
Коротка суть: Change Tracker зберігає зліпок (снапшот) кожного прочитаного об'єкта. При виклику `SaveChanges()` він порівнює поточні значення зі зліпком, щоб згенерувати SQL `UPDATE`. `.AsNoTracking()` відключає збереження зліпків, заощаджуючи до 50% пам'яті.

Розгорнута відповідь:

Коли ви завантажуєте сутності через звичайний запит:

var user = await db.Users.FirstAsync(u => u.Id == 1);
user.Name = "Нове Ім'я";
await db.SaveChangesAsync(); // Автоматично генерує: UPDATE Users SET Name = ... WHERE Id = 1

Що робить Change Tracker під капотом:

  1. Виділяє додаткову пам'ять у купі під копію вихідних даних кожної сутності.
  2. Прив'язує статус (EntityState.Unchanged).
  3. Під час виклику SaveChangesAsync() запускає важкий процес DetectChanges(), скануючи кожне поле кожного об'єкта в пам'яті на відмінність від вихідного зліпка.

Чому важливий .AsNoTracking(): Для будь-яких запитів читання (Read-Only) трекінг не потрібен. Відключення трекінгу позбавляє EF Core необхідності виділяти пам'ять під копії об'єктів та прискорює виконання запиту у 2–3 рази.

Підступні питання на співбесіді:
П: Що таке `.AsNoTrackingWithIdentityResolution()` і коли звичайного `.AsNoTracking()` недостатньо?

В: Звичайний `.AsNoTracking()` створює новий екземпляр C#-класу для кожного рядка результату запиту, навіть якщо в навігаційних властивостях зустрічається один і той самий об'єкт. `.AsNoTrackingWithIdentityResolution()` відстежує унікальність сутностей за їхнім Id (Identity Map) у межах запиту, гарантуючи, що повторювані об'єкти посилатимуться на один екземпляр у пам'яті, не вмикаючи при цьому повний Change Tracking.

6. Проблема $N+1$ запиту в EF Core: як виникає і як вирішити? Що таке Split Queries (`.AsSplitQuery()`)?

↑ До змісту
Коротка суть: Виникає, коли 1 запит витягує батьківські сутності, а зв'язані дочірні дістаються в циклі окремими $N$ запитами. Вирішується через Eager Loading (`Include`), проекцію `Select()` або розбиттям на окремі SQL-запити через `AsSplitQuery()`.

Розгорнута відповідь:

// КАТАСТРОФА (N+1):
var orders = await db.Orders.ToListAsync(); // 1 запит: витягнув 100 замовлень
foreach (var order in orders)
{
    Console.WriteLine(order.Customer.Name); // Робить ЩЕ 100 окремих запитів до бази!
}

Способи вирішення:

  • Жадібне завантаження через .Include(): 
    var orders = await db.Orders.Include(o => o.Customer).ToListAsync(); // 1 запит через SQL JOIN
  • Проекція через DTO (Найшвидший варіант): 
    var data = await db.Orders.Select(o => new { o.Id, CustomerName = o.Customer.Name }).ToListAsync();
  • Split Queries (.AsSplitQuery()): Якщо ви робите .Include() для кількох колекцій одночасно (наприклад, Include(OrderItems).Include(OrderLogs)), один гігантський LEFT JOIN створює «картезіанський вибух» (дублювання мільйонів рядків у трафіку). .AsSplitQuery() змушує EF зробити 2–3 швидких паралельних SQL-запити замість одного монструозного JOIN'а.
Підступні питання на співбесіді:
П: Який головний ризик або недолік використання `.AsSplitQuery()`?

В: Ризик порушення узгодженості даних (Data Consistency). Оскільки виконується декілька окремих SQL-запитів до бази, якщо паралельна транзакція змінить або видалить рядки між виконанням першого та другого запиту, матеріалізований граф сутностей у C# виявиться неконсистентним (якщо вибірка не загорнута в транзакцію з рівнем ізоляції Serializable/Snapshot).

7. Стратегії завантаження зв'язаних даних в EF Core: Eager, Lazy та Explicit loading.

↑ До змісту
Коротка суть: Eager — завантажує все одразу через `.Include()`. Lazy — підвантажує зв'язані дані автоматично при першому зверненні до властивості (вимагає virtual). Explicit — явне завантаження за запитом через `db.Entry(e).Collection().Load()`.

Порівняння підходів:

  • Eager Loading (Жадібне): Завантажує залежності одразу в першому запиті за допомогою методів .Include() та .ThenInclude(). Рекомендований дефолтний підхід у вебі.
  • Lazy Loading (Ліниве): Дані не вантажаться, поки ви не звернетеся до властивості: order.Customer. Вимагає спеціального пакету Proxies та оголошення полів як public virtual. Антипатерн для REST API, бо серіалізатор JSON пройдеться по всіх властивостях і несподівано вивантажить усю базу даних, зробивши сотні запитів!
  • Explicit Loading (Явне): Завантажує пов'язані дані лише тоді, коли ви явно попросите про це в коді: 
    await db.Entry(order).Reference(o => o.Customer).LoadAsync();
Підступні питання на співбесіді:
П: Що станеться, якщо спробувати виконати Lazy Loading після того, як `DbContext` було звільнено (disposed)?

В: Виникне помилка `ObjectDisposedException: Cannot access a disposed context instance`. Оскільки Lazy Loading використовує посилання на початковий контекст для надсилання SQL-запиту, звернення до властивості за межами скоупу запиту завжди закінчується аварією.

8. Рівні ізоляції транзакцій у SQL (ACID). Які аномалії можуть виникати?

↑ До змісту
Коротка суть: Рівні ізоляції (від слабкого до сильного): Read Uncommitted → Read Committed → Repeatable Read → Serializable. Чим вищий рівень, тим менше аномалій, але тим гірша паралельна продуктивність через блокування рядків/таблиць.

Аномалії паралельного читання:

  1. Брудне читання (Dirty Read): Транзакція А прочитала дані, які змінила транзакція Б, але транзакція Б раптово зробила ROLLBACK. Транзакція А працювала з даними, яких насправді ніколи не існувало в базі!
  2. Неповторюване читання (Non-repeatable Read): Транзакція А читає рядок двічі, але між цими читаннями транзакція Б оновила цей рядок і зробила COMMIT. Значення поля змінилося прямо під час виконання першої транзакції.
  3. Фантомне читання (Phantom Read): Транзакція А робить вибірку за діапазоном (наприклад, WHERE Age > 20 — повернуло 5 рядків). Транзакція Б вставляє новий 6-й рядок із цим критерієм. Повторне виконання запиту в транзакції А повертає вже 6 рядків.

Рівні ізоляції:

  • Read Uncommitted: Дозволяє всі 3 аномалії (включаючи брудне читання).
  • Read Committed: Дефолт для MS SQL та PostgreSQL. Забороняє Dirty Read.
  • Repeatable Read: Забороняє Dirty Read та Non-repeatable Read (блокує прочитані рядки).
  • Serializable: Повна ізоляція, блокує цілі діапазони ключів (Range Locks). Жодних аномалій, але викликає часті Deadlock'и.
Підступні питання на співбесіді:
П: Як рівень ізоляції Snapshot (або MVCC у PostgreSQL) вирішує проблему блокувань між читачами та письменниками?

В: Замість встановлення блокувань на прочитані рядки (Shared Locks), база створює копії старих версій рядків у системному сховищі (tempdb або undo logs). Читання завжди повертає стан даних на момент старту транзакції: письменники ніколи не блокують читачів, а читачі не блокують письменників.

9. Кластеризовані vs Некластеризовані індекси в БД. Що таке складений та покриваючий індекс?

↑ До змісту
Коротка суть: Кластеризований індекс — це сама таблиця, фізично впорядкована за ключем (може бути лише один). Некластеризований — окрема B-Tree структура, що містить покажчик на рядок. Покриваючий індекс містить усі необхідні для запиту поля, позбавляючи потреби ходити в таблицю.

Розгорнута відповідь:

  • Кластеризований індекс (Clustered Index): Листові вузли дерева індексу (B-Tree) містять реальні сторінки даних таблиці. Може бути лише один на таблицю (за замовчуванням це Primary Key).
  • Некластеризований індекс (Non-clustered Index): Окрема допоміжна структура даних. Листові вузли містять лише значення індексованого поля та покажчик (Row ID або Clustered Key) на рядок у головній таблиці. Пошук спочатку знаходить рядок у некластеризованому індексі, а потім робить Key Lookup у кластеризовану таблицю за рештою полів.
  • Складений індекс (Composite Index): Індекс по кількох колонках: (LastName, FirstName). Працює за правилом «лівого префікса»: допоможе для пошуку по LastName або LastName + FirstName, але марний для пошуку тільки по FirstName!
  • Покриваючий індекс (Covering Index / INCLUDE): Якщо індекс містить усі колонки, які запитує SELECT (через CREATE INDEX ... INCLUDE (Email, Age)), СУБД віддає дані прямо з індексу без жодного звернення до самої таблиці (0 Key Lookups).
Підступні питання на співбесіді:
П: Чому `SELECT *` нівелює переваги більшості некластеризованих індексів?

В: Оскільки некластеризований індекс містить лише індексовані колонки, для вибірки символу `*` серверу доведеться робити `Key Lookup` до основної таблиці для кожного знайденого запису. Якщо знайдених рядків багато, оптимізатор запитів взагалі відмовиться від індексу і перейде на повільний `Full Table Scan`.

10. Чи потрібні патерни Repository та Unit of Work поверх EF Core? Аргументи «За» та «Проти».

↑ До змісту
Коротка суть: Сам `DbContext` вже є реалізацією Unit of Work, а `DbSet` — реалізацією Repository. Власні обгортки поверх EF Core часто є надлишковим антипатерном, якщо тільки вони не інкапсулюють специфічні бізнес-специфікації.

Розгорнута відповідь:

  • Чому це часто АНТИПАТЕРН:
    • Створення загального GenericRepository<T> з методами GetById, GetAll банально дублює API самого EF Core.
    • Повернення IEnumerable замість IQueryable ламає фільтрацію на боці бази, змушуючи викачувати всю таблицю в пам'ять.
    • Спроба абстрагуватися від EF Core на випадок «раптом змінимо БД на Mongo» у 99% реальних проєктів ніколи не реалізується, але створює тисячі рядків марного коду.
  • Коли кастомний Repository має сенс: Коли репозиторій інкапсулює складну доменну логіку (DDD-підхід): агрегат завжди завантажується цілком з усіма обов'язковими дочірніми сутностями за інваріантом, захищаючи базу від некоректного часткового читання.
Підступні питання на співбесіді:
П: Як тестувати бізнес-логіку без Repository-обгорток, якщо напряму використовується `DbContext`?

В: Сучасний підхід — відмовитися від юніт-тестування викликів EF через мокування `DbSet` і писати швидкі інтеграційні тести за допомогою `WebApplicationFactory` та бібліотеки `Testcontainers`, які піднімають реальну тестову БД в Docker за частки секунди.

11. Що таке CQRS? Використання патерну Mediator та бібліотеки MediatR у .NET.

↑ До змісту
Коротка суть: CQRS розділяє модель на операції модифікації (Commands) та операції читання (Queries). MediatR позбавляє контролери прямих залежностей від бізнес-сервісів, відправляючи команди відповідним окремим обробникам (Handlers).

Розгорнута відповідь:

CQRS (Command Query Responsibility Segregation):

  • Command (Команда): Змінює стан системи (створення, редагування, видалення). Завжди виконує валідацію бізнес-правил, не повертає складних даних (повертає void або Id).
  • Query (Запит): Лише читає дані. Не змінює стан. Може оминати важкі доменні моделі та читати DTO напряму з бази через оптимізований Dapper або `.AsNoTracking()`.
// Запит:
public record GetUserByIdQuery(int Id) : IRequest<UserDto>;

// Окремий ізольований обробник:
public class GetUserByIdHandler : IRequestHandler<GetUserByIdQuery, UserDto>
{
    public async Task<UserDto> Handle(GetUserByIdQuery request, CancellationToken ct)
    {
        // Логіка тільки для цього запиту
    }
}

// Контролер знає лише про IMediator:
[HttpGet("{id}")]
public async Task<IActionResult> Get(int id) => Ok(await _mediator.Send(new GetUserByIdQuery(id)));

Перевага: Контролери стають ультратонкими, дотримано Single Responsibility Principle (кожна операція — окремий файл/клас), зручно додавати наскрізну функціональність (валідацію FluentValidation або логування) через IPipelineBehavior.

Підступні питання на співбесіді:
П: Коли використання MediatR перетворюється на архітектурний антипатерн?

В: Коли він перетворюється на "God Object" посередника для простого CRUD без наскрізних PipelineBehaviors. Це ускладнює навігацію кодом в IDE (неможливо перейти до реалізації методу за F12) і створює зайвий оверхед алокацій у пам'яті.

12. Комунікація між сервісами: REST проти gRPC проти Message Brokers (RabbitMQ / Kafka).

↑ До змісту
Коротка суть: REST — універсальний текстовий HTTP/JSON протокол для публічних клієнтів. gRPC — надшвидкий двійковий HTTP/2 RPC для внутрішньої взаємодії мікросервісів. RabbitMQ/Kafka — асинхронна комунікація через події без жорсткого зв'язування.

Порівняння підходів:

  • REST (HTTP + JSON): Простий, людиночитабельний, працює в будь-якому браузері. Мінуси: великий розмір текстового JSON, відсутність суворої схеми типів за замовчуванням, оверхед на парсинг рядків.
  • gRPC (HTTP/2 + Protocol Buffers): Двійкова серіалізація через контрактні .proto файли. У 5–10 разів швидший за REST, споживає мінімум мережевого трафіку, підтримує двосторонній стрімінг (bidirectional streaming) та мультиплексування з'єднань. Ідеальний для синхронних викликів між бекенд-мікросервісами.
  • Message Brokers (RabbitMQ, Apache Kafka): Асинхронна шина подій (Event-Driven). Якщо Сервіс оплат впав, Сервіс замовлень все одно публікує подію в чергу повідомлень. Коли сервіс підніметься — він спокійно дочитає повідомлення. Гарантує слабке зв'язування (Loose Coupling) та стійкість до відмов.
Підступні питання на співбесіді:
П: Що таке патерн Transactional Outbox і яку проблему він вирішує в мікросервісах?

В: Проблему неконсистентності: коли потрібно одночасно зберегти дані в базу та опублікувати подію в RabbitMQ/Kafka (розподілені транзакції 2PC повільні й ненадійні). За патерном Outbox подія зберігається в таблицю `OutboxMessages` у тій самій транзакції БД, що й основна сутність, а фоновий воркер гарантовано вичитує її та відправляє у брокер.

13. Стратегії кешування: In-Memory vs Розподілений кеш (Redis). Що таке Cache Stampede (Лавина кешу)?

↑ До змісту
Коротка суть: In-Memory кеш живе в RAM конкретного процесу і втрачається при перезапуску. Redis живе на окремому сервері і доступний усім подам кластера. Cache Stampede — це падіння бази даних, коли одночасно протухає популярний ключ і тисячі потоків одночасно біжать у БД.

Порівняння:

  • IMemoryCache: Працює прямо в оперативній пам'яті процесу .NET. Доступ миттєвий ($O(1)$ без мережевих затримок). Проблема: якщо у вас запущено 5 копій (інстансів) програми під балансувальником, у кожної буде свій незалежний розсинхронізований кеш.
  • Розподілений кеш (Redis через IDistributedCache): Окремий спільний сервіс. Усі інстанси додатка бачать один і той самий стан. При перезапуску додатка кеш зберігається.
  • Cache Stampede (Лавина запитів): Відбувається, коли закінчується TTL (термін життя) дуже популярного запису (наприклад, каталогу товарів на Чорну П'ятницю). Сотні паралельних користувацьких запитів виявляють, що в кеші порожньо, і одночасно надсилають важкий запит у SQL-базу, що миттєво «кладе» базу.
    Рішення: Використання HybridCache (у .NET 9+) або бібліотеки FusionCache із механізмом блокувань (Stampede lock), щоб лише один потік ішов у базу для оновлення, а інші отримували результат очікування.
Підступні питання на співбесіді:
П: Як новий `HybridCache` у .NET 9 вирішує проблему швидкодії та синхронізації кешів?

В: `HybridCache` об'єднує швидкий локальний L1-кеш (in-process RAM) і надійний розподілений L2-кеш (Redis), самостійно забезпечуючи вбудований захист від Cache Stampede та дедуплікацію паралельних запитів на рівні фабрики генерації даних.

14. Інтеграційні тести в ASP.NET Core: `WebApplicationFactory` та бібліотека Testcontainers.

↑ До змісту
Коротка суть: `WebApplicationFactory` піднімає весь реальний ASP.NET Core бекенд у пам'яті тестового процесу. `Testcontainers` автоматично запускає реальну базу даних (Postgres/MSSQL) у тимчасовому Docker-контейнері на час прогону тестів.

Розгорнута відповідь:

Раніше розробники часто тестували інтеграцію через In-Memory EF Core Provider, проте In-Memory провайдер не підтримує сирий SQL, збережені процедури, транзакції та зовнішні ключі, пропускаючи критичні баги.

// Сучасний золотий стандарт інтеграційного тесту:
public class OrderApiTests : IAsyncLifetime
{
    // 1. Автоматично стартує реальний PostgreSQL у Docker
    private readonly PostgreSqlContainer _dbContainer = new PostgreSqlBuilder().Build();

    public async Task InitializeAsync() => await _dbContainer.StartAsync();

    [Fact]
    public async Task CreateOrder_ValidRequest_Returns201Created()
    {
        // 2. Піднімаємо In-Memory веб-сервер із реальною базою в контейнері
        var factory = new WebApplicationFactory<Program>()
            .WithWebHostBuilder(builder =>
            {
                builder.ConfigureServices(services =>
                {
                    // Підміна рядка підключення на тимчасовий контейнер
                    services.AddDbContext<AppDbContext>(opt => opt.UseNpgsql(_dbContainer.GetConnectionString()));
                });
            });

        HttpClient client = factory.CreateClient();

        // 3. Відправляємо реальний HTTP-запит через увесь пайплайн
        var response = await client.PostAsJsonAsync("/api/orders", new CreateOrderDto("Laptop"));

        Assert.Equal(HttpStatusCode.Created, response.StatusCode);
    }

    public async Task DisposeAsync() => await _dbContainer.DisposeAsync();
}
Підступні питання на співбесіді:
П: Чому не варто запускати міграції бази на кожен окремий тест у Testcontainers?

В: Накат міграцій — це важка I/O операція, яка роздує час виконання тестів до десятків хвилин. Правильний підхід: підняти контейнер один раз на всю тестову колекцію (ICollectionFixture), накатити міграції, а між тестами очищати виключно дані за допомогою інструменту Respawn.

15. Що таке Observability? Структуроване логування (Serilog) та Health Checks в ASP.NET Core.

↑ До змісту
Коротка суть: Observability складається з Трьох Кигів: Logs, Metrics та Traces. Структуроване логування зберігає повідомлення не звичайним текстом, а як JSON-об'єкти з параметрами для зручного пошуку в ElasticSearch/Seq.

Розгорнута відповідь:

  • Структуроване логування (Structured Logging): 
    // ПОГАНО: Звичайний текст. Складно знайти замовлення в Kibana/Seq
_logger.LogInformation($"Замовлення {orderId} створено клієнтом {userId}");

// ДОБРЕ: Повідомлення зберігає властивості як окремі поля JSON-об'єкта!
_logger.LogInformation("Замовлення {OrderId} створено клієнтом {UserId}", orderId, userId);
    У системах моніторингу (Seq, ElasticSearch, Loki) тепер можна робити запити на зразок: UserId == 42 AND OrderId > 100 без повільних регулярних виразів.
  • Health Checks: Вбудований механізм перевірки працездатності додатку для Kubernetes або балансувальника: 
    builder.Services.AddHealthChecks()
    .AddNpgSql(connectionString) // Перевірка доступності бази даних
    .AddRedis(redisConnectionString); // Перевірка Redis

app.MapHealthChecks("/healthz"); // Ендпоінт для k8s Liveness/Readiness проби
Підступні питання на співбесіді:
П: У чому різниця між Liveness Probe та Readiness Probe у Kubernetes?

В: `Liveness` перевіряє, чи взагалі живий процес додатку (якщо проба падає, Kubernetes примусово перезавантажує контейнер). `Readiness` перевіряє, чи готовий додаток приймати трафік користувачів (наприклад, чи підключився до БД). Якщо Readiness падає, контейнер не перезапускають, а тимчасово виключають із балансувальника трафіку.
