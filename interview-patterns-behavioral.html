Патерн 13: Chain of Responsibility (Ланцюжок обов'язків)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє передавати запити послідовно через ланцюжок обробників. Кожен обробник вирішує: обробити запит самостійно, передати його далі наступному чи перервати виконання.

2. Коли застосовувати

  • Запит повинен пройти серію незалежних послідовних перевірок (перевірка авторизації, обмеження частоти Rate Limiting, валідація, кешування).
  • Склад і черговість обробників повинні гнучко конфігуруватися під час запуску програми без зміни коду самих обробників.
Приклади у .NET: Конвеєр Middleware в ASP.NET Core (app.UseAuthentication(), app.UseAuthorization() тощо), ланцюжки DelegatingHandler у HttpClientFactory.

3. Реалізація на C#

using System;

// 1. Request model
public class SupportTicket
{
    public string Description { get; set; }
    public int SeverityLevel { get; set; }

    public SupportTicket(string desc, int level)
    {
        Description = desc;
        SeverityLevel = level;
    }
}

// 2. Base handler defining the chain structure
public abstract class BaseHandler
{
    private BaseHandler _next;

    public BaseHandler SetNext(BaseHandler next)
    {
        _next = next;
        return next;
    }

    public virtual void Handle(SupportTicket ticket)
    {
        if (_next != null)
            _next.Handle(ticket);
        else
            Console.WriteLine($"[!] Unable to handle: {ticket.Description}");
    }
}

// 3. Concrete handler: automated bot
public class BotHandler : BaseHandler
{
    public override void Handle(SupportTicket ticket)
    {
        if (ticket.SeverityLevel == 1)
            Console.WriteLine($"[Bot] Resolved: {ticket.Description}");
        else
            base.Handle(ticket);
    }
}

// 4. Concrete handler: support engineer
public class EngineerHandler : BaseHandler
{
    public override void Handle(SupportTicket ticket)
    {
        if (ticket.SeverityLevel == 2)
            Console.WriteLine($"[Engineer] Fixed bug: {ticket.Description}");
        else
            base.Handle(ticket);
    }
}

class Program
{
    static void Main()
    {
        var bot = new BotHandler();
        var engineer = new EngineerHandler();
        bot.SetNext(engineer);

        bot.Handle(new SupportTicket("Forgot password", 1));
        bot.Handle(new SupportTicket("Database crashed", 2));
    }
}

/* Результат виконання: **************************************/

[Bot] Resolved: Forgot password
[Engineer] Fixed bug: Database crashed

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви службу підтримки інтернет-провайдера. Ти телефонуєш на гарячу лінію. Спочатку слухавку бере автоматичний голосовий бот. Якщо ти забув пароль або хочеш перевірити баланс — бот вирішує це сам. Якщо в тебе фізично обірвався кабель, бот перемикає тебе на інженера техпідтримки. Якщо впала магістральна мережа міста — інженер передає тікет на рівень головного системного архітектора. Тобі не треба знати номер телефону архітектора: ти дзвониш на єдину точку входу, а запит сам мандрує ланцюжком.

1. Як влаштований код
Клієнт (Main) │ надсилає SupportTicket ▼ BotHandler (Рівень 1: Прості тікети) │ якщо Severity != 1 — передає далі через _next ▼ EngineerHandler (Рівень 2: Складні технічні баги) │ якщо Severity != 2 — передає далі через _next ▼ Кінець ланцюжка (_next == null) ──► Повідомлення: не вдалося обробити

Головна ідея: відправник не знає, хто саме виконає задачу. Запит рухається по ланцюжку вперед, поки хтось не скаже: «Я знаю, як це вирішити».

2. Розбираємо код по частинах

Частина 1. Модель запиту SupportTicket

Звичайний об'єкт із описом проблеми та рівнем критичності SeverityLevel (1 — банальний, 2 — складний інженерний баг).

Частина 2. Базовий клас BaseHandler

У ньому зосереджено весь механізм побудови зв'язаного списку ланцюжка:

public BaseHandler SetNext(BaseHandler next)
{
    _next = next;
    return next; // Повертаємо переданого наступника
}

Завдяки return next; ланцюжки можна будувати елегантним ланцюжком: bot.SetNext(engineer).SetNext(director).

А ось як влаштований метод переходу:

public virtual void Handle(SupportTicket ticket)
{
    if (_next != null) 
        _next.Handle(ticket);
    else 
        Console.WriteLine($"[!] Unable to handle: {ticket.Description}");
}

Якщо обробник не зміг впоратися, він викликає base.Handle(ticket), який автоматично «штовхає» тікет наступній ланці.

Частина 3. Конкретні класи BotHandler та EngineerHandler

Кожен клас перевіряє свій рівень:

if (ticket.SeverityLevel == 1)
    Console.WriteLine($"[Bot] Resolved: {ticket.Description}");
else
    base.Handle(ticket); // Передаємо вище по інстанції
3. Що відбувається в Main() крок за кроком
Крок 1 — Збирання ланцюжка:
Створюємо bot та engineer. Виклик bot.SetNext(engineer) вказує боту, хто є його старшим наступником.
Крок 2 — Перший тікет ("Forgot password", рівень 1):
Клієнт передає тікет боту. Бот перевіряє умову: SeverityLevel == 1 → істина! Бот сам друкує [Bot] Resolved: Forgot password. Тікет успішно оброблено, далі запит не йде.
Крок 3 — Другий тікет ("Database crashed", рівень 2):
Клієнт знову віддає тікет на першу ланку (боту). Бот бачить рівень 2, не вміє цього лагодити й викликає base.Handle(). Запит перелітає до engineer. Інженер перевіряє: SeverityLevel == 2 → істина! Друкується [Engineer] Fixed bug: Database crashed.
4. Чому це краще за наївний if-else?

Без патерну ти б написав велетенський спагеті-метод із 20 умовами if-else. Кожен новий тип проблеми роздував би цей метод до тисячі рядків коду.
У Chain of Responsibility кожен обробник — це окремий незалежний клас (SRP). Ти можеш будь-якої миті вставити посередині SecurityHandler чи RateLimitHandler без зміни коду бота чи інженера (OCP). Саме так працює конвеєр Middleware в ASP.NET Core!

4. Плюси та мінуси

  • Переваги: усуває жорстку залежність між відправником і отримувачами; дозволяє гнучко налаштовувати черговість фільтрів та перевірок під час запуску.
  • Недоліки: якщо ланцюжок сконфігуровано без замикаючого дефолтного обробника, запит може пройти до кінця й залишитися непомітно втраченим.

Патерн 14: Command (Команда)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Перетворює запити або дії на окремі самостійні об'єкти. Це дозволяє передавати операції як параметри, ставити їх у чергу на відкладене виконання, логувати та реалізовувати скасування дій (Undo/Redo).

2. Коли застосовувати

  • Потрібна повноцінна історія дій із можливістю відкату (Undo) та повтору (Redo) в текстових, графічних редакторах або банківських додатках.
  • Потрібно ставити завдання в чергу для фонової обробки або відкладеного виконання за розкладом (Job Queues).
Приклади у .NET: Інтерфейс ICommand у WPF / .NET MAUI (зв'язування дій користувача з кнопками в патерні MVVM), архітектура CQRS через бібліотеку MediatR.

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Receiver: contains business logic
public class BankAccount
{
    public decimal Balance { get; private set; }
    public void Deposit(decimal amt) => Balance += amt;
    public void Withdraw(decimal amt) => Balance -= amt;
}

// 2. Command interface
public interface ICommand
{
    void Execute();
    void Undo();
}

// 3. Concrete Command
public class DepositCommand : ICommand
{
    private readonly BankAccount _acc;
    private readonly decimal _amt;

    public DepositCommand(BankAccount acc, decimal amt)
    {
        _acc = acc;
        _amt = amt;
    }

    public void Execute() => _acc.Deposit(_amt);
    public void Undo() => _acc.Withdraw(_amt);
}

// 4. Invoker: tracks execution history for undo
public class TransactionManager
{
    private readonly Stack<ICommand> _history = new();

    public void Execute(ICommand cmd)
    {
        cmd.Execute();
        _history.Push(cmd);
    }

    public void Undo()
    {
        if (_history.Count > 0)
            _history.Pop().Undo();
    }
}

class Program
{
    static void Main()
    {
        var acc = new BankAccount();
        var manager = new TransactionManager();

        manager.Execute(new DepositCommand(acc, 500m));
        Console.WriteLine($"Balance: {acc.Balance:C}");

        manager.Undo();
        Console.WriteLine($"Balance after Undo: {acc.Balance:C}");
    }
}

/* Результат виконання: **************************************/

Balance: 500,00 ₴
Balance after Undo: 0,00 ₴

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви ресторан. Ти сідаєш за столик і замовляєш стейк. Ти не біжиш на кухню і не кричиш кухарю в спину: «Смаж м'ясо!». Замість цього підходить офіціант і записує замовлення на паперовий чековий талончик. Цей талончик — і є Команда. Він містить усе необхідне: що приготувати, для якого столика і скільки порцій. Його можна покласти в чергу, перенести на пізніше, а якщо ти передумав — забрати талончик назад і скасувати приготування.

1. Як влаштований код
Invoker (Менеджер транзакцій: веде Stack історії) │ Execute(cmd) ──► запускає команду та кладе її у стек ▼ ICommand (Інтерфейс: вимагає вміти Execute() та Undo()) ▲ │ реалізує DepositCommand (Конкретна команда: знає рахунок і суму) │ керує діями ▼ Receiver (BankAccount: реальний рахунок із методами Deposit/Withdraw)

Головна ідея: дія перетворюється на самостійний об'єкт, який можна зберігати в змінних, масивах або стеках.

2. Розбираємо код по частинах

Частина 1. Одержувач (Receiver) BankAccount

Звичайний клас бізнес-логіки. Він вміє збільшувати (Deposit) та зменшувати (Withdraw) баланс рахунку.

Частина 2. Контракт команди ICommand

public interface ICommand
{
    void Execute();
    void Undo();
}

Кожна дія зобов'язана не лише вміти виконатися (Execute), а й знати, як повністю повернути все назад у початковий стан (Undo).

Частина 3. Конкретна команда DepositCommand

Команда в конструкторі запам'ятовує рахунок і суму поповнення. Коли викликають Execute(), вона викликає Deposit(). Коли викликають Undo(), вона викликає протилежну дію: Withdraw() на ту саму суму!

Частина 4. Ініціатор (Invoker) TransactionManager

Зверни увагу на використання стека:

private readonly Stack<ICommand> _history = new();

Коли ми виконуємо команду, ми викликаємо її метод і кладемо в стек через _history.Push(cmd). Коли ми кажемо Undo(), ми знімаємо верхівку стека через _history.Pop() і викликаємо її скасування. Це дає змогу легко відкотити 10, 20 чи 100 дій назад!

3. Що відбувається в Main() крок за кроком
Крок 1 — Створення та виконання команди:
Ми створюємо команду поповнення на 500 грн і віддаємо її менеджеру: manager.Execute(new DepositCommand(acc, 500m));. Менеджер виконує команду і кладе її у стек. Рахунок показує:
Balance: 500,00 ₴.
Крок 2 — Відкат операції (Undo):
Ми викликаємо manager.Undo();. Менеджер дістає останню команду зі стека і викликає її метод Undo(), який списує 500 грн назад.
Крок 3 — Перевірка результату:
Баланс знову стає нульовим, немов операції ніколи й не було:
Balance after Undo: 0,00 ₴.
4. Чому це краще за прямий виклик acc.Deposit(500)?

Якщо викликати методи напряму, код викликача намертво зв'язується з рахунком. Ти не зможеш записати історію дій у базу даних для аудиту, не зможеш реалізувати комбінацію клавіш Ctrl+Z і не зможеш відкласти транзакцію на ніч. Патерн Command перетворює дію на повноцінні дані першого класу.

4. Плюси та мінуси

  • Переваги: природна реалізація операцій скасування (Undo) і повторення (Redo); повне розв'язування ініціатора виклику та виконавця.
  • Недоліки: велика кількість дрібних класів під кожну операцію в системі.

Патерн 15: Iterator (Ітератор)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дає можливість послідовно обходити елементи складної колекції, не розкриваючи її внутрішнього влаштування (масив, дерево, стек, граф чи зв'язаний список).

2. Коли застосовувати

  • Потрібно приховати складну внутрішню структуру сховища даних від клієнтського коду заради безпеки та інкапсуляції.
  • Необхідно підтримувати кілька різних варіантів обходу однієї й тієї самої колекції (прямий, зворотний, за алфавітом).
У .NET: Патерн закладений у саму основу платформи через інтерфейси IEnumerable<T>, IEnumerator<T>, оператор foreach та генераторний синтаксис yield return.

3. Реалізація на C#

using System;
using System.Collections;
using System.Collections.Generic;

// Collection supporting custom iteration
public class Playlist : IEnumerable<string>
{
    private readonly List<string> _songs = new();
    public void Add(string song) => _songs.Add(song);

    public IEnumerator<string> GetEnumerator()
    {
        foreach (var s in _songs)
            yield return s;
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();

    public IEnumerable<string> Backwards()
    {
        for (int i = _songs.Count - 1; i >= 0; i--)
            yield return _songs[i];
    }
}

class Program
{
    static void Main()
    {
        var list = new Playlist { "Song 1", "Song 2", "Song 3" };

        foreach (var song in list.Backwards())
        {
            Console.WriteLine(song);
        }
    }
}

/* Результат виконання: **************************************/

Song 3
Song 2
Song 1

/*************************************************************/

4. Плюси та мінуси

  • Переваги: спрощує інтерфейс колекцій; дозволяє паралельно робити незалежні обходи тих самих даних кількома різними потоками.
  • Недоліки: використання для примітивних одновимірних масивів є надлишковим.

Патерн 16: Mediator (Посередник)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Змушує компоненти взаємодіяти не напряму між собою, а через єдиний об'єкт-посередник. Це перетворює заплутану павутину зв'язків «багато-до-багатьох» ($M \times N$) на просту зіркоподібну топологію «один-до-багатьох» ($1 \times N$).

2. Коли застосовувати

  • Між класами інтерфейсу користувача (UI) або мікросервісами виникла хаотична сітка взаємних посилань і подій.
  • Потрібно перевикористовувати графічні компоненти форми в різних діалогових вікнах, не прив'язуючи їх намертво до сусідніх кнопок.
Приклади у .NET: Популярна бібліотека MediatR для організації зв'язку між контролерами веб-API та сервісами бізнес-логіки за принципом CQRS.

3. Реалізація на C#

using System;

// 1. Mediator contract
public interface IMediator
{
    void Notify(object sender, string ev);
}

// 2. Colleague 1: Button
public class Button
{
    private IMediator _m;
    public bool IsEnabled { get; set; }

    public void SetMediator(IMediator m) => _m = m;
}

// 3. Colleague 2: Checkbox
public class Checkbox
{
    private IMediator _m;
    public bool Checked { get; private set; }
    public void SetMediator(IMediator m) => _m = m;

    public void Toggle()
    {
        Checked = !Checked;
        _m?.Notify(this, "toggle");
    }
}

// 4. Concrete Mediator coordinating UI components
public class DialogMediator : IMediator
{
    private readonly Button _btn;
    private readonly Checkbox _cb;

    public DialogMediator(Button btn, Checkbox cb)
    {
        _btn = btn;
        _btn.SetMediator(this);
        _cb = cb;
        _cb.SetMediator(this);
    }

    public void Notify(object sender, string ev)
    {
        if (ev == "toggle")
            _btn.IsEnabled = _cb.Checked;
    }
}

class Program
{
    static void Main()
    {
        var button = new Button();
        var checkbox = new Checkbox();
        var mediator = new DialogMediator(button, checkbox);

        Console.WriteLine("Initial state:");
        Console.WriteLine($"Checkbox Checked: {checkbox.Checked}");
        Console.WriteLine($"Button IsEnabled: {button.IsEnabled}\n");

        Console.WriteLine("Toggle checkbox (user accepts terms):");
        checkbox.Toggle();
        Console.WriteLine($"Checkbox Checked: {checkbox.Checked}");
        Console.WriteLine($"Button IsEnabled: {button.IsEnabled}\n");

        Console.WriteLine("Toggle checkbox again:");
        checkbox.Toggle();
        Console.WriteLine($"Checkbox Checked: {checkbox.Checked}");
        Console.WriteLine($"Button IsEnabled: {button.IsEnabled}");
    }
}

/* Результат виконання: **************************************/

Initial state:
Checkbox Checked: False
Button IsEnabled: False

Toggle checkbox (user accepts terms):
Checkbox Checked: True
Button IsEnabled: True

Toggle checkbox again:
Checkbox Checked: False
Button IsEnabled: False

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви диспетчерську вежу аеропорту. У небі кружляють десятки літаків. Пілоти не виходять у спільний радіоефір зі словами: «Гей, борт 105, я зараз сідаю, почекай, поки я звільню смугу!». Це призвело б до катастрофи за кілька хвилин. Кожен літак спілкується лише з диспетчером у вежі, а диспетчер централізовано вирішує, кому злітати, а кому чекати. Диспетчер — це і є класичний Посередник (Mediator).

1. Як влаштований код
Button (Кнопка) Checkbox (Чекбокс) │ │ │ не знають про існування один одного! │ надсилають сигнал лише диспетчеру: └───► Notify(this, "toggle") ◄───┘ │ ▼ DialogMediator (Посередник) (Координує взаємодію: якщо Checkbox позначено — увімкнути Button)

Головна ідея: компоненти інтерфейсу абсолютно ізольовані. Вони не тримають посилань на сусідні кнопки й не знають, хто стоїть поруч із ними на формі.

2. Розбираємо код по частинах

Частина 1. Інтерфейс посередника IMediator

public interface IMediator
{
    void Notify(object sender, string ev);
}

Контракт має один метод нотифікації: хто надіслав (sender) та що сталося (ev — ім'я події).

Частина 2. Колеги (Button і Checkbox)

Зверни увагу на клас Checkbox:

public void Toggle()
{
    Checked = !Checked;
    _m?.Notify(this, "toggle");
}

Чекбокс змінює свій внутрішній стан і просто кричить у рацію посередника: «У мене відбулася подія toggle!». Він не знає, чи є на формі кнопка, чи текстове поле, чи взагалі нікого немає.

Частина 3. Конкретний посередник DialogMediator

Він збирає кнопку та чекбокс разом і реєструє себе як їхнього посередника (SetMediator(this)). Коли приходить сповіщення, він запускає логіку взаємозв'язку:

public void Notify(object sender, string ev)
{
    if (ev == "toggle")
        _btn.IsEnabled = _cb.Checked;
}
3. Що відбувається в Main() крок за кроком
Крок 1 — Стартовий стан:
Чекбокс порожній (Checked: False), кнопка заблокована (IsEnabled: False).
Крок 2 — Користувач ставить галочку («Погоджуюсь з умовами»):
Викликається checkbox.Toggle(). Чекбокс сповіщає посередника. Посередник дивиться на _cb.Checked (там тепер true) і розблоковує кнопку:
Checkbox Checked: True
Button IsEnabled: True.
Крок 3 — Зняття галочки:
Повторний клік перемикає галочку в false. Посередник миттєво реагує та блокує кнопку назад:
Button IsEnabled: False.
4. Чому це краще за наївний підхід?

Уяви реальну діалогову форму реєстрації: 5 полів вводу, 2 чекбокси, 3 радіокнопки й кнопка відправки. Якщо кожен елемент підписуватиметься на події інших 10 елементів напряму, утвориться нерозплутувана павутина залежностей. Зміниш один чекбокс — зламаються три кнопки.
Mediator концентрує всю бізнес-координацію форми в одному місці (SRP). Самі кнопки та чекбокси залишаються «чистими» і можуть перевикористовуватися в будь-яких інших вікнах.

4. Плюси та мінуси

  • Переваги: усуває хаос взаємних посилань між класами; дозволяє повторно використовувати окремі компоненти без зміни їхнього коду.
  • Недоліки: з часом клас посередника може надмірно розростися й перетворитися на перевантажений God Object.

Патерн 17: Memento (Знімок)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє зберігати та відновлювати минулий стан об'єкта, не порушуючи його інкапсуляцію та не виставляючи приватні поля напоказ зовнішньому світу.

2. Коли застосовувати

  • Потрібно реалізувати збереження контрольних точок (checkpoints) гри чи документа для відкату назад при виникненні помилок.
  • Пряме відкриття полів стану об'єкта через публічні геттери/сеттери зламало б його архітектурну безпеку.
Приклади у .NET: Механізм відстеження змін у Entity Framework Core: властивість EntityEntry.OriginalValues зберігає знімок початкових значень полів, зчитаних із бази даних.

3. Реалізація на C#

using System;
using System.Collections.Generic;

// Marker interface for snapshots
public interface IMemento { }

// Originator: stateful object
public class Editor
{
    private string _text = "";

    public void Type(string words) => _text += words;

    public string Text => _text;

    public IMemento Save() => new Memento(_text);

    public void Restore(IMemento m)
    {
        if (m is Memento s)
            _text = s.State;
    }

    // Private inner snapshot class protecting encapsulation
    private class Memento : IMemento
    {
        public string State { get; }

        public Memento(string state) => State = state;
    }
}

class Program
{
    static void Main()
    {
        var editor = new Editor();
        var history = new Stack<IMemento>();

        editor.Type("Version 1");
        history.Push(editor.Save());

        editor.Type(" + error text");
        editor.Restore(history.Pop());
        Console.WriteLine(editor.Text);
    }
}

/* Результат виконання: **************************************/

Version 1

/*************************************************************/

4. Плюси та мінуси

  • Переваги: зберігає стан надійно закритим від зовнішнього втручання; надає простий спосіб відкату назад.
  • Недоліки: часте створення знімків важких об'єктів створює велике навантаження на оперативну пам'ять (RAM).

Патерн 18: Observer (Спостерігач)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Створює механізм підписки, який дозволяє об'єктам автоматично отримувати сповіщення про зміну стану іншого суб'єкта, за яким вони спостерігають.

2. Коли застосовувати

  • Зміна стану одного компонента вимагає автоматичного оновлення багатьох інших невідомих заздалегідь об'єктів.
  • Побудова реактивних інтерфейсів (UI), моделей Publisher-Subscriber або обробки потоків подій у реальному часі.
Приклади у .NET: Ключове слово event та делегати мови C#, інтерфейс INotifyPropertyChanged у WPF/MAUI, інтерфейси IObservable<T> та IObserver<T> у бібліотеці Reactive Extensions (Rx.NET).

3. Реалізація на C#

using System;

// Subject: raises an event when its state changes
public class Product
{
    private decimal _price;

    // Idiomatic C# event-based Observer
    public event Action<decimal> PriceChanged;

    public decimal Price
    {
        get => _price;
        set
        {
            if (_price != value)
            {
                _price = value;
                PriceChanged?.Invoke(_price);
            }
        }
    }
}

class Program
{
    static void Main()
    {
        var product = new Product();

        // Subscribing to notifications
        product.PriceChanged += price => Console.WriteLine($"New price alert: {price:C}");

        // Modifying state triggers observer callback
        product.Price = 120m;
    }
}

/* Результат виконання: **************************************/

New price alert: 120,00 ₴

(Формат валюти залежить від системної локалі, наприклад: 120,00 ₴ або $120.00)

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви підписку на YouTube-канал або Telegram-паблік. Блогер не ходить особисто до кожного підписника додому, щоб сказати: «Я випустив нове відео!». Ти просто тиснеш кнопку «Підписатися» (дзвіночок). Як тільки блогер завантажує нове відео, платформа YouTube автоматично шле пуш-повідомлення всім підписникам одночасно. Блогер не знає твого імені чи адреси — він знає лише, що є список підписників, яким треба надіслати сигнал.

1. Як влаштований код
Product (Видавець / Subject) ├── Внутрішній стан: _price └── event Action<decimal> PriceChanged ──► Список зареєстрованих підписників │ │ при зміні ціни автоматично шле сповіщення: ▼ Підписники (Observers: лямбда в Main(), віджети UI, аудитори тощо)

Головна ідея: видавець нічого не знає про своїх підписників, крім того, що вони готові прийняти нове значення ціни.

2. Розбираємо код по частинах

Частина 1. Оголошення події event

У сучасному C# для Observer не потрібно створювати громіздкі інтерфейси ISubscriber — для цього є вбудований синтаксис:

public event Action<decimal> PriceChanged;

Ключове слово event грає роль захисного бар'єра: воно забороняє сторонньому коду примусово викликати подію або випадково очистити список усіх підписників через product.PriceChanged = null;. Зовнішній код може лише додати себе через += або відписатися через -=.

Частина 2. Сеттер властивості Price

if (_price != value)
{
    _price = value;
    PriceChanged?.Invoke(_price);
}

1. Перевірка _price != value захищає від марного спаму: якщо ціну перезаписали тим самим числом, ніхто не тривожитиме підписників.
2. Оператор безпечного виклику ?.Invoke(...) захищає від падіння з NullReferenceException, якщо на подію взагалі ніхто не підписався.

3. Що відбувається в Main() крок за кроком
Крок 1 — Підписка на подію (+=):
Ми реєструємо спостерігача за допомогою лямбда-виразу:
product.PriceChanged += price => Console.WriteLine($"New price alert: {price:C}");.
Крок 2 — Зміна ціни:
Ми присвоюємо product.Price = 120m;. Спрацьовує сеттер властивості.
Крок 3 — Автоматичне оповіщення:
Сеттер викликає делегат PriceChanged. Спостерігач негайно перехоплює значення і виводить:
New price alert: 120,00 ₴.
4. Питання-пастка зі співбесіди: «Lapsed Listener Problem»
Увага! Це один із найпідступніших витоків пам'яті в C#. Якщо короткоживучий об'єкт підписався на подію довгоживучого сервісу (наприклад, синглтона), довгоживучий об'єкт утримує сильне посилання (Strong Reference) на підписника через делегат. Якщо забути відписатися через -=, Garbage Collector ніколи не звільнить пам'ять підписника!

4. Плюси та мінуси

  • Переваги: слабке зв'язування між видавцем і слухачами; підтримка додавання нових підписників під час роботи програми без зміни видавця.
  • Недоліки: небезпека витоків пам'яті при забутій відписці; порядок оповіщення підписників не гарантується.

Патерн 19: State (Стан)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє об'єкту кардинально змінювати свою поведінку при зміні внутрішнього стану, створюючи враження, що об'єкт змінив свій клас, та позбавляючи від гігантських конструкцій switch/case.

2. Коли застосовувати

  • Поведінка сутності кардинально залежить від її поточного бізнес-статусу (наприклад, Замовлення: Нове → Оплачене → Відправлене).
  • Методи класу перевантажені громіздкими розгалуженнями if (status == Status.Paid) ... else if (...).
Приклади у .NET: Бібліотека Stateless для наочного опису скінченних автоматів (State Machines) у чистому C# коді.

3. Реалізація на C#

using System;

// 1. State contract
public interface IOrderState
{
    void Pay(OrderContext ctx);

    void Ship(OrderContext ctx);
}

// 2. Context holding the active state
public class OrderContext
{
    private IOrderState _state = new NewState();

    public void SetState(IOrderState state) => _state = state;

    public void Pay() => _state.Pay(this);

    public void Ship() => _state.Ship(this);
}

// 3. Concrete State: New
public class NewState : IOrderState
{
    public void Pay(OrderContext ctx)
    {
        Console.WriteLine("Order paid successfully.");
        ctx.SetState(new PaidState());
    }

    public void Ship(OrderContext ctx) => Console.WriteLine("Error: Cannot ship an unpaid order!");
}

// 4. Concrete State: Paid
public class PaidState : IOrderState
{
    public void Pay(OrderContext ctx) => Console.WriteLine("Warning: Already paid.");

    public void Ship(OrderContext ctx) => Console.WriteLine("Order shipped via courier.");
}

class Program
{
    static void Main()
    {
        var order = new OrderContext();

        Console.WriteLine("1. Attempting to ship new order:");
        order.Ship();

        Console.WriteLine("\n2. Paying for the order:");
        order.Pay();

        Console.WriteLine("\n3. Attempting to pay again:");
        order.Pay();

        Console.WriteLine("\n4. Shipping the paid order:");
        order.Ship();
    }
}

/* Результат виконання: **************************************/

1. Attempting to ship new order:
Error: Cannot ship an unpaid order!

2. Paying for the order:
Order paid successfully.

3. Attempting to pay again:
Warning: Already paid.

4. Shipping the paid order:
Order shipped via courier.

/*************************************************************/

4. Плюси та мінуси

  • Переваги: позбавляє від заплутаного спагеті-коду умовних переходів; локалізує поведінку кожного стану у власному класі (SRP).
  • Недоліки: може бути надлишковим ускладненням для систем, що мають лише 2 прості стани.

Патерн 20: Strategy (Стратегія)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Визначає сімейство взаємозамінних алгоритмів, інкапсулює кожен із них в окремий клас і дає змогу підміняти алгоритми на льоту під час виконання програми.

2. Коли застосовувати

  • Потрібно використовувати різні варіації розрахунків (тарифи доставки, розрахунок податків, алгоритми стиснення або сортування).
  • Необхідно підміняти алгоритм прямо під час роботи програми залежно від вибору користувача без зміни класу-контексту.
Приклади у .NET: Інтерфейси IComparer<T> та IEqualityComparer<T> у методах LINQ OrderBy та Array.Sort.

3. Реалізація на C#

using System;

// 1. Strategy contract
public interface IShippingStrategy
{
    decimal Calculate(decimal total);
}

// 2. Concrete Strategy: Postal delivery
public class PostalShipping : IShippingStrategy
{
    public decimal Calculate(decimal total) => 50m;
}

// 3. Concrete Strategy: Courier delivery
public class CourierShipping : IShippingStrategy
{
    public decimal Calculate(decimal total) => 150m;
}

// 4. Context using strategy via composition
public class OrderCalculator
{
    private IShippingStrategy _strategy;

    public OrderCalculator(IShippingStrategy s) => _strategy = s;

    public void SetStrategy(IShippingStrategy s) => _strategy = s;

    public decimal GetTotal(decimal subtotal) => subtotal + _strategy.Calculate(subtotal);
}

class Program
{
    static void Main()
    {
        decimal subtotal = 1000m;
        Console.WriteLine($"Base order amount: {subtotal} UAH\n");

        var calculator = new OrderCalculator(new PostalShipping());
        decimal postalTotal = calculator.GetTotal(subtotal);
        Console.WriteLine($"Total with postal shipping: {postalTotal} UAH");

        calculator.SetStrategy(new CourierShipping());
        decimal courierTotal = calculator.GetTotal(subtotal);
        Console.WriteLine($"Total with courier shipping: {courierTotal} UAH");
    }
}

/* Результат виконання: **************************************/

Base order amount: 1000 UAH

Total with postal shipping: 1050 UAH
Total with courier shipping: 1150 UAH

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви додаток Google Maps або Waze. Ти вводиш точку призначення: «Центральний вокзал». Як туди дістатися? Додаток пропонує вибір: на авто (маршрут через магістралі з урахуванням заторів), пішки (найкоротший шлях крізь двори та парки) або велосипедом (через велодоріжки). Мета однакова — дістатися вокзалу, але алгоритм розрахунку маршруту кардинально змінюється залежно від обраного транспорту. Кожен такий алгоритм — це окрема Стратегія.

1. Як влаштований код
OrderCalculator (Контекст: знає суму замовлення) │ тримає посилання на поточну стратегію ▼ IShippingStrategy (Контракт алгоритму: Calculate(decimal total)) ▲ │ реалізують різні формули ┌──┴──────────────┐ │ │ PostalShipping CourierShipping (+50 грн) (+150 грн)

Головна ідея: контекст не знає формули розрахунку. Він просто делегує математику об'єкту-стратегії, який йому передали.

2. Розбираємо код по частинах

Частина 1. Інтерфейс IShippingStrategy

Визначає єдиний метод decimal Calculate(decimal total). Будь-який новий спосіб доставки зобов'язаний прийняти суму і повернути вартість доставки.

Частина 2. Конкретні стратегії PostalShipping та CourierShipping

Кожен клас інкапсулює власну математику. Пошта повертає фіксовані 50 грн, а кур'єрська служба — 150 грн.

Частина 3. Контекст OrderCalculator

public void SetStrategy(IShippingStrategy s) => _strategy = s;
public decimal GetTotal(decimal subtotal) => subtotal + _strategy.Calculate(subtotal);

Калькулятор агрегує стратегію через композицію. Метод SetStrategy дозволяє підмінити алгоритм на льоту в будь-яку секунду роботи програми без створення нового калькулятора.

3. Що відбувається в Main() крок за кроком
Крок 1 — Розрахунок за базовою стратегією (Пошта):
Калькулятор ініціалізується поштовою доставкою. Метод GetTotal(1000) повертає: 1000 + 50 = 1050 UAH.
Крок 2 — Підміна стратегії в runtime:
Користувач обирає кур'єра: calculator.SetStrategy(new CourierShipping());.
Крок 3 — Повторний розрахунок:
Той самий калькулятор рахує ту саму суму за новим алгоритмом: 1000 + 150 = 1150 UAH.
4. Strategy проти State: у чому різниця?

UML-діаграми обох патернів ідентичні, але їхній намір протилежний:

  • У Strategy клієнт сам свідомо обирає й підставляє потрібний алгоритм. Стратегії ізольовані одна від одної та ніколи не перемикають контекст самостійно.
  • У State переходи між станами відбуваються автоматично всередині самих класів станів (наприклад, стан NewState сам перемикає контекст у PaidState після оплати).

4. Плюси та мінуси

  • Переваги: швидка заміна алгоритмів прямо під час виконання (runtime); повна ізоляція математики від бізнес-моделі за принципом Open/Closed.
  • Недоліки: клієнтський код зобов'язаний знати різницю між доступними стратегіями, щоб обрати коректну.

Патерн 21: Template Method (Шаблонний метод)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Задає непорушний каркас алгоритму в базовому класі, дозволяючи підкласам перевизначати окремі специфічні кроки без зміни загальної послідовності виконання дій.

2. Коли застосовувати

  • Алгоритм складається з суворої фіксованої послідовності кроків, але окремі етапи мають різні варіації для різних типів файлів або форматів.
  • Потрібно усунути дублювання спільного коду скелета алгоритму (принцип DRY).
Приклади у .NET: Стандартний патерн звільнення некерованих ресурсів Dispose(bool disposing) у базових типах .NET BCL.

3. Реалізація на C#

using System;

// Base class defining the algorithm template
public abstract class DataExporter
{
    // The Template Method defining the step execution skeleton
    public void Export()
    {
        ReadData();
        FormatData();
        Save();
    }

    private void ReadData() => Console.WriteLine("Reading data from database...");

    protected abstract void FormatData();

    protected virtual void Save() => Console.WriteLine("Saving by default...");
}

// Concrete subclass overriding only the specific formatting step
public class PdfExporter : DataExporter
{
    protected override void FormatData() => Console.WriteLine("Formatting data to PDF.");
}

public class Program
{
    public static void Main(string[] args)
    {
        Console.WriteLine("--- PDF Export Execution ---");
        DataExporter exporter = new PdfExporter();

        // Calling the template method
        exporter.Export();
    }
}

/* Результат виконання: **************************************/

--- PDF Export Execution ---
Reading data from database...
Formatting data to PDF.
Saving by default...

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви інструкцію зі збирання шафи IKEA. В інструкції прописано залізобетонний порядок: 1. Розпакувати коробку → 2. Зібрати зовнішній каркас → 3. Вставити внутрішні полиці → 4. Прикрутити дверцята. Не можна прикручувати дверцята до того, як зібрано каркас. Але крок 3 (полиці) може варіюватися: ти можеш поставити скляні полиці або дерев'яні. Загальний скелет алгоритму зафіксовано намертво, а варіативність дозволена лише в призначених для цього кроках.

1. Як влаштований код
DataExporter (Базовий клас) ├── Export() ──► ШАБЛОННИЙ МЕТОД (1. ReadData -> 2. FormatData -> 3. Save) ├── ReadData() ──► private: загальний крок, однаковий для всіх ├── abstract FormatData() ──► ДІРКА В КАРКАСІ: підклас зобов'язаний реалізувати └── virtual Save() ──► ХУК (Hook): поведінка за замовчуванням ▲ │ успадковує PdfExporter (Нащадок: перевизначає ЛИШЕ FormatData())

Головна ідея: базовий клас керує нащадком, а не навпаки (Голлівудський принцип: «Не дзвоніть нам, ми самі вам зателефонуємо»).

2. Розбираємо код по частинах

Частина 1. Шаблонний метод Export()

public void Export()
{
    ReadData();
    FormatData();
    Save();
}

Цей метод невіртуальний. Клієнтський код не може змінити порядок рядків: спочатку читання, потім форматування, потім збереження.

Частина 2. Три типи методів усередині шаблону

  • private void ReadData(): Жорстка логіка, закрита від підкласів. Зчитування з бази для всіх однакове.
  • protected abstract void FormatData(): Абстрактний метод. Базовий клас каже: «Я знаю, ЩО треба відформатувати, але ЯК форматувати у PDF чи Excel — вирішує підклас».
  • protected virtual void Save(): Хук за замовчуванням. Нащадок може перевизначити його, якщо хоче, або залишити як є.
3. Що відбувається в Main() крок за кроком
Крок 1 — Створення екземпляра:
Ми створюємо new PdfExporter() під базовим типом DataExporter.
Крок 2 — Виклик шаблонного методу:
Ми викликаємо лише один метод: exporter.Export();.
Крок 3 — Послідовне проходження кроків:
1. Базовий клас зчитує дані: Reading data from database....
2. Базовий клас викликає віртуальний FormatData() нащадка: Formatting data to PDF..
3. Базовий клас зберігає файл дефолтним способом: Saving by default....
4. Template Method проти Strategy: спадкування чи композиція?
  • Template Method: використовує успадкування. Алгоритм «зашитий» у клас намертво на етапі компіляції. Підкласи жорстко прив'язані до батька, але ми гарантуємо, що ніхто не порушить черговість етапів.
  • Strategy: використовує композицію через інтерфейси. Алгоритм можна повністю підмінити на льоту прямо під час виконання програми. Сучасна розробка частіше обирає Strategy через гнучкість тестування.

4. Плюси та мінуси

  • Переваги: захищає алгоритм від порушення послідовності кроків; повністю виключає дублювання спільного коду скелета (DRY).
  • Недоліки: жорстка зв'язаність через спадкування (зміна базового класу може зламати нащадків); неможливо підмінити крок у рантаймі.

Патерн 22: Visitor (Відвідувач)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє додавати нові операції до класів, не змінюючи їхній вихідний код, за допомогою механізму подвійної диспетчеризації (Double Dispatch).

2. Коли застосовувати

  • Потрібно виконувати різні непов'язані операції над складною структурою вузлів (синтаксичні дерева компіляторів AST, експорт у різні формати).
  • Ієрархія класів елементів стабільна і рідко змінюється, а нові операції над ними з'являються постійно.
Приклади у .NET: Клас ExpressionVisitor у просторі System.Linq.Expressions (використовується в EF Core для розбору дерев виразів LINQ та їхньої трансляції в SQL).

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Visitor contract
public interface IVisitor
{
    void Visit(Bank b);

    void Visit(Shop s);
}

// 2. Element contract
public interface IPlace
{
    void Accept(IVisitor v);
}

// 3. Concrete Elements
public class Bank : IPlace
{
    public void Accept(IVisitor v) => v.Visit(this);
}

public class Shop : IPlace
{
    public void Accept(IVisitor v) => v.Visit(this);
}

// 4. Concrete Visitor containing operation logic
public class TaxVisitor : IVisitor
{
    public void Visit(Bank b) => Console.WriteLine("Bank tax calculation: 10%");

    public void Visit(Shop s) => Console.WriteLine("Shop tax calculation: 5%");
}

public class Program
{
    public static void Main(string[] args)
    {
        var places = new List<IPlace>
        {
            new Bank(),
            new Shop(),
            new Bank()
        };

        IVisitor taxVisitor = new TaxVisitor();

        Console.WriteLine("--- Tax Calculation Execution ---");
        foreach (var place in places)
        {
            place.Accept(taxVisitor);
        }
    }
}

/* Результат виконання: **************************************/

--- Tax Calculation Execution ---
Bank tax calculation: 10%
Shop tax calculation: 5%
Bank tax calculation: 10%

/*************************************************************/

4. Плюси та мінуси

  • Переваги: легке додавання нових операцій без зміни класів елементів (OCP); централізація спорідненої функціональності в одному відвідувачі (SRP).
  • Недоліки: вкрай важко додавати нові класи елементів в ієрархію, адже це змушує змінювати інтерфейс IVisitor та всі створені класи відвідувачів.

Патерн 23: Interpreter (Інтерпретатор)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Визначає граматику простої спеціалізованої мови та будує деревоподібне представлення виразів (AST) для їхнього послідовного обчислення.

2. Коли застосовувати

  • Потрібно створити простий внутрішній парсер предметно-орієнтованої мови (DSL) для фільтрації складних запитів, логічних правил або калькуляторів формул.
  • Граматика мови проста й компактна.
Приклади у .NET: Клас System.Text.RegularExpressions.Regex (інтерпретатор синтаксису регулярних виразів).

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Expression contract
public interface IExpression
{
    int Interpret(Dictionary<string, int> context);
}

// 2. Terminal expression (number constant)
public class NumberExpression : IExpression
{
    private readonly int _num;

    public NumberExpression(int n) => _num = n;

    public int Interpret(Dictionary<string, int> ctx) => _num;
}

// 3. Non-terminal expression (addition operation)
public class AddExpression : IExpression
{
    private readonly IExpression _left;
    private readonly IExpression _right;

    public AddExpression(IExpression l, IExpression r)
    {
        _left = l;
        _right = r;
    }

    public int Interpret(Dictionary<string, int> ctx) => _left.Interpret(ctx) + _right.Interpret(ctx);
}

class Program
{
    static void Main()
    {
        // AST representing expression: 5 + 10
        IExpression expr = new AddExpression(new NumberExpression(5), new NumberExpression(10));
        Console.WriteLine($"Result: {expr.Interpret(null)}");
    }
}

/* Результат виконання: **************************************/

Result: 15

/*************************************************************/

4. Плюси та мінуси

  • Переваги: легке розширення граматики новими вузлами правил; ідеально для спеціалізованих предметних мов (DSL).
  • Недоліки: при ускладненні граматики дерево класів стає надто громіздким для ручної підтримки.
