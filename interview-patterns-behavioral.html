Патерн 13: Chain of Responsibility (Ланцюжок обов'язків)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє передавати запити послідовно через ланцюжок обробників. Кожен обробник вирішує: обробити запит самостійно, передати його далі наступному чи перервати виконання.

2. Коли застосовувати

  • Запит повинен пройти серію послідовних незалежних перевірок (автентифікація, ліміти запитів Rate Limiting, валідація, кешування).
  • Склад і точний порядок обробників повинні гнучко конфігуруватися під час запуску програми.
Приклади у .NET: Конвеєр Middleware в ASP.NET Core (app.UseAuthentication(), app.UseAuthorization() тощо), ланцюжки DelegatingHandler у HttpClientFactory.

3. Реалізація на C#

using System;

// 1. Request model
public class SupportTicket
{
    public string Description { get; set; }
    public int SeverityLevel { get; set; }

    public SupportTicket(string desc, int level)
    {
        Description = desc;
        SeverityLevel = level;
    }
}

// 2. Base handler defining the chain structure
public abstract class BaseHandler
{
    private BaseHandler _next;

    public BaseHandler SetNext(BaseHandler next)
    {
        _next = next;
        return next;
    }

    public virtual void Handle(SupportTicket ticket)
    {
        if (_next != null)
            _next.Handle(ticket);
        else
            Console.WriteLine($"[!] Unable to handle: {ticket.Description}");
    }
}

// 3. Concrete handler: automated bot
public class BotHandler : BaseHandler
{
    public override void Handle(SupportTicket ticket)
    {
        if (ticket.SeverityLevel == 1)
            Console.WriteLine($"[Bot] Resolved: {ticket.Description}");
        else
            base.Handle(ticket);
    }
}

// 4. Concrete handler: support engineer
public class EngineerHandler : BaseHandler
{
    public override void Handle(SupportTicket ticket)
    {
        if (ticket.SeverityLevel == 2)
            Console.WriteLine($"[Engineer] Fixed bug: {ticket.Description}");
        else
            base.Handle(ticket);
    }
}

class Program
{
    static void Main()
    {
        var bot = new BotHandler();
        var engineer = new EngineerHandler();
        bot.SetNext(engineer);

        bot.Handle(new SupportTicket("Forgot password", 1));
        bot.Handle(new SupportTicket("Database crashed", 2));
    }
}

/* Результат виконання: **************************************/

[Bot] Resolved: Forgot password
[Engineer] Fixed bug: Database crashed

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн будується на зв'язаному списку обробників запиту:

  • Модель запиту SupportTicket: Несе дані про задачу та її рівень складності (SeverityLevel).
  • Базовий обробник BaseHandler: Зберігає посилання на наступну ланку (_next) та реалізує перехід по ланцюжку.
  • Конкретні обробники: BotHandler (вирішує прості тікети рівня 1) та EngineerHandler (вирішує критичні баги рівня 2).
  • Клієнт Program: Формує послідовність зв'язків і надсилає запит лише у вхідну точку ланцюжка.
2. Розбираємо код по частинах

Зв'язування ланок (SetNext):
Метод повертає переданий наступний обробник (return next;), що дозволяє зв'язувати ланцюжки лаконічно: first.SetNext(second).SetNext(third).

Логіка делегування base.Handle(ticket): Якщо поточний обробник не може розв'язати проблему (наприклад, для бота прийшов критичний рівень 2), він викликає базовий метод base.Handle(), який автоматично перенаправляє тікет до _next.

Кінець ланцюжка: Якщо жодна ланка не змогла обробити запит і _next == null, базовий обробник виводить повідомлення про неможливість обробки.

3. Що відбувається в Main() по кроках
Крок 1: Побудова ланцюжка
Створюються bot та engineer. Виклик bot.SetNext(engineer) призначає інженера наступником бота.
Крок 2: Обробка першого тікета (рівень 1)
Викликається bot.Handle("Forgot password", 1). Умова SeverityLevel == 1 істинна, бот закриває питання сам: [Bot] Resolved: Forgot password. Запит далі не йде.
Крок 3: Обробка другого тікета (рівень 2)
Викликається bot.Handle("Database crashed", 2). Бот не вміє лагодити базу і передає тікет через base.Handle() до engineer. Інженер підтверджує рівень 2: [Engineer] Fixed bug: Database crashed.
4. У чому головна користь патерну?

Відправник запиту повністю ізольований від кінцевих виконавців. Можна додавати нові перевірки (наприклад, ManagerHandler) або змінювати черговість фільтрів під час запуску програми без модифікації коду інших обробників.

4. Плюси та мінуси

  • Переваги: послаблює зв'язок між відправником і отримувачами (SRP); дозволяє гнучко налаштовувати конвеєр обробки.
  • Недоліки: якщо ланцюжок налаштовано некоректно, запит може пройти до кінця і залишитися необробленим.

Патерн 14: Command (Команда)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Перетворює запити або операції на окремі самостійні об'єкти. Це дає змогу передавати запити як параметри, ставити їх у чергу, логувати та реалізовувати скасування дій (Undo/Redo).

2. Коли застосовувати

  • Потрібна підтримка відкату змін (Undo) та повтору дій (Redo) у текстових або графічних редакторах, фінансових операціях.
  • Потрібно планувати виконання операцій у часі (фонові черги задач Job Queues).
Приклади у .NET: Інтерфейс ICommand у WPF / .NET MAUI (зв'язування команд із кнопками в MVVM), архітектура CQRS через бібліотеку MediatR.

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Receiver: contains business logic
public class BankAccount
{
    public decimal Balance { get; private set; }

    public void Deposit(decimal amt) => Balance += amt;

    public void Withdraw(decimal amt) => Balance -= amt;
}

// 2. Command interface
public interface ICommand
{
    void Execute();

    void Undo();
}

// 3. Concrete Command
public class DepositCommand : ICommand
{
    private readonly BankAccount _acc;
    private readonly decimal _amt;

    public DepositCommand(BankAccount acc, decimal amt)
    {
        _acc = acc;
        _amt = amt;
    }

    public void Execute() => _acc.Deposit(_amt);

    public void Undo() => _acc.Withdraw(_amt);
}

// 4. Invoker: tracks execution history for undo
public class TransactionManager
{
    private readonly Stack<ICommand> _history = new();

    public void Execute(ICommand cmd)
    {
        cmd.Execute();
        _history.Push(cmd);
    }

    public void Undo()
    {
        if (_history.Count > 0)
            _history.Pop().Undo();
    }
}

class Program
{
    static void Main()
    {
        var acc = new BankAccount();
        var manager = new TransactionManager();

        manager.Execute(new DepositCommand(acc, 500m));
        Console.WriteLine($"Balance: {acc.Balance:C}");

        manager.Undo();
        Console.WriteLine($"Balance after Undo: {acc.Balance:C}");
    }
}

/* Результат виконання: **************************************/

Balance: 500,00 ₴
Balance after Undo: 0,00 ₴

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн складається з чотирьох ключових елементів:

  • Одержувач (Receiver) BankAccount: Знає, як реально змінювати баланс (методи Deposit і Withdraw).
  • Контракт команди ICommand: Оголошує пряму дію Execute() та зворотну дію Undo().
  • Конкретна команда DepositCommand: Зв'язує одержувача з аргументом операції (сума поповнення).
  • Ініціатор (Invoker) TransactionManager: Зберігає стек історії виконання та керує процесом відкату.
2. Розбираємо код по частинах

Інкапсуляція операції: Клас DepositCommand запам'ятовує рахунок та суму в конструкторі. Коли викликається Execute(), команда виконує поповнення. Коли викликається Undo(), команда виконує протилежну операцію — списання тієї самої суми.

Стек історії в TransactionManager:
Використовується структура даних Stack<ICommand> (LIFO — Last In, First Out). При виклику manager.Execute(cmd) команда спочатку виконується, а потім поміщається на вершину стека через _history.Push(cmd).

Метод Undo(): Знімає останню команду з вершини стека через _history.Pop() та викликає її метод Undo(). Завдяки цьому можна реалізувати багаторівневий відкат десятків дій назад.

3. Що відбувається в Main() по кроках
Крок 1: Виконання депозиту
Створюється команда new DepositCommand(acc, 500m) і передається менеджеру. Рахунок збільшується на 500. Консоль виводить: Balance: 500,00 ₴. Команда потрапляє у стек.
Крок 2: Виклик Undo()
Менеджер витягує команду зі стека і викликає її метод Undo(), який списує 500 назад.
Крок 3: Перевірка фінального стану
Баланс знову стає нульовим: Balance after Undo: 0,00 ₴.
4. У чому перевага над прямим викликом методів?

Якби ми викликали acc.Deposit(500) напряму, ми б втратили можливість автоматично скасувати цю дію, зберегти історію в файл або відкласти операцію на ніч для пакетної обробки. Команда перетворює метод на самостійні дані, якими можна маніпулювати як завгодно.

4. Плюси та мінуси

  • Переваги: елегантна підтримка операцій скасування (Undo) і повтору дій (Redo); відокремлення ініціатора виклику від виконавця.
  • Недоліки: розмноження класів команд під кожну окрему бізнес-операцію.

Патерн 15: Iterator (Ітератор)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дає можливість послідовно обходити елементи складної колекції, не розкриваючи її внутрішнього влаштування (масив, дерево, зв'язаний список).

2. Коли застосовувати

  • Потрібно надати клієнту зручний спосіб навігації без надання прямого доступу до внутрішніх структур даних.
  • Потрібно підтримувати кілька різних варіантів обходу однієї колекції (прямий, зворотний, фільтрований).
У .NET: Патерн глибоко інтегрований у мову C# через інтерфейси IEnumerable<T>, IEnumerator<T>, цикл foreach та ключове слово yield return.

3. Реалізація на C#

using System;
using System.Collections;
using System.Collections.Generic;

// Collection supporting custom iteration
public class Playlist : IEnumerable<string>
{
    private readonly List<string> _songs = new();

    public void Add(string song) => _songs.Add(song);

    public IEnumerator<string> GetEnumerator()
    {
        foreach (var s in _songs)
            yield return s;
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();

    public IEnumerable<string> Backwards()
    {
        for (int i = _songs.Count - 1; i >= 0; i--)
            yield return _songs[i];
    }
}

class Program
{
    static void Main()
    {
        var list = new Playlist { "Song 1", "Song 2", "Song 3" };

        foreach (var song in list.Backwards())
        {
            Console.WriteLine(song);
        }
    }
}

/* Результат виконання: **************************************/

Song 3
Song 2
Song 1

/*************************************************************/

4. Плюси та мінуси

  • Переваги: спрощує роботу з колекціями; дозволяє паралельно робити кілька незалежних обходів одних даних.
  • Недоліки: використання для простих масивів може бути надлишковим.

Патерн 16: Mediator (Посередник)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Змушує компоненти взаємодіяти не напряму між собою, а через єдиний об'єкт-посередник. Це перетворює заплутані зв'язки «багато-до-багатьох» ($M \times N$) на прості зв'язки «один-до-багатьох» ($1 \times N$).

2. Коли застосовувати

  • Між класами інтерфейсу або сервісами виникла складна «павутина» взаємних посилань і подій.
  • Потрібно повторно використовувати компоненти форми або бізнес-шару в різних сценаріях, не прив'язуючи їх намертво до сусідів.
Приклади у .NET: Бібліотека MediatR для розділення контролерів API та обробників доменної логіки за принципом CQRS.

3. Реалізація на C#

using System;

// 1. Mediator contract
public interface IMediator
{
    void Notify(object sender, string ev);
}

// 2. Colleague 1: Button
public class Button
{
    private IMediator _m;
    public bool IsEnabled { get; set; }

    public void SetMediator(IMediator m) => _m = m;
}

// 3. Colleague 2: Checkbox
public class Checkbox
{
    private IMediator _m;
    public bool Checked { get; private set; }

    public void SetMediator(IMediator m) => _m = m;

    public void Toggle()
    {
        Checked = !Checked;
        _m?.Notify(this, "toggle");
    }
}

// 4. Concrete Mediator coordinating UI components
public class DialogMediator : IMediator
{
    private readonly Button _btn;
    private readonly Checkbox _cb;

    public DialogMediator(Button btn, Checkbox cb)
    {
        _btn = btn;
        _btn.SetMediator(this);
        _cb = cb;
        _cb.SetMediator(this);
    }

    public void Notify(object sender, string ev)
    {
        if (ev == "toggle")
            _btn.IsEnabled = _cb.Checked;
    }
}

class Program
{
    static void Main()
    {
        var button = new Button();
        var checkbox = new Checkbox();
        var mediator = new DialogMediator(button, checkbox);

        Console.WriteLine("Initial state:");
        Console.WriteLine($"Checkbox Checked: {checkbox.Checked}");
        Console.WriteLine($"Button IsEnabled: {button.IsEnabled}\n");

        Console.WriteLine("Toggle checkbox (user accepts terms):");
        checkbox.Toggle();
        Console.WriteLine($"Checkbox Checked: {checkbox.Checked}");
        Console.WriteLine($"Button IsEnabled: {button.IsEnabled}\n");

        Console.WriteLine("Toggle checkbox again:");
        checkbox.Toggle();
        Console.WriteLine($"Checkbox Checked: {checkbox.Checked}");
        Console.WriteLine($"Button IsEnabled: {button.IsEnabled}");
    }
}

/* Результат виконання: **************************************/

Initial state:
Checkbox Checked: False
Button IsEnabled: False

Toggle checkbox (user accepts terms):
Checkbox Checked: True
Button IsEnabled: True

Toggle checkbox again:
Checkbox Checked: False
Button IsEnabled: False

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн вибудовує зіркоподібну топологію комунікації:

  • Контракт посередника IMediator: Метод Notify(object sender, string ev), через який надсилаються всі повідомлення про події.
  • Колеги (Colleagues): Button і Checkbox. Вони взагалі не знають про існування один одного! Вони мають посилання лише на інтерфейс IMediator.
  • Конкретний посередник DialogMediator: Зберігає прямі посилання на кнопку й чекбокс та містить усю логіку їхньої взаємодії.
2. Розбираємо код по частинах

Ізоляція компонентів: У класі Checkbox у методі Toggle() немає рядка _button.IsEnabled = true. Чекбокс лише сповіщає: «у мене відбулася подія "toggle"» через _m?.Notify(this, "toggle").

Централізована координація: Метод DialogMediator.Notify аналізує, хто надіслав повідомлення і яка саме подія відбулася. Якщо це перемикання чекбокса, він встановлює доступність кнопки: _btn.IsEnabled = _cb.Checked.

3. Що відбувається в Main() по кроках
Крок 1: Початковий стан
Кнопка вимкнена (IsEnabled = false), чекбокс не позначений (Checked = false).
Крок 2: Перше перемикання (Toggle)
Користувач клікає чекбокс. Чекбокс змінює Checked на true і шле нотифікацію в DialogMediator. Посередник перехоплює подію та вмикає кнопку: Button IsEnabled: True.
Крок 3: Повторне перемикання
Користувач знімає галочку. Чекбокс інформує посередника, який синхронно вимикає кнопку: Button IsEnabled: False.
4. У чому саме полягає патерн Mediator?

Без посередника форма з 10 елементами (кнопки, списки, поля вводу, чекбокси) перетворюється на хаос: кожен елемент повинен підписуватися на події інших дев'яти. Посередник забирає всю координаційну логіку на себе, роблячи UI-компоненти максимально простими та перевикористовуваними.

4. Плюси та мінуси

  • Переваги: усуває хаос взаємних посилань (SRP); полегшує повторне використання окремих класів.
  • Недоліки: з часом клас посередника може надмірно розростися й перетворитися на важкопідтримуваний God Object.

Патерн 17: Memento (Знімок)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє фіксувати та відновлювати минулий стан об'єкта, не порушуючи його інкапсуляцію та не розкриваючи приватні поля назовні.

2. Коли застосовувати

  • Потрібно зберігати контрольні точки (checkpoints) гри чи документа для подальшого повернення назад.
  • Прямий доступ до полів об'єкта зламав би інкапсуляцію або внутрішні бізнес-правила.
Приклади у .NET: Механізм відстеження змін у EF Core: EntityEntry.OriginalValues фіксує початковий знімок значень властивостей при зчитуванні з бази даних.

3. Реалізація на C#

using System;
using System.Collections.Generic;

// Marker interface for snapshots
public interface IMemento { }

// Originator: stateful object
public class Editor
{
    private string _text = "";

    public void Type(string words) => _text += words;

    public string Text => _text;

    public IMemento Save() => new Memento(_text);

    public void Restore(IMemento m)
    {
        if (m is Memento s)
            _text = s.State;
    }

    // Private inner snapshot class protecting encapsulation
    private class Memento : IMemento
    {
        public string State { get; }

        public Memento(string state) => State = state;
    }
}

class Program
{
    static void Main()
    {
        var editor = new Editor();
        var history = new Stack<IMemento>();

        editor.Type("Version 1");
        history.Push(editor.Save());

        editor.Type(" + error text");
        editor.Restore(history.Pop());
        Console.WriteLine(editor.Text);
    }
}

/* Результат виконання: **************************************/

Version 1

/*************************************************************/

4. Плюси та мінуси

  • Переваги: надійне збереження стану без розкриття приватних полів класу; простий інтерфейс відновлення.
  • Недоліки: часте створення знімків важких об'єктів створює значне навантаження на оперативну пам'ять.

Патерн 18: Observer (Спостерігач)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Створює механізм підписки, який дає змогу об'єктам автоматично отримувати сповіщення про зміну стану іншого суб'єкта, за яким вони спостерігають.

2. Коли застосовувати

  • Зміна стану одного компонента вимагає синхронного оновлення багатьох інших, набір яких заздалегідь невідомий.
  • Побудова реактивних інтерфейсів (UI), моделей Publisher-Subscriber або обробки подій у реальному часі.
Приклади у .NET: Ключове слово event та стандартні делегати C#, інтерфейс INotifyPropertyChanged у WPF/MAUI, інтерфейси IObservable<T> та IObserver<T> у бібліотеці Reactive Extensions (Rx.NET).

3. Реалізація на C#

using System;

// Subject: raises an event when its state changes
public class Product
{
    private decimal _price;

    // Idiomatic C# event-based Observer
    public event Action<decimal> PriceChanged;

    public decimal Price
    {
        get => _price;
        set
        {
            if (_price != value)
            {
                _price = value;
                PriceChanged?.Invoke(_price);
            }
        }
    }
}

class Program
{
    static void Main()
    {
        var product = new Product();

        // Subscribing to notifications
        product.PriceChanged += price => Console.WriteLine($"New price alert: {price:C}");

        // Modifying state triggers observer callback
        product.Price = 120m;
    }
}

/* Результат виконання: **************************************/

New price alert: 120,00 ₴

(Формат валюти залежить від системної локалі, наприклад: 120,00 ₴ або $120.00)

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

У C# патерн Observer найчастіше реалізують ідіоматично за допомогою делегатів та подій:

  • Суб'єкт (Subject) Product: Джерело подій. Містить стан (_price) та оголошує подію event Action<decimal> PriceChanged.
  • Спостерігач (Observer): Будь-який метод або лямбда-функція, сигнатура якої збігається з Action<decimal>.
  • Клієнт Program: Підписує спостерігача через оператор += та змінює стан суб'єкта.
2. Розбираємо код по частинах

Ключове слово event: На відміну від звичайного публічного поля-делегата, конструкція event забороняє зовнішньому коду скидати список підписників через = null або штучно викликати подію ззовні. Зовнішній код може лише підписатися (+=) або відписатися (-=).

Сеттер властивості Price:
1. Спочатку перевіряє умову if (_price != value), щоб уникнути спаму нотифікацій, якщо ціна фактично не змінилася.
2. Виклик PriceChanged?.Invoke(_price) використовує оператор безпечного доступу (Null-conditional operator ?.). Якщо підписників немає, подія просто не викликається без генерації NullReferenceException.

3. Що відбувається в Main() по кроках
Крок 1: Підписка спостерігача
Код підписує лямбда-вираз на подію: product.PriceChanged += price => .... Список викликів делегата тепер містить один обробник.
Крок 2: Зміна стану
Присвоєння product.Price = 120m запускає сеттер властивості.
Крок 3: Оповіщення
Сеттер викликає PriceChanged?.Invoke(120m). Спостерігач миттєво реагує та друкує в консоль: New price alert: 120,00 ₴.
4. Пастка на співбесіді: «Lapsed Listener Problem»

Коли короткоживучий об'єкт підписується на подію довгоживучого сервісу через +=, довгоживучий об'єкт утримує сильне посилання (Strong Reference) на підписника через делегат. Якщо забути відписатися через -= або IDisposable, збирач сміття (GC) ніколи не звільнить пам'ять підписника, що призводить до непомітних, але критичних витоків пам'яті.

4. Плюси та мінуси

  • Переваги: слабке зв'язування суб'єкта з одержувачами; можливість динамічно підключати та відключати підписників у рантаймі.
  • Недоліки: ризик витоку пам'яті (Lapsed Listener); порядок сповіщення підписників зазвичай не гарантується.

Патерн 19: State (Стан)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє об'єкту кардинально змінювати свою поведінку при зміні внутрішнього стану, створюючи ілюзію того, що об'єкт змінив свій клас, та усуваючи громіздкі блоки умов switch/case.

2. Коли застосовувати

  • Поведінка сутності залежить від її поточного бізнес-статусу (наприклад, Замовлення: Нове → Оплачене → Відправлене).
  • Методи класу перевантажені десятками розгалужень if (status == 1) ... else if (status == 2).
Приклади у .NET: Бібліотека Stateless для наочного опису скінченних автоматів (State Machines) у чистому C# коді.

3. Реалізація на C#

using System;

// 1. State contract
public interface IOrderState
{
    void Pay(OrderContext ctx);

    void Ship(OrderContext ctx);
}

// 2. Context holding the active state
public class OrderContext
{
    private IOrderState _state = new NewState();

    public void SetState(IOrderState state) => _state = state;

    public void Pay() => _state.Pay(this);

    public void Ship() => _state.Ship(this);
}

// 3. Concrete State: New
public class NewState : IOrderState
{
    public void Pay(OrderContext ctx)
    {
        Console.WriteLine("Order paid successfully.");
        ctx.SetState(new PaidState());
    }

    public void Ship(OrderContext ctx) => Console.WriteLine("Error: Cannot ship an unpaid order!");
}

// 4. Concrete State: Paid
public class PaidState : IOrderState
{
    public void Pay(OrderContext ctx) => Console.WriteLine("Warning: Already paid.");

    public void Ship(OrderContext ctx) => Console.WriteLine("Order shipped via courier.");
}

class Program
{
    static void Main()
    {
        var order = new OrderContext();

        Console.WriteLine("1. Attempting to ship new order:");
        order.Ship();

        Console.WriteLine("\n2. Paying for the order:");
        order.Pay();

        Console.WriteLine("\n3. Attempting to pay again:");
        order.Pay();

        Console.WriteLine("\n4. Shipping the paid order:");
        order.Ship();
    }
}

/* Результат виконання: **************************************/

1. Attempting to ship new order:
Error: Cannot ship an unpaid order!

2. Paying for the order:
Order paid successfully.

3. Attempting to pay again:
Warning: Already paid.

4. Shipping the paid order:
Order shipped via courier.

/*************************************************************/

4. Плюси та мінуси

  • Переваги: прибирає спагеті-код складних умовних операторів; ізолює поведінку кожного стану в окремий клас (SRP).
  • Недоліки: може бути надлишковим ускладненням для простих сутностей із двома станами.

Патерн 20: Strategy (Стратегія)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Визначає сімейство взаємозамінних алгоритмів, інкапсулює кожен із них в окремий клас і дає змогу підміняти алгоритми на льоту під час роботи програми.

2. Коли застосовувати

  • Потрібно використовувати різні варіації розрахунків (тарифи доставки, розрахунок податків, алгоритми стиснення або сортування).
  • Необхідно підміняти алгоритм у реальному часі залежно від вибору клієнта без зміни класу, який проводить операцію.
Приклади у .NET: Інтерфейси IComparer<T> та IEqualityComparer<T> у методах LINQ OrderBy та Array.Sort.

3. Реалізація на C#

using System;

// 1. Strategy contract
public interface IShippingStrategy
{
    decimal Calculate(decimal total);
}

// 2. Concrete Strategy: Postal delivery
public class PostalShipping : IShippingStrategy
{
    public decimal Calculate(decimal total) => 50m;
}

// 3. Concrete Strategy: Courier delivery
public class CourierShipping : IShippingStrategy
{
    public decimal Calculate(decimal total) => 150m;
}

// 4. Context using strategy via composition
public class OrderCalculator
{
    private IShippingStrategy _strategy;

    public OrderCalculator(IShippingStrategy s) => _strategy = s;

    public void SetStrategy(IShippingStrategy s) => _strategy = s;

    public decimal GetTotal(decimal subtotal) => subtotal + _strategy.Calculate(subtotal);
}

class Program
{
    static void Main()
    {
        decimal subtotal = 1000m;
        Console.WriteLine($"Base order amount: {subtotal} UAH\n");

        var calculator = new OrderCalculator(new PostalShipping());
        decimal postalTotal = calculator.GetTotal(subtotal);
        Console.WriteLine($"Total with postal shipping: {postalTotal} UAH");

        calculator.SetStrategy(new CourierShipping());
        decimal courierTotal = calculator.GetTotal(subtotal);
        Console.WriteLine($"Total with courier shipping: {courierTotal} UAH");
    }
}

/* Результат виконання: **************************************/

Base order amount: 1000 UAH

Total with postal shipping: 1050 UAH
Total with courier shipping: 1150 UAH

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн Strategy реалізує принцип композиції замість успадкування:

  • Контракт стратегії IShippingStrategy: Описує єдиний метод decimal Calculate(decimal total).
  • Конкретні стратегії: PostalShipping (фіксований тариф 50 грн) та CourierShipping (тариф 150 грн).
  • Контекст OrderCalculator: Зберігає посилання на інтерфейс стратегії та викликає її для розрахунку загальної суми.
  • Клієнт Program: Обирає початкову стратегію та може будь-якої миті змінити її на іншу через SetStrategy().
2. Розбираємо код по частинах

Гнучкість через SetStrategy: Контекст не прив'язується до конкретної формули доставки. Він лише комбінує суму замовлення з результатом розрахунку поточної стратегії: subtotal + _strategy.Calculate(subtotal).

Принцип відкритості/закритості (OCP): Якщо завтра з'явиться експрес-доставка дроном за 300 грн, ми просто створимо клас DroneShipping : IShippingStrategy. Клас OrderCalculator не зміниться ні на символ.

3. Що відбувається в Main() по кроках
Крок 1: Розрахунок за базовою стратегією
Калькулятор ініціалізується стратегією PostalShipping. Для замовлення на 1000 грн метод GetTotal() повертає: 1000 + 50 = 1050 UAH.
Крок 2: Зміна стратегії на льоту
Клієнт змінює алгоритм викликом calculator.SetStrategy(new CourierShipping()). Об'єкт калькулятора залишається тим самим.
Крок 3: Повторний розрахунок
Наступний виклик GetTotal() звертається до нового алгоритму: 1000 + 150 = 1150 UAH.
4. Strategy проти State: у чому різниця?

Хоча UML-діаграми патернів однакові:

  • У Strategy клієнт сам передає та перемикає стратегії. Стратегії нічого не знають про сусідів і не перемикають себе.
  • У State переходи між станами відбуваються автоматично всередині самих станів або контексту (наприклад, стан New сам перемикає контекст у Paid після успішної оплати).

4. Плюси та мінуси

  • Переваги: швидка підміна алгоритмів під час виконання (runtime); повна ізоляція математики від бізнес-моделі (OCP).
  • Недоліки: клієнтський код повинен знати різницю між доступними стратегіями, щоб правильно обрати потрібну.

Патерн 21: Template Method (Шаблонний метод)*

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Задає жорсткий каркас алгоритму в базовому класі, дозволяючи підкласам перевизначати окремі кроки без зміни загальної структури алгоритму.

2. Коли застосовувати

  • Алгоритм складається з чіткої фіксованої черговості кроків, але деякі з них мають специфічні варіації в різних нащадках.
  • Потрібно усунути дублювання однакового каркасного коду (принцип DRY).
Приклади у .NET: Стандартний патерн звільнення некерованих ресурсів Dispose(bool disposing) у базових класах .NET BCL.

3. Реалізація на C#

using System;

// Base class defining the algorithm template
public abstract class DataExporter
{
    // The Template Method defining the step execution skeleton
    public void Export()
    {
        ReadData();
        FormatData();
        Save();
    }

    private void ReadData() => Console.WriteLine("Reading data from database...");

    protected abstract void FormatData();

    protected virtual void Save() => Console.WriteLine("Saving by default...");
}

// Concrete subclass overriding only the specific formatting step
public class PdfExporter : DataExporter
{
    protected override void FormatData() => Console.WriteLine("Formatting data to PDF.");
}

public class Program
{
    public static void Main(string[] args)
    {
        Console.WriteLine("--- PDF Export Execution ---");
        DataExporter exporter = new PdfExporter();

        // Calling the template method
        exporter.Export();
    }
}

/* Результат виконання: **************************************/

--- PDF Export Execution ---
Reading data from database...
Formatting data to PDF.
Saving by default...

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн будується на розподілі рівнів абстракції всередині ієрархії спадкування:

  • Базовий клас DataExporter: Містить невіртуальний шаблонний метод Export(), який задає непорушний порядок дій.
  • Незмінні приватні кроки (ReadData): Загальна логіка, однакова для всіх форматів.
  • Абстрактні кроки (FormatData): Обов'язкові для реалізації в нащадках специфічні операції.
  • Віртуальні кроки (Save — хуки): Надають стандартну поведінку за замовчуванням, яку за потреби можна перекрити.
2. Розбираємо код по частинах

Шаблонний метод Export():

public void Export()
{
    ReadData();
    FormatData();
    Save();
}

Клієнтський код не викликає окремо ReadData() або Save(). Він викликає лише метод Export(), завдяки чому неможливо випадково зберегти дані до їхнього зчитування чи форматування.

Голлівудський принцип («Не дзвоніть нам, ми самі вам зателефонуємо»): Базовий клас сам викликає методи нащадка FormatData() у потрібний для себе момент часу, керуючи потоком виконання зверху-вниз.

3. Що відбувається в Main() по кроках
Крок 1: Створення екземпляра
Створюється new PdfExporter() під базовим типом DataExporter.
Крок 2: Виклик шаблонного методу
Викликається exporter.Export().
Крок 3: Послідовне виконання кроків
1. Виконується приватний метод бази: Reading data from database....
2. Викликається поліморфний метод нащадка FormatData(): Formatting data to PDF..
3. Виконується віртуальний метод збереження: Saving by default....
4. Template Method проти Strategy: спадкування проти композиції

На технічних співбесідах часто запитують: чому в сучасній архітектурі Strategy обирають частіше?

  • Template Method прив'язаний до успадкування: ви не можете змінити крок алгоритму під час виконання (runtime), а підкласи жорстко залежать від коду батьківського класу.
  • Strategy базується на композиції інтерфейсів, що дає змогу легко підміняти реалізації в рантаймі та тестувати компоненти ізольовано.

4. Плюси та мінуси

  • Переваги: усуває дублювання спільного коду каркаса (DRY); суворо фіксує послідовність кроків бізнес-алгоритму.
  • Недоліки: жорстка зв'язаність класів через механізм спадкування; неможливість зміни поведінки в рантаймі.

Патерн 22: Visitor (Відвідувач)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє додавати нові операції до класів, не змінюючи їхній вихідний код, за допомогою механізму подвійної диспетчеризації (Double Dispatch).

2. Коли застосовувати

  • Потрібно виконувати різні непов'язані між собою операції над складною структурою вузлів (наприклад, синтаксичні дерева компіляторів AST, експорт у різні формати).
  • Ієрархія класів елементів стабільна і рідко змінюється, а нові операції над ними додаються регулярно.
Приклади у .NET: Клас ExpressionVisitor у просторі System.Linq.Expressions (застосовується в EF Core для парсингу дерев виразів LINQ та їхньої трансляції в SQL).

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Visitor contract
public interface IVisitor
{
    void Visit(Bank b);

    void Visit(Shop s);
}

// 2. Element contract
public interface IPlace
{
    void Accept(IVisitor v);
}

// 3. Concrete Elements
public class Bank : IPlace
{
    public void Accept(IVisitor v) => v.Visit(this);
}

public class Shop : IPlace
{
    public void Accept(IVisitor v) => v.Visit(this);
}

// 4. Concrete Visitor containing operation logic
public class TaxVisitor : IVisitor
{
    public void Visit(Bank b) => Console.WriteLine("Bank tax calculation: 10%");

    public void Visit(Shop s) => Console.WriteLine("Shop tax calculation: 5%");
}

public class Program
{
    public static void Main(string[] args)
    {
        var places = new List<IPlace>
        {
            new Bank(),
            new Shop(),
            new Bank()
        };

        IVisitor taxVisitor = new TaxVisitor();

        Console.WriteLine("--- Tax Calculation Execution ---");
        foreach (var place in places)
        {
            place.Accept(taxVisitor);
        }
    }
}

/* Результат виконання: **************************************/

--- Tax Calculation Execution ---
Bank tax calculation: 10%
Shop tax calculation: 5%
Bank tax calculation: 10%

/*************************************************************/

4. Плюси та мінуси

  • Переваги: легке додавання нових операцій без переписування класів елементів (OCP); централізація спорідненої логіки в одному відвідувачі (SRP).
  • Недоліки: надзвичайно важко додавати нові класи елементів в ієрархію, адже це змушує оновлювати контракт IVisitor та всіх його реалізацій.

Патерн 23: Interpreter (Інтерпретатор)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Визначає граматику простої спеціалізованої мови та будує деревоподібне представлення виразів (AST) для їхнього послідовного обчислення.

2. Коли застосовувати

  • Потрібно створити простий внутрішній рушій предметно-орієнтованої мови (DSL) для фільтрації запитів, логічних правил або калькуляторів виразів.
  • Граматика мови проста і компактна.
Приклади у .NET: Клас System.Text.RegularExpressions.Regex (інтерпретатор синтаксису регулярних виразів).

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Expression contract
public interface IExpression
{
    int Interpret(Dictionary<string, int> context);
}

// 2. Terminal expression (number constant)
public class NumberExpression : IExpression
{
    private readonly int _num;

    public NumberExpression(int n) => _num = n;

    public int Interpret(Dictionary<string, int> ctx) => _num;
}

// 3. Non-terminal expression (addition operation)
public class AddExpression : IExpression
{
    private readonly IExpression _left;
    private readonly IExpression _right;

    public AddExpression(IExpression l, IExpression r)
    {
        _left = l;
        _right = r;
    }

    public int Interpret(Dictionary<string, int> ctx) => _left.Interpret(ctx) + _right.Interpret(ctx);
}

class Program
{
    static void Main()
    {
        // AST representing expression: 5 + 10
        IExpression expr = new AddExpression(new NumberExpression(5), new NumberExpression(10));
        Console.WriteLine($"Result: {expr.Interpret(null)}");
    }
}

/* Результат виконання: **************************************/

Result: 15

/*************************************************************/

4. Плюси та мінуси

  • Переваги: легке розширення граматики новими правилами-вузлами; чудово підходить для створення предметно-орієнтованих мов (DSL).
  • Недоліки: зі зростанням граматики дерево класів стає занадто складним для підтримки.
