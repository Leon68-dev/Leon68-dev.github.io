1. Коваріантність та контраваріантність у Generics: що це, навіщо потрібні `out` та `in`? Чому не працює для Value Types?

↑ До змісту
Коротка суть: Варіантність дозволяє приводити дженерик-інтерфейси/делегати на основі спорідненості їх типів. `out` (коваріантність) — тип повертається (більш специфічний тип до базового). `in` (контраваріантність) — тип приймається як аргумент. Працює ТІЛЬКИ для Reference Types!

Розгорнута відповідь:

За замовчуванням узагальнення в C# є інваріантними (наприклад, List<string> не можна привести до List<object>, інакше ви змогли б додати туди число і поламати безпеку типів).

  • Коваріантність (out T): Дозволяє використати тип-нащадок замість батьківського типу. Тип T може бути ТІЛЬКИ результатом методів: 
    IEnumerable<string> strings = new List<string>();
IEnumerable<object> objects = strings; // Працює, бо IEnumerable<out T>
  • Контраваріантність (in T): Дозволяє використати батьківський тип замість нащадка. Тип T може бути ТІЛЬКИ вхідним аргументом: 
    Action<object> actObject = obj => Console.WriteLine(obj);
Action<string> actString = actObject; // Працює, бо Action<in T>
  • Чому НЕ працює з Value Types: Структури мають різний бінарний розмір у пам'яті (наприклад, int — 4 байти, а double — 8 байт). Посилальні типи завжди мають розмір 4 або 8 байт (покажчик), тому CLR може безпечно працювати з ними на рівні масивів та регістрів без конвертації/боксингу.

2. Що таке замикання (Closures) в C#? Як компілятор реалізує його під капотом (Display Class)?

↑ До змісту
Коротка суть: Замикання — це здатність лямбда-функції «запам'ятовувати» змінні зі своєї зовнішньої області видимості. Компілятор створює невидимий службовий клас у купі (Display Class) і робить захоплені змінні його полями.

Розгорнута відповідь:

Коли ви пишете:

int factor = 10;
Func<int, int> multiplier = x => x * factor;

Компілятор Roslyn генерує спеціальний прихований клас:

// Те, що робить компілятор "під капотом":
[CompilerGenerated]
private sealed class <>c__DisplayClass0_0
{
    public int factor; // Локальна змінна перетворилася на поле класу в Купі!
    public int <Main>b__0(int x) => x * factor;
}

Небезпеки та пастки:

  • Приховані алокації: Кожне замикання створює екземпляр класу в Heap, збільшуючи навантаження на Garbage Collector.
  • Захоплення змінної в циклі (історичний баг у for): Якщо лямбда захоплює лічильник for (int i = 0; i < 5; i++), всі лямбди посилаються на одне й те саме спільне поле displayClass.i, тому в кінці виконання всі виведуть 5. (У циклі foreach це виправили в C# 5).

3. Як влаштований `yield return` під капотом? Скінченний автомат (State Machine).

↑ До змісту
Коротка суть: Компілятор генерує внутрішній клас, що реалізує `IEnumerator` зі switch-case автоматом у методі `MoveNext()`, зберігаючи поточну точку виконання та локальні змінні.

Розгорнута відповідь:

Оператор yield return дозволяє створювати ітератори без попереднього виділення колекції в пам'яті.

  • Скінченний автомат: Компілятор перетворює метод на клас зі станами (state = 0, 1, 2... -1).
  • Кожен виклик yield return value:
    1. Присвоює поточне значення властивості Current.
    2. Змінює внутрішній _state на наступний крок.
    3. Повертає true з методу MoveNext().
  • Наступний виклик MoveNext() заходить у метод і через switch (_state) миттєво стрибає на той рядок, де зупинився минулого разу.
  • Підступний нюанс: Якщо перед першим yield return кинути виняток валідації аргументів (if (arg == null) throw ...), цей виняток НЕ викинеться в момент виклику методу! Він викинеться лише тоді, коли хтось уперше викличе foreach або MoveNext().

4. Що таке `Span`, `ReadOnlySpan` та `Memory`? Чому `Span` це `ref struct` і де його не можна використовувати?

↑ До змісту
Коротка суть: `Span` — швидкий покажчик на неперервний блок пам'яті без алокацій (zero-allocation). Це `ref struct`, тому він живе ТІЛЬКИ на стеку. `Memory` — обгортка над пам'яттю, яка може жити в Купі (Heap).

Розгорнута відповідь:

Span<T> уніфікує доступ до пам'яті: масивів у купі, буферів на стеку (через stackalloc) або пам'яті, виділеної через некерований код (P/Invoke). Забезпечує нарізку (Slicing) без створення копій у пам'яті.

string str = "12345";
ReadOnlySpan<char> span = str.AsSpan(0, 3); // "123" БЕЗ створення нового string у купі!
int num = int.Parse(span);

Чому Span<T> є ref struct:
Він містить керований покажчик (by-ref pointer). Щоб уникнути ситуації, коли потік або GC втратить покажчик, ref struct гарантовано розміщується виключно на стеку.

Де Span<T> ЗАБОРОНЕНО використовувати:

  • Не може бути полем звичайного класу (бо клас живе в купі).
  • Не можна використовувати всередині асинхронних методів (async / await) між точками зупинки (бо асинхронна стан-машина є класом у купі).
  • Не можна пакувати (Boxing в object).
  • Не може бути типом аргументу в дженериках (List<Span<int>> — помилка компіляції).

Рішення для асинхронного коду: Використовувати Memory<T> / ReadOnlyMemory<T> — це звичайні структури, які можуть лежати в купі та перетворюватися на Span безпосередньо перед синхронною обробкою.

5. Сучасний Pattern Matching у C#: які види патернів існують?

↑ До змісту
Коротка суть: Потужний інструмент перевірки форми та значень об'єктів без громіздких кастів. Включає type patterns, relational, logical (and/or/not), property та positional patterns.

Розгорнута відповідь:

// Switch-вираз із різними патернами:
decimal GetDeliveryCost(object order) => order switch
{
    // Property Pattern + Relational Pattern (>=, <=)
    Order { TotalPrice: >= 1000m } => 0m, 

    // Logical Patterns (and / or / not)
    Order { WeightKg: > 10 and <= 30 } => 150m,

    // Type Pattern з перевіркою властивості
    ExpressOrder eo when eo.IsUrgent => 300m,

    // Positional Pattern (через Deconstruct у record/туплах)
    (string city, int dist) when city == "Київ" => 50m,

    null => throw new ArgumentNullException(nameof(order)),
    _ => 100m // Discard pattern (default)
};

6. Як детально працює Garbage Collector? Покоління 0, 1, 2, LOH та POH. Пороги розмірів.

↑ До змісту
Коротка суть: GC працює на основі трасування графів від GC Roots. Покоління 0/1/2 дозволяють швидко чистити короткоживучі об'єкти. LOH (від 85 000 байт) не дефрагментується за замовчуванням. POH (.NET 5+) тримає закріплені об'єкти.

Розгорнута відповідь:

Гіпотеза поколінь: Чим новіший об'єкт, тим коротший його час життя. Чим довше об'єкт живе, тим менша ймовірність, що він помре найближчим часом.

  • Gen 0: Сюди потрапляють абсолютно всі нові малі об'єкти. Збір відбувається найчастіше і за мілісекунди. Ті, хто вижив, переходять у Gen 1.
  • Gen 1: Буфер між новими та старими об'єктами.
  • Gen 2: Довгожителі (статичні змінні, кеші, синглтони). Збір сміття тут називається Full GC, він зупиняє потоки додатку (Stop-The-World) на відчутніший час.
  • LOH (Large Object Heap): Об'єкти розміром від 85 000 байт (та великі масиви чисел від 1000 елементів) створюються одразу тут, оминаючи Gen 0. Особливість: через дорожнечу копіювання пам'яті LOH за замовчуванням не дефрагментується, що може призводити до фрагментації віртуальної пам'яті.
  • POH (Pinned Object Heap): З'явився в .NET 5. Окремий пул для об'єктів, закріплених у пам'яті через GCHandle.Alloc(..., GCHandleType.Pinned) (наприклад, для передачі в C++ бібліотеки), щоб GC не дефрагментував решту звичайної купи.

7. У чому різниця між Workstation GC та Server GC? Що таке Background GC?

↑ До змісту
Коротка суть: Workstation GC оптимізований під швидкий відгук користувацького інтерфейсу (1 куча). Server GC виділяє окрему купу та окремий потік GC на кожне ядро CPU для максимальної пропускної здатності серверів.

Порівняння режимів:

  • Workstation GC: Призначений для настільних програм (WPF, WinForms, консоль). Має одну купу. Пріоритет — мінімізувати час пауз, щоб UI не "зависав".
  • Server GC: Стандартний режим для ASP.NET Core на серверах. CLR створює окрему пам'ять (heap) та окремий потік збору сміття для кожного логічного процесора. Пропускна здатність набагато вища, але споживає більше базової пам'яті.
  • Background GC: Прийшов на зміну Concurrent GC. Дозволяє збирати сміття в Gen 0 та Gen 1 паралельно, навіть коли в цей самий момент триває важкий збір у Gen 2, зменшуючи тривалість блокувань Stop-the-World.

8. Патерн `Dispose(bool disposing)`. Навіщо потрібен `GC.SuppressFinalize(this)`?

↑ До змісту
Коротка суть: Канонічний патерн очищення ресурсів. Захищає від подвійного виклику. `GC.SuppressFinalize` каже збирачу сміття не витрачати ресурси на виклик фіналізатора, якщо ресурси вже звільнені детерміновано через `Dispose()`.

Реалізація патерну:

public class ResourceHolder : IDisposable
{
    private bool _disposed = false;
    private IntPtr _unmanagedHandle; // Некерований ресурс

    public void Dispose()
    {
        Dispose(true);
        // Запобігаємо виклику фіналізатора! Об'єкт помре в Gen 0 без черги фіналізації
        GC.SuppressFinalize(this); 
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 1. Звільняємо керовані IDisposable ресурси (наприклад, файлові стріми)
        }

        // 2. Звільняємо прямі некеровані ресурси (Win32 API handles, malloc memory)
        CloseHandle(_unmanagedHandle);

        _disposed = true;
    }

    // Фіналізатор (деструктор) — підстраховка, якщо розробник забув викликати Dispose()
    ~ResourceHolder()
    {
        Dispose(false); // disposing = false, бо керовані об'єкти вже могли бути зібрані GC!
    }
}

9. Які бувають витоки пам'яті (Memory Leaks) у керованому .NET? Як їх діагностувати?

↑ До змісту
Коротка суть: У .NET витік пам'яті — це не втрата покажчика (як у C++), а збереження живого посилання (GC Root) на непотрібний об'єкт. Топ причин: незняті event'и, статичні колекції та захоплення в замиканнях.

Головні джерела витоків:

  1. Підписка на події без відписки (Event Handlers): Видавець події (Publisher) тримає сильне посилання на підписника (Subscriber) через його метод у делегаті. Доки живий Publisher (наприклад, Singleton), подписник ніколи не буде зібраний GC!
  2. Статичні поля та колекції: Об'єкти, додані в static List<T> або статичний Dictionary, вважаються GC Roots і живуть до завершення роботи всього процесу.
  3. Замикання таймерів (`System.Threading.Timer`): Таймер тримає екземпляр класу через callback, не даючи йому вмерти.
  4. Неочищені ресурси `IDisposable`: Створення пулів з'єднань або потоків без виклику Dispose.

Як шукати: Зняття дампів пам'яті (Memory Dump) та аналіз за допомогою профайлерів: JetBrains dotMemory, PerfView або команди dotnet-dump у Linux/Docker.

10. Як влаштований `async / await` під капотом? Що таке `IAsyncStateMachine`?

↑ До змісту
Коротка суть: Компілятор розбиває асинхронний метод на стани у згенерованій структурі `IAsyncStateMachine`. Метод `MoveNext()` підписується на завершення Task'а через Awaiter і повертає потік у ThreadPool, звільняючи його для інших задач.

Розгорнута відповідь:

Коли зустрічається ключове слово await task:

  1. Викликається task.GetAwaiter().
  2. Якщо задача вже завершена (awaiter.IsCompleted == true), метод продовжує виконуватися синхронно в тому самому потоці без перемикання контексту!
  3. Якщо задача ще виконується:
    • Стан-машина записує поточну точку зупинки (state = 1).
    • Викликається awaiter.UnsafeOnCompleted(MoveNext), що реєструє продовження (continuation).
    • Поточний потік повертається в пул потоків (ThreadPool) обслуговувати інші HTTP-запити.
  4. Коли асинхронна операція введення-виведення (I/O) завершується (наприклад, драйвер мережевої карти отримує байти від БД), потік із пулу викликає MoveNext() знову, відновлює локальні змінні та продовжує виконання коду після await.

11. Що таке `SynchronizationContext`? Навіщо потрібен `ConfigureAwait(false)`?

↑ До змісту
Коротка суть: Контекст синхронізації повертає виконання після `await` у специфічний потік (головний потік UI у WPF або старий HttpContext в ASP.NET MVC). `ConfigureAwait(false)` каже не повертатися в оригінальний потік, запобігаючи дедлокам у бібліотеках.

Розгорнута відповідь:

  • В інтерфейсних додатках (WPF, WinForms, MAUI) оновлювати кнопки й текст можна лише з головного UI-потоку. SynchronizationContext запам'ятовує UI-потік перед `await` і маршалить код після `await` назад у цей потік.
  • Небезпека дедлоку: Якщо викликати Task.Result або .Wait() у UI-потоці, UI блокується в очікуванні таски. Коли таска завершується, вона намагається повернутися в UI-потік через контекст синхронізації, але він заблокований! Виникає класичний Deadlock.
  • ConfigureAwait(false): Вказує рантайму: «Мені все одно, в якому потоці продовжувати код після await — візьми будь-який вільний потік із пулу».
    Порада: У бібліотеках загального призначення (Class Libraries, NuGet) завжди слід писати ConfigureAwait(false). В сучасному ASP.NET Core контекст синхронізації було видалено взагалі, тому там ризику такого дедлоку немає.

12. У чому різниця між `Task` та `ValueTask`? Коли використовувати `ValueTask`?

↑ До змісту
Коротка суть: `Task` — це клас (завжди виділяє пам'ять у купі). `ValueTask` — це структура (0 байт алокацій у разі синхронного завершення). Не можна робити подвійний await для `ValueTask`!

Розгорнута відповідь:

Якщо метод викликається мільйони разів на секунду (наприклад, читання з локального сокету або кешу пам'яті):

// Якщо дані в кеші є — метод завершується СИНХРОННО.
public ValueTask<string> GetCachedDataAsync(string key)
{
    if (_cache.TryGetValue(key, out var val))
    {
        return new ValueTask<string>(val); // Нуль алокацій! Пам'ять у купі не витрачається
    }
    return new ValueTask<string>(FetchFromDbAsync(key)); // Асинхронний повільний шлях
}

Суворі обмеження ValueTask:

  • НЕ можна викликати await двічі: Об'єкт усередині пулиться та перевикористовується через IValueTaskSource. Подвійний await призведе до невизначеної поведінки або винятку.
  • НЕ можна викликати .AsTask() кілька разів або паралельно очікувати через Task.WhenAll() без явної конвертації в Task.

13. Як влаштований `ThreadPool` у .NET? Що таке Work-Stealing та Thread Starvation?

↑ До змісту
Коротка суть: Пул потоків тримає глобальну чергу та локальні черги для кожного потоку. Якщо у потоку закінчилася робота, він «краде» задачі в інших (Work-Stealing). Блокування потоків веде до Thread Starvation.

Розгорнута відповідь:

  • Створення реального системного потоку ОС (new Thread()) займає ~1 МБ пам'яті під стек та сотні мікросекунд процесорного часу. ThreadPool підтримує пул уже створених живих потоків.
  • Алгоритм Work-Stealing: У пулі є одна глобальна черга завдань FIFO і локальна черга LIFO для кожного потоку. Коли робочий потік звільняється, він спочатку розгрібає власну чергу, а якщо вона порожня — «краде» задачі з хвоста черги інших зайнятих потоків. Це мінімізує конкуренцію за блокування між потоками.
  • Thread Starvation (голодування пулу): Виникає, коли асинхронний код блокують синхронно через .Result або Thread.Sleep(). Пул потоків повільно ін'єктує нові потоки (приблизно 1 потік на 500 мс за алгоритмом Hill Climbing). Запити шикуються в гігантську чергу, і сервіс перестає відповідати на HTTP-запити.

14. Примітиви синхронізації: `lock` (`Monitor`), `SemaphoreSlim`, `Mutex`, `AutoResetEvent`. Коли що обирати?

↑ До змісту
Коротка суть: `lock` — для швидких синхронних блокувань у пам'яті. `SemaphoreSlim` — підтримує `await` для асинхронного коду та пулів. `Mutex` — блокування між різними процесами ОС.

Порівняльна таблиця:

  • lock (obj) (під капотом Monitor.Enter / Exit): Найшвидший спосіб захисту критичної секції. Працює тільки всередині одного процесу. Не можна писати await всередині блоку lock!
  • SemaphoreSlim: Легковажний семафор. Дозволяє обмежити доступ кількості потоків одночасно (наприклад, не більше 5 паралельних HTTP запитів). Підтримує await semaphore.WaitAsync(), тому є стандартом для асинхронного C#!
  • Mutex: Важкий примітив рівня ядра ОС. Дозволяє синхронізувати різні процеси (наприклад, заборонити запуск двох копій одного додатку в операційній системі за допомогою іменованого м'ютексу).
  • ManualResetEventSlim / AutoResetEvent: Події-сигнали для очікування завершення операції іншим потоком («ворота відкриті / закриті»).

15. Атомарні операції `Interlocked`, ключове слово `volatile` та Memory Barriers.

↑ До змісту
Коротка суть: `Interlocked` виконує операції на рівні інструкцій CPU без блокування потоків. `volatile` та бар'єри пам'яті забороняють компілятору і процесору оптимізувати/переставляти місцями читання та запис полів.

Розгорнута відповідь:

Операція count++ насправді не є атомарною (вона складається з 3 кроків: зчитати в регістр CPU, додати 1, записати назад у пам'ять). У багатопотоковому середовищі це веде до втрати даних (Race Condition).

// Замість важкого блокування через lock:
private static int _counter;

// Атомарна операція за 1 такт процесора:
Interlocked.Increment(ref _counter);
Interlocked.Add(ref _counter, 5);
Interlocked.CompareExchange(ref _location, newValue, comparand); // CAS операція
  • Бар'єри пам'яті (Memory Barriers): Сучасні процесори та JIT-компілятор можуть переставляти інструкції читання/запису місцями для прискорення (Out-of-order execution). Бар'єр гарантує, що всі операції до бар'єра будуть виконані суворо раніше за операції після нього.
  • volatile: Підказує компілятору, що поле може змінюватися іншими паралельними потоками. Забороняє кешувати його значення в регістрах CPU і змушує завжди читати актуальне значення напряму з оперативної пам'яті.
