Патерн 6: Adapter (Адаптер)*

Структурний (Structural)
↑ До змісту

1. Призначення

Дозволяє об'єктам із несумісними інтерфейсами працювати разом, виступаючи перехідником-обгорткою між ними.

2. Коли застосовувати

  • Потрібно підключити сторонню бібліотеку або legacy-сервіс, інтерфейс якого не відповідає вимогам вашої системи.
  • Необхідно узгодити несумісні типи даних (наприклад, сума в копійках проти decimal у гривнях, JSON проти XML), не переписуючи вихідний код обох сторін.
Приклади у .NET: StreamReader(Stream) (адаптує низькорівневий потік байтів до текстового зчитування символів), DbDataAdapter в ADO.NET.

3. Реалізація на C#

using System;

// 1. Target interface expected by the client
public interface IPaymentProcessor
{
    void Pay(decimal amount);
}

// 2. Existing modern implementation
public class ModernPaymentProcessor : IPaymentProcessor
{
    public void Pay(decimal amount) => Console.WriteLine($"[ModernPay] Paid: {amount:C}");
}

// 3. Adaptee: legacy service with an incompatible contract
public class LegacyBankService
{
    public void MakeTransaction(long amountInCents, string transactionId)
    {
        Console.WriteLine($"[LegacyBank] Transaction #{transactionId} for {amountInCents} cents.");
    }
}

// 4. Adapter: translates IPaymentProcessor calls into LegacyBankService calls
public class LegacyBankAdapter : IPaymentProcessor
{
    private readonly LegacyBankService _legacyService;

    public LegacyBankAdapter(LegacyBankService legacyService)
    {
        _legacyService = legacyService;
    }

    public void Pay(decimal amount)
    {
        long cents = (long)(amount * 100);
        string id = Guid.NewGuid().ToString().Substring(0, 8);
        _legacyService.MakeTransaction(cents, id);
    }
}

class Program
{
    static void Main()
    {
        IPaymentProcessor processor = new LegacyBankAdapter(new LegacyBankService());
        processor.Pay(250.75m);
    }
}

/* Результат виконання: **************************************/

[LegacyBank] Transaction #3f8a1b2c for 25075 cents.
*(де 3f8a1b2c — випадковий згенерований ID транзакції)*

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн Adapter вирішує проблему несумісності сигнатур та типів даних за допомогою чотирьох учасників:

  • Target (Цільовий інтерфейс) IPaymentProcessor: Стандартний контракт, з яким уміє взаємодіяти клієнтська система.
  • Adaptee (Адаптований клас) LegacyBankService: Готовий клас зі сторонньої бібліотеки або legacy-модуля. Має метод MakeTransaction(long, string), несумісний із клієнтським кодом.
  • Adapter (Адаптер) LegacyBankAdapter: Реалізує IPaymentProcessor та огортає посилання на LegacyBankService.
  • Клієнт Program: Спілкується виключно через цільовий інтерфейс, не підозрюючи про існування застарілого класу.
2. Розбираємо код по частинах

Конструктор адаптера: Приймає екземпляр LegacyBankService через композицію та зберігає його в private readonly поле.

Метод Pay(decimal amount): Це серце патерну. Тут виконується мапінг між двома різними світами:
1. Конвертація типу: amount * 100 перетворює дробове значення грошей у копійки типу long.
2. Генерація додаткових параметрів: застаріла служба вимагає обов'язковий ідентифікатор transactionId, якого немає у вхідному виклику. Адаптер самостійно генерує його: Guid.NewGuid().ToString().Substring(0, 8).
3. Делегування: викликається реальний метод адаптованого об'єкта _legacyService.MakeTransaction(cents, id).

3. Що відбувається в Main() по кроках
Крок 1: Ініціалізація адаптера
Клієнт створює об'єкт LegacyBankService і передає його в конструктор LegacyBankAdapter. Змінна зберігається під абстрактним типом IPaymentProcessor.
Крок 2: Виклик стандартного методу
Викликається processor.Pay(250.75m). Клієнт вважає, що працює зі звичайною сучасною платіжною системою.
Крок 3: Перетворення та делегування
Адаптер перераховує 250.75m у 25075 копійок, генерує випадковий ID і передає виклик у LegacyBankService. Консоль виводить повідомлення банку.
4. У чому саме полягає патерн Adapter?

Патерн змінює інтерфейс об'єкта, не чіпаючи його вихідний код. Він рятує від необхідності переписувати надійний старий код або підлаштовувати всю свою архітектуру під чужі сторонні SDK.

4. Плюси та мінуси

  • Переваги: відокремлює логіку перетворення даних від бізнес-коду (SRP); дозволяє додавати нові адаптери без модифікації існуючого клієнтського коду (OCP).
  • Недоліки: збільшує кількість дрібних класів-обгорток у проєкті.

Патерн 7: Bridge (Міст)*

Структурний (Structural)
↑ До змісту

1. Призначення

Розділяє великий клас на дві окремі незалежні ієрархії — Абстракцію та Реалізацію, дозволяючи змінювати їх незалежно і запобігаючи комбінаторному вибуху кількості класів ($M \times N$).

2. Коли застосовувати

  • Клас розвивається у двох незалежних площинах (наприклад, типи пультів керування та конкретні пристрої; форми вікон ОС та графічні рушії DirectX/OpenGL).
  • Потрібно динамічно підміняти рушій реалізації під час виконання програми.
Приклади у .NET: DbConnection (абстракція зв'язку з БД відокремлена від платформних драйверів: SqlClient, Npgsql, SqliteConnection).

3. Реалізація на C#

using System;

// 1. Implementor interface
public interface IDevice
{
    bool IsEnabled();

    void Enable();

    void Disable();

    int GetVolume();

    void SetVolume(int percent);
}

// Concrete Implementor: TV
public class TvDevice : IDevice
{
    private bool _on;
    private int _vol = 30;

    public bool IsEnabled() => _on;

    public void Enable()
    {
        _on = true;
        Console.WriteLine("[TV] Enabled.");
    }

    public void Disable()
    {
        _on = false;
        Console.WriteLine("[TV] Disabled.");
    }

    public int GetVolume() => _vol;

    public void SetVolume(int p)
    {
        _vol = Math.Clamp(p, 0, 100);
        Console.WriteLine($"[TV] Volume: {_vol}%");
    }
}

// 2. Abstraction
public class RemoteControl
{
    protected readonly IDevice _device;

    public RemoteControl(IDevice device) => _device = device;

    public void TogglePower()
    {
        if (_device.IsEnabled())
            _device.Disable();
        else
            _device.Enable();
    }

    public void VolumeUp() => _device.SetVolume(_device.GetVolume() + 10);
}

// 3. Refined Abstraction
public class AdvancedRemoteControl : RemoteControl
{
    public AdvancedRemoteControl(IDevice device) : base(device) { }

    public void Mute()
    {
        Console.WriteLine("[Remote] Mute.");
        _device.SetVolume(0);
    }
}

class Program
{
    static void Main()
    {
        IDevice tv = new TvDevice();
        var remote = new AdvancedRemoteControl(tv);

        remote.TogglePower();
        remote.VolumeUp();
        remote.Mute();
    }
}

/* Результат виконання: **************************************/

[TV] Enabled.
[TV] Volume: 40%
[Remote] Mute.
[TV] Volume: 0%

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Міст розділяє систему на дві незалежні гілки, з'єднані посиланням через інтерфейс:

  • Гілка реалізації (Implementor): Інтерфейс IDevice та конкретні класи обладнання (TvDevice, а в майбутньому RadioDevice).
  • Гілка абстракції (Abstraction): Базовий клас RemoteControl та його розширення AdvancedRemoteControl.

Головна ідея: пульт не знає, як усередині влаштований телевізор чи радіо. Він звертається лише до методів інтерфейсу IDevice.

2. Розбираємо код по частинах

Інтерфейс IDevice: Контракт низькорівневих дій пристрою: вмикання, вимикання, регулювання гучності.

Клас TvDevice: Зберігає внутрішній стан телевізора (_on і _vol = 30). Метод SetVolume(int p) використовує Math.Clamp(p, 0, 100), щоб гучність ніколи не виходила за межі діапазону 0–100%.

Клас RemoteControl (Абстракція):
• Поле protected readonly IDevice _device: посилання зберігається саме через інтерфейс, що дозволяє працювати з будь-яким пристроєм. Модифікатор protected надає прямий доступ підкласам на кшталт AdvancedRemoteControl.
• Метод TogglePower() перевіряє стан і або вмикає, або вимикає пристрій.

Клас AdvancedRemoteControl: Успадковує базовий пульт і додає функцію швидкого вимкнення звуку Mute(), викликаючи _device.SetVolume(0).

3. Що відбувається в Main() по кроках
Крок 1: TogglePower()
Телевізор спочатку вимкнений (_on = false). Метод перемикача вмикає його, виводячи: [TV] Enabled.
Крок 2: VolumeUp()
Початкова гучність становила 30%. Пульт зчитує її, додає 10% і передає нове значення назад: [TV] Volume: 40%.
Крок 3: Mute()
Розширений пульт примусово скидає звук до нуля:
[Remote] Mute.
[TV] Volume: 0%
4. У чому саме полягає патерн Bridge?

Якби ми використовували звичайне успадкування без Bridge, нам довелося б створювати окремі класи під кожну комбінацію: TvRemote, AdvancedTvRemote, RadioRemote, AdvancedRadioRemote. При додаванні 5 пристроїв і 4 видів пультів кількість класів зросла б до 20 ($5 \times 4$).

Міст перетворює множення на додавання ($5 + 4 = 9$ класів). Обидві гілки розвиваються абсолютно вільно одна від одної.

4. Плюси та мінуси

  • Переваги: усуває комбінаторний вибух класів; дозволяє змінювати конкретну реалізацію прямо під час виконання програми.
  • Недоліки: ускладнює початкову структуру коду введенням додаткового інтерфейсного шару.

Патерн 8: Composite (Компонувальник)

Структурний (Structural)
↑ До змісту

1. Призначення

Згруповує об'єкти в деревоподібну структуру («частина — ціле»), дозволяючи клієнту однаково працювати як з окремими об'єктами, так і з їхніми вкладеними групами.

2. Коли застосовувати

  • Модель даних природно представляється у вигляді дерева: файлова система (файли та папки), кошики покупок (товари та пакунки з товарами), організаційна структура компанії.
  • Клієнт повинен застосовувати операції (розрахунок вартості, вивід дерева на екран) до всієї гілки без ручного розпізнавання, де окремий елемент, а де контейнер.
Приклади у .NET: Візуальне дерево елементів у WPF/MAUI (UIElement / Panel), ієрархічні секції конфігурації IConfiguration.

3. Реалізація на C#

using System;
using System.Collections.Generic;
using System.Linq;

// 1. Common Component interface
public interface IItem
{
    string Name { get; }

    decimal GetPrice();

    void Display(int depth = 0);
}

// 2. Leaf element
public class Product : IItem
{
    public string Name { get; }
    private readonly decimal _price;

    public Product(string name, decimal price)
    {
        Name = name;
        _price = price;
    }

    public decimal GetPrice() => _price;

    public void Display(int depth = 0) => Console.WriteLine($"{new string(' ', depth * 2)}- {Name} ({_price:C})");
}

// 3. Composite container
public class Box : IItem
{
    private readonly List<IItem> _children = new();
    public string Name { get; }

    public Box(string name) => Name = name;

    public void Add(IItem item) => _children.Add(item);

    public decimal GetPrice() => _children.Sum(i => i.GetPrice());

    public void Display(int depth = 0)
    {
        Console.WriteLine($"{new string(' ', depth * 2)}+ [{Name}]");
        foreach (var item in _children)
            item.Display(depth + 1);
    }
}

class Program
{
    static void Main()
    {
        var box = new Box("Main Order");
        box.Add(new Product("Smartphone", 800m));

        var subBox = new Box("Accessories");
        subBox.Add(new Product("Phone Case", 20m));
        box.Add(subBox);

        box.Display();
        Console.WriteLine($"Total: {box.GetPrice():C}");
    }
}

/* Результат виконання: **************************************/

+ [Main Order]
  - Smartphone (800,00 ₴)
  + [Accessories]
    - Phone Case (20,00 ₴)
Total: 820,00 ₴

(Формат і знак валюти залежать від системної локалі, наприклад: 800,00 ₴ або $800.00)

/*************************************************************/

4. Плюси та мінуси

  • Переваги: спрощує роботу з рекурсивними деревоподібними структурами завдяки поліморфізму; полегшує додавання нових видів вузлів.
  • Недоліки: важко накласти обмеження на типи дочірніх компонентів у конкретних контейнерах на етапі компіляції.

Патерн 9: Decorator (Декоратор)*

Структурний (Structural)
↑ До змісту

1. Призначення

Дозволяє динамічно додавати об'єктам нові обов'язки та поведінку під час виконання програми, загортаючи їх у класи-обгортки без використання наслідування.

2. Коли застосовувати

  • Потрібно додавати функціонал (логування, шифрування, валідацію, кешування) на льоту, комбінуючи шари за потребою.
  • Успадкування неможливе або веде до комбінаторного вибуху класів (наприклад, коли базовий клас позначений як sealed).
Приклади у .NET: Ланцюжки потоків у System.IO: new CryptoStream(new GZipStream(new FileStream(...))), реєстрація декораторів сервісів у DI за допомогою бібліотеки Scrutor.

3. Реалізація на C#

using System;

// 1. Component contract
public interface INotifier
{
    void Send(string message);
}

// 2. Concrete base component
public class EmailNotifier : INotifier
{
    public void Send(string message) => Console.WriteLine($"[Email]: {message}");
}

// 3. Base Decorator wrapper
public abstract class NotifierDecorator : INotifier
{
    protected readonly INotifier _wrappee;

    protected NotifierDecorator(INotifier wrappee) => _wrappee = wrappee;

    public virtual void Send(string message) => _wrappee.Send(message);
}

// 4. Concrete Decorators
public class SmsDecorator : NotifierDecorator
{
    public SmsDecorator(INotifier wrappee) : base(wrappee) { }

    public override void Send(string message)
    {
        base.Send(message);
        Console.WriteLine($"[SMS]: {message}");
    }
}

public class TelegramDecorator : NotifierDecorator
{
    public TelegramDecorator(INotifier wrappee) : base(wrappee) { }

    public override void Send(string message)
    {
        base.Send(message);
        Console.WriteLine($"[Telegram]: {message}");
    }
}

class Program
{
    static void Main()
    {
        // Multi-layer wrapping: Email + SMS + Telegram
        INotifier notifier = new TelegramDecorator(
            new SmsDecorator(
                new EmailNotifier()
            )
        );

        notifier.Send("Warning! Server overloaded.");
    }
}

/* Результат виконання: **************************************/

[Email]: Warning! Server overloaded.
[SMS]: Warning! Server overloaded.
[Telegram]: Warning! Server overloaded.

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн Decorator будується на принципі «матрьошки» за спільним інтерфейсом:

  • Інтерфейс компонента INotifier: Єдиний контракт для базового сервісу та всіх його декораторів.
  • Базовий компонент EmailNotifier: Реалізує первинну базову функціональність (відправка пошти).
  • Базовий декоратор NotifierDecorator: Реалізує INotifier і одночасно зберігає посилання на вкладений INotifier.
  • Конкретні декоратори SmsDecorator та TelegramDecorator: Додають новий функціонал до або після виклику загорнутого об'єкта.
2. Розбираємо код по частинах

Секрет базового декоратора:

public abstract class NotifierDecorator : INotifier
{
    protected readonly INotifier _wrappee;
    protected NotifierDecorator(INotifier wrappee) => _wrappee = wrappee;
    public virtual void Send(string message) => _wrappee.Send(message);
}

Декоратор зовні поводиться точно як INotifier, тому клієнт навіть не здогадується, що працює з обгорткою. Будь-який декоратор може обертати як базовий компонент, так і інший декоратор.

Виклик base.Send(message): Конкретний декоратор спочатку передає виклик углиб ланцюжка через base.Send(), а потім виконує власну специфічну дію (друк у консоль SMS або Telegram).

3. Що відбувається в Main() по кроках
Крок 1: Конструювання ланцюжка обгорток
Створюється EmailNotifier. Він огортається в SmsDecorator, який своєю чергою огортається в TelegramDecorator. Змінна зберігається як інтерфейс INotifier.
Крок 2: Виклик методу Send()
Клієнт викликає notifier.Send(...) на зовнішньому об'єкті TelegramDecorator.
Крок 3: Розгортання викликів зсередини-назовні
1. TelegramDecorator викликає base.Send() → переходить у SmsDecorator.
2. SmsDecorator викликає base.Send() → переходить у EmailNotifier.
3. EmailNotifier не має обгорток і виконує дію першим: [Email]: Warning! ....
4. Стек повертається: SmsDecorator виводить [SMS]: Warning! ....
5. TelegramDecorator завершує виклик: [Telegram]: Warning! ....
4. У чому саме полягає патерн Decorator?

Патерн зберігає незмінним інтерфейс об'єкта, але розширює його обов'язки. Це альтернатива успадкуванню: замість створення класів на кожну комбінацію (EmailAndSms, EmailAndTelegram, EmailAndSmsAndTelegram) поведінка збирається динамічно під час роботи програми.

4. Плюси та мінуси

  • Переваги: динамічна комбінація поведінки без монолітного спадкування; дотримання принципу Single Responsibility.
  • Недоліки: порядок огортання шарів має вирішальне значення; стек викликів важче відлагоджувати при багатьох вкладених рівнях.

Патерн 10: Facade (Фасад)*

Структурний (Structural)
↑ До змісту

1. Призначення

Надає простий та високорівневий уніфікований інтерфейс до складної підсистеми, що складається з десятків взаємопов'язаних сервісів або бібліотек.

2. Коли застосовувати

  • Потрібно сховати хаос складної сторонньої бібліотеки або внутрішньої архітектури мікросервісів за кількома зрозумілими методами.
  • Потрібно послабити зачеплення (coupling) між клієнтським кодом і внутрішніми службами підсистеми.
Приклади у .NET: DbContext в EF Core (фасад над кешем відстеження сутностей, генератором SQL-виразів та пулом з'єднань ADO.NET), високорівневий клас HttpClient.

3. Реалізація на C#

using System;

// 1. Complex subsystem services
public class InventoryService
{
    public bool CheckStock(string id)
    {
        Console.WriteLine($"[Inventory] Product {id} is in stock.");
        return true;
    }
}

public class PaymentService
{
    public bool Charge(string email, decimal amount)
    {
        Console.WriteLine($"[Payment] Charged {amount:C}.");
        return true;
    }
}

public class LogisticsService
{
    public string CreateShippingOrder(string id, string addr)
    {
        Console.WriteLine("[Logistics] Shipping order created.");
        return "TTN-123";
    }
}

// 2. High-level Facade
public class OrderFacade
{
    private readonly InventoryService _inventory = new();
    private readonly PaymentService _payment = new();
    private readonly LogisticsService _logistics = new();

    public bool PlaceOrder(string productId, decimal amount, string email, string address)
    {
        if (!_inventory.CheckStock(productId))
            return false;

        if (!_payment.Charge(email, amount))
            return false;

        _logistics.CreateShippingOrder(productId, address);

        Console.WriteLine("Order placed successfully!");
        return true;
    }
}

class Program
{
    static void Main()
    {
        var facade = new OrderFacade();
        facade.PlaceOrder("LAPTOP", 2500m, "alex@test.com", "Kyiv");
    }
}

/* Результат виконання: **************************************/

[Inventory] Product LAPTOP is in stock.
[Payment] Charged 2 500,00 ₴.
[Logistics] Shipping order created.
Order placed successfully!

(Формат валюти залежить від системної локалі, наприклад: 2 500,00 ₴ або $2,500.00)

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн організовує роботу двох рівнів системи:

  • Низькорівнева складна підсистема: Незалежні класи InventoryService, PaymentService, LogisticsService. Кожен із них вимагає специфічних параметрів і має власний життєвий цикл.
  • Фасад OrderFacade: Агрегує посилання на всі сервіси підсистеми і надає єдиний зручний метод PlaceOrder(...).
  • Клієнт Program: Спілкується лише з фасадом, позбавляючись потреби знати порядок викликів підсистеми.
2. Розбираємо код по частинах

Сервіси підсистеми:
• InventoryService.CheckStock: перевіряє залишки на складі.
• PaymentService.Charge: списує кошти з платіжного шлюзу.
• LogisticsService.CreateShippingOrder: реєструє товар у службі доставки.

Метод фасаду PlaceOrder: Об'єднує типовий користувацький бізнес-сценарій в один виклик. Він бере на себе координацію послідовності кроків: перевірка наявності → списання оплати → оформлення доставки. Якщо один із проміжних кроків повертає false, подальший процес безпечно переривається.

3. Що відбувається в Main() по кроках
Крок 1: Створення фасаду
Клієнт інстанціює facade = new OrderFacade(). Фасад ініціалізує необхідні підсистеми всередині себе.
Крок 2: Оформлення замовлення одним рядком
Клієнт викликає facade.PlaceOrder("LAPTOP", 2500m, "alex@test.com", "Kyiv").
Крок 3: Послідовна робота підсистем
Фасад по черзі викликає сервіси: склад підтверджує наявність, банк списує гроші, логістика формує накладну, і консоль видає: Order placed successfully!.
4. У чому саме полягає патерн Facade?

Фасад спрощує інтерфейс і знижує поріг входження для клієнтського коду. При цьому він не блокує прямий доступ до підсистем: якщо досвідченому модулю знадобиться звернутися безпосередньо до LogisticsService, він все ще може це зробити напряму.

4. Плюси та мінуси

  • Переваги: захищає клієнтський код від складності компонентів підсистеми; суттєво зменшує зв'язність (Loose Coupling).
  • Недоліки: при неконтрольованому розширенні фасад ризикує перетворитися на перевантажений God Object.

Патерн 11: Flyweight (Легковаговик)

Структурний (Structural)
↑ До змісту

1. Призначення

Заощаджує оперативну пам'ять процесу, розділяючи стан величезної кількості дрібних об'єктів на внутрішній (спільний, незмінний) та зовнішній (контекстний, унікальний).

2. Коли застосовувати

  • У пам'яті одночасно створюються сотні тисяч або мільйони схожих об'єктів (символи в документі, частинки графіки, елементи карти в іграх).
  • Більшість полів об'єктів дублюють однакові статичні дані (наприклад, колір, текстура, назва), які можна винести в спільний пул.
Приклади у .NET: Таблиця інтернування рядків у CLR (string.Intern): однакові рядкові літерали зберігаються в пам'яті лише в одному екземплярі.

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Intrinsic state: shared immutable flyweight
public class TreeType
{
    public string Name { get; }
    public string Color { get; }

    public TreeType(string name, string color)
    {
        Name = name;
        Color = color;
    }

    public void Draw(int x, int y) => Console.WriteLine($"Tree '{Name}' ({Color}) at ({x}, {y})");
}

// 2. Flyweight Factory: caches shared instances
public static class TreeFactory
{
    private static readonly Dictionary<string, TreeType> _types = new();

    public static TreeType GetTreeType(string name, string color)
    {
        string key = $"{name}_{color}";
        if (!_types.TryGetValue(key, out var type))
        {
            type = new TreeType(name, color);
            _types[key] = type;
        }
        return type;
    }
}

// 3. Extrinsic state: unique coordinates context
public class Tree
{
    private readonly int _x;
    private readonly int _y;
    private readonly TreeType _type;

    public Tree(int x, int y, TreeType type)
    {
        _x = x;
        _y = y;
        _type = type;
    }

    public void Draw() => _type.Draw(_x, _y);
}

class Program
{
    static void Main()
    {
        var forest = new List<Tree>();
        var oakType = TreeFactory.GetTreeType("Oak", "Green");

        for (int i = 0; i < 1000; i++)
        {
            forest.Add(new Tree(i, i * 2, oakType));
        }
    }
}

/* Результат виконання: **************************************/

У наведеному коді в методі Main немає викликів Console.WriteLine() або методу .Draw(), 
тому на консоль нічого не виведеться (вивід порожній).

(Якщо додати в кінець Main, наприклад, виклик forest[0].Draw();, результат буде таким):

Tree 'Oak' (Green) at (0, 0)

/*************************************************************/

4. Плюси та мінуси

  • Переваги: радикальне скорочення споживання RAM при масивах однотипних даних.
  • Недоліки: витрати процесорного часу на пошук об'єктів у хеш-таблиці пулу; ускладнення коду через поділ внутрішнього та зовнішнього стану.

Патерн 12: Proxy (Замісник)*

Структурний (Structural)
↑ До змісту

1. Призначення

Надає об'єкт-замінник іншого сервісу для контролю доступу до нього: лінивої ініціалізації, кешування запитів, перевірки прав тощо.

2. Коли застосовувати

  • Virtual Proxy: відкладене завантаження ресурсомісткого об'єкта лише в момент його реального першого виклику.
  • Caching Proxy: автоматичне збереження та повернення результатів повторюваних важких обчислень чи запитів.
  • Protection Proxy: перевірка ролей та авторизації клієнта перед виконанням цільової операції.
Приклади у .NET: Ліниве завантаження зв'язаних сутностей в EF Core (UseLazyLoadingProxies на базі Castle DynamicProxy), клієнтські проксі WCF та gRPC.

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Service contract
public interface IVideoDownloader
{
    void DownloadVideo(string videoId);
}

// 2. Real heavy service
public class YouTubeDownloader : IVideoDownloader
{
    public YouTubeDownloader() => Console.WriteLine("[YouTube] Heavy network connection initialized...");

    public void DownloadVideo(string id) => Console.WriteLine($"[YouTube] Downloading video #{id}...");
}

// 3. Proxy: lazy loading and caching
public class CachedYouTubeProxy : IVideoDownloader
{
    private YouTubeDownloader _service;
    private readonly HashSet<string> _cache = new();

    public void DownloadVideo(string id)
    {
        _service ??= new YouTubeDownloader();

        if (_cache.Contains(id))
        {
            Console.WriteLine($"[Proxy] Video #{id} served from local cache!");
            return;
        }

        _service.DownloadVideo(id);
        _cache.Add(id);
    }
}

class Program
{
    static void Main()
    {
        IVideoDownloader downloader = new CachedYouTubeProxy();
        downloader.DownloadVideo("patterns");
        downloader.DownloadVideo("patterns");
    }
}

/* Результат виконання: **************************************/

[YouTube] Heavy network connection initialized...
[YouTube] Downloading video #patterns...
[Proxy] Video #patterns served from local cache!

/*************************************************************/
🔍 Детальний розбір: як працює код
1. Архітектура та структура коду

Патерн Proxy будується на повному збігу інтерфейсів між обгорткою та цільовим об'єктом:

  • Контракт сервісу IVideoDownloader: Описує метод DownloadVideo(string videoId).
  • Реальний сервіс YouTubeDownloader: Важкий сервіс, який при ініціалізації встановлює дороге мережеве з'єднання.
  • Проксі CachedYouTubeProxy: Реалізує IVideoDownloader, відкладає створення YouTubeDownloader до першої потреби та кешує результати.
  • Клієнт Program: Працює через інтерфейс IVideoDownloader і не знає, що звертається до проксі.
2. Розбираємо код по частинах

Лінива ініціалізація (Virtual Proxy):
Конструктор CachedYouTubeProxy взагалі не створює реальний об'єкт. Створення відбувається лише всередині DownloadVideo за допомогою оператора C# _service ??= new YouTubeDownloader();. Якщо клієнт створив проксі, але жодного разу не викликав завантаження, важке з'єднання ніколи не буде встановлено.

Локальне кешування (Caching Proxy):
Колекція HashSet<string> _cache зберігає ідентифікатори вже завантажених відео. При повторному запиті того самого videoId виклик перехоплюється: реальний сервіс не навантажується мережевим запитом, а результат миттєво віддається з локального кешу.

3. Що відбувається в Main() по кроках
Крок 1: Перший виклик завантаження
Клієнт викликає downloader.DownloadVideo("patterns"). Проксі бачить, що _service == null, ініціалізує YouTubeDownloader (виводиться повідомлення про важке підключення), завантажує відео з мережі та додає його ID у кеш.
Крок 2: Другий виклик завантаження з тим самим ID
Клієнт повторно викликає downloader.DownloadVideo("patterns").
Крок 3: Перехоплення запиту
Проксі перевіряє умову _cache.Contains(id), знаходить запис і миттєво виводить: [Proxy] Video #patterns served from local cache!. До реального сервісу виклик навіть не доходить.
4. У чому різниця між Proxy та Decorator?

Хоча UML-діаграми патернів ідентичні (обидва огортають об'єкт із тим самим інтерфейсом):

  • Decorator: Додає нову поведінку та бізнес-можливості. Клієнт зазвичай сам збирає матрьошку декораторів.
  • Proxy: Не змінює результат роботи і не додає нової бізнес-функціональності — він контролює доступ, оптимізує ресурси та захищає реальний об'єкт. Найчастіше проксі сам створює та керує життєвим циклом свого реального суб'єкта.

4. Плюси та мінуси

  • Переваги: оптимізація споживання ресурсів завдяки лінивому створенню; прозорий контроль прав доступу та кешування без змін у вихідному сервісі.
  • Недоліки: невелике збільшення затримки виконання викликів через додатковий проміжний шар.
