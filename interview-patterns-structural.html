Патерн 6: Adapter (Адаптер)*

Структурний (Structural)
↑ До змісту

1. Призначення

Дозволяє об'єктам із несумісними інтерфейсами працювати разом, виступаючи перехідником-обгорткою між ними.

2. Коли застосовувати

  • Потрібно підключити сторонню бібліотеку або застарілий (legacy) клас, інтерфейс якого не відповідає вимогам вашої системи.
  • Необхідно узгодити несумісні типи даних (дробові гривні проти копійок типу long, XML проти JSON), не змінюючи код обох сторін.
Приклади у .NET: StreamReader(Stream) (адаптує низькорівневий байтовий потік до читання символьних рядків), DbDataAdapter в ADO.NET.

3. Реалізація на C#

using System;

// 1. Target interface expected by the client
public interface IPaymentProcessor
{
    void Pay(decimal amount);
}

// 2. Existing modern implementation
public class ModernPaymentProcessor : IPaymentProcessor
{
    public void Pay(decimal amount) => Console.WriteLine($"[ModernPay] Paid: {amount:C}");
}

// 3. Adaptee: legacy service with an incompatible contract
public class LegacyBankService
{
    public void MakeTransaction(long amountInCents, string transactionId)
    {
        Console.WriteLine($"[LegacyBank] Transaction #{transactionId} for {amountInCents} cents.");
    }
}

// 4. Adapter: translates IPaymentProcessor calls into LegacyBankService calls
public class LegacyBankAdapter : IPaymentProcessor
{
    private readonly LegacyBankService _legacyService;

    public LegacyBankAdapter(LegacyBankService legacyService)
    {
        _legacyService = legacyService;
    }

    public void Pay(decimal amount)
    {
        long cents = (long)(amount * 100);
        string id = Guid.NewGuid().ToString().Substring(0, 8);
        _legacyService.MakeTransaction(cents, id);
    }
}

class Program
{
    static void Main()
    {
        IPaymentProcessor processor = new LegacyBankAdapter(new LegacyBankService());
        processor.Pay(250.75m);
    }
}

/* Результат виконання: **************************************/

[LegacyBank] Transaction #3f8a1b2c for 25075 cents.
*(де 3f8a1b2c — випадковий згенерований ID транзакції)*

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви, що ти прилетів у Велику Британію зі своїм ноутбуком. Твоя європейська вилка кругла з двома штирями, а розетка в номері готелю — потрійна прямокутна. Ти не будеш розбирати стіну і міняти розетку в готелі, і не відрізатимеш провід у ноутбука. Ти просто купуєш перехідник (адаптер). Патерн Adapter робить у програмуванні саме це: змушує чужі або старі класи працювати з твоїм інтерфейсом без переписування коду.

1. Як влаштований код
IPaymentProcessor (Твій цільовий контракт: очікує Pay(decimal amount)) ▲ │ реалізує LegacyBankAdapter (Адаптер-перехідник) │ │ перетворює: гривні -> копійки, генерує transactionId ▼ LegacyBankService (Старий банк: вимагає MakeTransaction(long cents, string id))

Головна ідея: твій клієнтський код навіть не підозрює, що внизу працює старий банківський клас. Він бачить лише звичний метод Pay(...).

2. Розбираємо код по частинах

Частина 1. Інтерфейс IPaymentProcessor

public interface IPaymentProcessor
{
    void Pay(decimal amount);
}

Це сучасний інтерфейс твоєї програми. Він лаконічний: передаємо суму у вигляді decimal (наприклад, 250.75m), і платіж виконано.

Частина 2. Застарілий клас LegacyBankService

public void MakeTransaction(long amountInCents, string transactionId)

А ось так виглядає сторонній SDK або банківський модуль 15-річної давнини. У нього дві проблеми:
1. Він не приймає decimal у гривнях — він вимагає ціле число копійок long.
2. Він вимагає обов'язковий рядок transactionId, якого у твоєму новому коді взагалі немає.

Частина 3. Клас LegacyBankAdapter

Зверни увагу на те, як елегантно адаптер згладжує ці розбіжності:

public void Pay(decimal amount)
{
    long cents = (long)(amount * 100);
    string id = Guid.NewGuid().ToString().Substring(0, 8);
    _legacyService.MakeTransaction(cents, id);
}

Адаптер бере 250.75m, множить на 100 і приводить до 25075 копійок. Сам генерує унікальний 8-значний ID транзакції через Guid і викликає метод старого банку. Усі специфічні вимоги старого сервісу інкапсульовані всередині адаптера!

3. Що відбувається в Main() крок за кроком
Крок 1 — Створення адаптера:
Ми створюємо LegacyBankService і огортаємо його в new LegacyBankAdapter(...). Посилання зберігаємо в інтерфейсній змінній IPaymentProcessor.
Крок 2 — Виклик Pay():
Клієнт передає зрозумілу для себе суму: processor.Pay(250.75m);.
Крок 3 — Робота перехідника:
Адаптер перераховує гроші в копійки, генерує ID і звертається до LegacyBankService, виводячи в консоль:
[LegacyBank] Transaction #3f8a1b2c for 25075 cents.
4. Чому це краще за наївне рішення?

Без адаптера тобі довелося б по всьому проєкту писати умовні перевірки на кшталт:

if (isLegacy) {
    long cents = (long)(amt * 100);
    legacyService.MakeTransaction(cents, Guid.NewGuid().ToString());
} else {
    modernProcessor.Pay(amt);
}

Код бізнес-логіки перетворився б на спагеті з конвертаціями даних. Адаптер ізолює брудні перетворення в одному окремому класі (SRP) і дозволяє системі працювати з будь-якими новими банками без жодних змін у бізнес-коді (OCP).

4. Плюси та мінуси

  • Переваги: відділяє логіку перетворення даних від бізнес-шару (SRP); дозволяє додавати нові адаптери без модифікації існуючого клієнтського коду (OCP).
  • Недоліки: збільшує кількість дрібних допоміжних класів у проєкті.

Патерн 7: Bridge (Міст)*

Структурний (Structural)
↑ До змісту

1. Призначення

Розділяє великий клас на дві окремі незалежні ієрархії — Абстракцію (керування) та Реалізацію (пристрої), дозволяючи змінювати їх незалежно і запобігаючи вибуху кількості підкласів ($M \times N$).

2. Коли застосовувати

  • Клас розвивається у двох незалежних вимірах (наприклад, типи пультів керування та конкретні пристрої; форми вікон програми та графічні рушії рендерингу DirectX/OpenGL/Vulkan).
  • Потрібно динамічно підміняти апаратну чи платформну реалізацію під час виконання без перекомпіляції клієнтського коду.
Приклади у .NET: DbConnection в ADO.NET (абстрактне керування зв'язком відокремлене від драйверів платформ: SqlServer, PostgreSQL, SQLite).

3. Реалізація на C#

using System;

// 1. Implementor interface
public interface IDevice
{
    bool IsEnabled();
    void Enable();
    void Disable();
    int GetVolume();
    void SetVolume(int percent);
}

// Concrete Implementor: TV
public class TvDevice : IDevice
{
    private bool _on;
    private int _vol = 30;

    public bool IsEnabled() => _on;

    public void Enable()
    {
        _on = true;
        Console.WriteLine("[TV] Enabled.");
    }

    public void Disable()
    {
        _on = false;
        Console.WriteLine("[TV] Disabled.");
    }

    public int GetVolume() => _vol;

    public void SetVolume(int p)
    {
        _vol = Math.Clamp(p, 0, 100);
        Console.WriteLine($"[TV] Volume: {_vol}%");
    }
}

// 2. Abstraction
public class RemoteControl
{
    protected readonly IDevice _device;

    public RemoteControl(IDevice device) => _device = device;

    public void TogglePower()
    {
        if (_device.IsEnabled())
            _device.Disable();
        else
            _device.Enable();
    }

    public void VolumeUp() => _device.SetVolume(_device.GetVolume() + 10);
}

// 3. Refined Abstraction
public class AdvancedRemoteControl : RemoteControl
{
    public AdvancedRemoteControl(IDevice device) : base(device) { }

    public void Mute()
    {
        Console.WriteLine("[Remote] Mute.");
        _device.SetVolume(0);
    }
}

class Program
{
    static void Main()
    {
        IDevice tv = new TvDevice();
        var remote = new AdvancedRemoteControl(tv);

        remote.TogglePower();
        remote.VolumeUp();
        remote.Mute();
    }
}

/* Результат виконання: **************************************/

[TV] Enabled.
[TV] Volume: 40%
[Remote] Mute.
[TV] Volume: 0%

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Цей код демонструє, як відокремити пульт керування від пристрою, яким цей пульт керує. Пояснимо на наочному прикладі телевізора та радіо.

1. Як влаштований код
AdvancedRemoteControl (Розширений пульт: додає Mute()) │ │ успадковує RemoteControl (Звичайний пульт: TogglePower(), VolumeUp()) │ │ працює через інтерфейс ▼ IDevice (Контракт для пристроїв) ▲ │ реалізують ┌──┴───────────────┐ │ │ TvDevice RadioDevice (можна легко додати)

Головна ідея: пульт не повинен знати, як саме влаштований телевізор. Він знає лише, що пристрій підтримує методи інтерфейсу IDevice.

2. Розбираємо код по частинах

Частина 1. Інтерфейс IDevice

Інтерфейс визначає, що повинен уміти будь-який пристрій, яким керуватиме пульт: IsEnabled(), Enable(), Disable(), GetVolume(), SetVolume(int percent). Сам інтерфейс нічого не вмикає — він лише задає обов'язковий контракт поведінки.

Частина 2. Клас TvDevice

Тут реалізовано поведінку телевізора. Він має поля стану: _on (увімкнений/вимкнений) та _vol = 30 (початкова гучність 30%).
Зверни увагу на метод встановлення гучності:

public void SetVolume(int p)
{
    _vol = Math.Clamp(p, 0, 100);
    Console.WriteLine($"[TV] Volume: {_vol}%");
}

Функція Math.Clamp(p, 0, 100) обмежує передане число діапазоном від 0 до 100. Якщо передати -20, результат буде 0; якщо 50 → 50; якщо 130 → 100. Гучність ніколи не вийде за безпечні межі.

Частина 3. Клас RemoteControl (Абстракція)

Зверни увагу на три важливі моменти в оголошенні поля:

protected readonly IDevice _device;
  • IDevice _device: пульт зберігає посилання саме на інтерфейс, а не на конкретний TvDevice.
  • protected: поле доступне не лише всередині самого RemoteControl, а й у його підкласах-нащадках на кшталт AdvancedRemoteControl.
  • readonly: після прив'язки пристрою в конструкторі поле не можна випадково підмінити на інше.

Метод TogglePower() перевіряє стан: якщо телевізор увімкнений — вимикає його, якщо вимкнений — вмикає. Метод VolumeUp() читає поточну гучність, додає 10% і записує нове значення назад.

Частина 4. Клас AdvancedRemoteControl

Цей клас успадковує RemoteControl. Йому не треба повторно писати методи вмикання чи зміни звуку — він уже має їх від батька. Але він додає нову унікальну функцію:

public void Mute()
{
    Console.WriteLine("[Remote] Mute.");
    _device.SetVolume(0);
}
3. Що відбувається в Main() крок за кроком
Крок 1 — remote.TogglePower():
Телевізор спочатку вимкнений (_on = false), тому метод вмикає його:
[TV] Enabled.
Крок 2 — remote.VolumeUp():
Було 30%. Додаємо 10%:
[TV] Volume: 40%
Крок 3 — remote.Mute():
Розширений пульт примусово вимикає звук до 0%:
[Remote] Mute.
[TV] Volume: 0%
4. У чому саме полягає патерн Bridge?

Патерн Bridge відокремлює дві незалежні гілки:
• Абстракція — можливості пультів керування (звичайний, сенсорний, голосовий).
• Реалізація — конкретні пристрої, які виконують команди (телевізор, радіо, кондиціонер).

Чому це краще за наївне успадкування?
Без Bridge тобі довелося б створювати окремі комбіновані класи: TvRemote, AdvancedTvRemote, RadioRemote, AdvancedRadioRemote. Якщо у тебе 5 типів пультів і 10 пристроїв — це вже 50 класів ($5 \times 10$)!
З Bridge це лише 15 класів ($5 + 10$). Ти можеш створити RadioDevice : IDevice і без жодної зміни в класах пультів керувати ним через той самий AdvancedRemoteControl.

4. Плюси та мінуси

  • Переваги: рятує від комбінаторного вибуху класів; дозволяє змінювати реалізацію пристроїв прямо під час виконання програми.
  • Недоліки: додає додатковий рівень непрямого доступу через інтерфейси, що на старті трохи ускладнює код.

Патерн 8: Composite (Компонувальник)

Структурний (Structural)
↑ До змісту

1. Призначення

Згруповує об'єкти в деревоподібну структуру («частина — ціле»), дозволяючи клієнту однаково працювати як з окремими об'єктами, так і з їхніми вкладеними групами через єдиний поліморфний інтерфейс.

2. Коли застосовувати

  • Дані системи природно утворюють дерево: файлова система (файли та папки з файлами), кошик замовлення (окремі товари та подарункові бокси з товарами), ієрархія посад компанії.
  • Клієнт повинен обчислювати загальну ціну або виводити структуру на екран, не перевіряючи вручну, де листок дерева, а де гілка з нащадками.
Приклади у .NET: Візуальне дерево елементів у WPF/MAUI (UIElement / Panel), секції конфігурації IConfiguration.

3. Реалізація на C#

using System;
using System.Collections.Generic;
using System.Linq;

// 1. Common Component interface
public interface IItem
{
    string Name { get; }

    decimal GetPrice();

    void Display(int depth = 0);
}

// 2. Leaf element
public class Product : IItem
{
    public string Name { get; }
    private readonly decimal _price;

    public Product(string name, decimal price)
    {
        Name = name;
        _price = price;
    }

    public decimal GetPrice() => _price;

    public void Display(int depth = 0) => Console.WriteLine($"{new string(' ', depth * 2)}- {Name} ({_price:C})");
}

// 3. Composite container
public class Box : IItem
{
    private readonly List<IItem> _children = new();
    public string Name { get; }

    public Box(string name) => Name = name;

    public void Add(IItem item) => _children.Add(item);

    public decimal GetPrice() => _children.Sum(i => i.GetPrice());

    public void Display(int depth = 0)
    {
        Console.WriteLine($"{new string(' ', depth * 2)}+ [{Name}]");
        foreach (var item in _children)
            item.Display(depth + 1);
    }
}

class Program
{
    static void Main()
    {
        var box = new Box("Main Order");
        box.Add(new Product("Smartphone", 800m));

        var subBox = new Box("Accessories");
        subBox.Add(new Product("Phone Case", 20m));
        box.Add(subBox);

        box.Display();
        Console.WriteLine($"Total: {box.GetPrice():C}");
    }
}

/* Результат виконання: **************************************/

+ [Main Order]
  - Smartphone (800,00 ₴)
  + [Accessories]
    - Phone Case (20,00 ₴)
Total: 820,00 ₴

(Формат і знак валюти залежать від системної локалі, наприклад: 800,00 ₴ або $800.00)

/*************************************************************/

4. Плюси та мінуси

  • Переваги: елегантний рекурсивний обхід дерева будь-якої вкладеності завдяки поліморфізму; легке додавання нових типів елементів.
  • Недоліки: важко накласти статичні обмеження на типи дочірніх елементів у певних коробках на етапі компіляції.

Патерн 9: Decorator (Декоратор)*

Структурний (Structural)
↑ До змісту

1. Призначення

Дозволяє динамічно додавати об'єктам нові обов'язки та поведінку під час виконання програми, огортаючи їх у класи-обгортки без використання спадкування.

2. Коли застосовувати

  • Потрібно динамічно нашаровувати поведінку (шифрування, стиснення, кешування, логування) на льоту в довільних комбінаціях.
  • Успадкування неможливе (наприклад, базовий клас позначений як sealed) або призводить до комбінаторного розростання десятків класів.
Приклади у .NET: Ланцюжки потоків введення-виведення у просторі System.IO: new CryptoStream(new GZipStream(new FileStream(...))), реєстрація декораторів у DI через бібліотеку Scrutor.

3. Реалізація на C#

using System;

// 1. Component contract
public interface INotifier
{
    void Send(string message);
}

// 2. Concrete base component
public class EmailNotifier : INotifier
{
    public void Send(string message) => Console.WriteLine($"[Email]: {message}");
}

// 3. Base Decorator wrapper
public abstract class NotifierDecorator : INotifier
{
    protected readonly INotifier _wrappee;

    protected NotifierDecorator(INotifier wrappee) => _wrappee = wrappee;

    public virtual void Send(string message) => _wrappee.Send(message);
}

// 4. Concrete Decorators
public class SmsDecorator : NotifierDecorator
{
    public SmsDecorator(INotifier wrappee) : base(wrappee) { }

    public override void Send(string message)
    {
        base.Send(message);
        Console.WriteLine($"[SMS]: {message}");
    }
}

public class TelegramDecorator : NotifierDecorator
{
    public TelegramDecorator(INotifier wrappee) : base(wrappee) { }

    public override void Send(string message)
    {
        base.Send(message);
        Console.WriteLine($"[Telegram]: {message}");
    }
}

class Program
{
    static void Main()
    {
        // Multi-layer wrapping: Email + SMS + Telegram
        INotifier notifier = new TelegramDecorator(
            new SmsDecorator(
                new EmailNotifier()
            )
        );

        notifier.Send("Warning! Server overloaded.");
    }
}

/* Результат виконання: **************************************/

[Email]: Warning! Server overloaded.
[SMS]: Warning! Server overloaded.
[Telegram]: Warning! Server overloaded.

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви зимовий одяг. Коли тобі холодно, ти одягаєш футболку. Якщо цього замало — зверху светр. Стало зовсім морозно — одягаєш куртку. Кожен новий шар додає тепла (новий функціонал), але ти залишаєшся тією самою людиною (інтерфейс не змінюється). Decorator працює за принципом такої матрьошки з класів.

1. Як влаштований код
TelegramDecorator (Зовнішній шар: відправляє в Telegram) │ огортає SmsDecorator (Середній шар: відправляє SMS) │ огортає EmailNotifier (Базовий компонент: відправляє Email) ▼ Усі три класи реалізують єдиний інтерфейс INotifier!

Головна ідея: декоратор зовні поводиться точно як оригінальний об'єкт, тому що реалізує той самий інтерфейс, але всередині додає щось своє.

2. Розбираємо код по частинах

Частина 1. Інтерфейс компонента INotifier

Контракт гранично простий: один метод Send(string message). І поштовий сервіс, і будь-яка обгортка зобов'язані його мати.

Частина 2. Базовий клас-декоратор NotifierDecorator

Це ключова точка патерну. Зверни увагу на конструкцію:

public abstract class NotifierDecorator : INotifier
{
    protected readonly INotifier _wrappee;
    protected NotifierDecorator(INotifier wrappee) => _wrappee = wrappee;
    public virtual void Send(string message) => _wrappee.Send(message);
}

Декоратор реалізує інтерфейс INotifier і водночас приймає в конструкторі інший INotifier! Метод за замовчуванням просто делегує виклик далі вглиб через _wrappee.Send(message).

Частина 3. Конкретні декоратори SmsDecorator та TelegramDecorator

Поглянь на метод відправки в SmsDecorator:

public override void Send(string message)
{
    base.Send(message); // Спершу викликаємо загорнутий об'єкт
    Console.WriteLine($"[SMS]: {message}"); // Потім додаємо свою поведінку
}
3. Що відбувається в Main() крок за кроком
Крок 1 — Складання матрьошки:
Ми створюємо EmailNotifier, пакуємо його в SmsDecorator, а той пакуємо в TelegramDecorator. Змінна зберігається як звичайний INotifier.
Крок 2 — Виклик Send():
Клієнт викликає notifier.Send(...) на зовнішньому об'єкті TelegramDecorator.
Крок 3 — Каскад викликів углиб і назад:
1. TelegramDecorator викликає base.Send() → потрапляє в SmsDecorator.
2. SmsDecorator викликає base.Send() → потрапляє в EmailNotifier.
3. EmailNotifier виконує реальну дію: [Email]: Warning! ....
4. Стек повертається назад: SmsDecorator виводить [SMS]: Warning! ....
5. TelegramDecorator виводить [Telegram]: Warning! ....
4. Чому це краще за наївне успадкування?

Якби ми вирішували задачу спадкуванням, нам довелося б наплодити купу класів: EmailAndSmsNotifier, EmailAndTelegramNotifier, EmailAndSmsAndTelegramNotifier. Додавання четвертого каналу (наприклад, Slack) подвоїло б кількість класів!
З Декоратором у нас залишається лише 4 класи, які ми можемо міксувати на льоту в будь-якому порядку прямо в runtime.

4. Плюси та мінуси

  • Переваги: неймовірна гнучкість комбінування функцій без створення десятків підкласів; чисте дотримання принципу Single Responsibility.
  • Недоліки: порядок огортання шарів має суттєве значення; важче відлагоджувати помилки, коли стек викликів проходить крізь 8 шарів обгорток.

Патерн 10: Facade (Фасад)*

Структурний (Structural)
↑ До змісту

1. Призначення

Надає простий та зрозумілий високорівневий інтерфейс до складної підсистеми, що складається з багатьох класів, сервісів або бібліотек.

2. Коли застосовувати

  • Потрібно сховати хаос взаємодії десятків мікросервісів або складного стороннього SDK за кількома простими методами.
  • Потрібно зменшити залежність клієнтського коду від деталей внутрішньої реалізації складної підсистеми.
Приклади у .NET: DbContext в EF Core (фасад над кешем відстеження сутностей ChangeTracker, генератором SQL-запитів та пулом підключень ADO.NET), високорівневий HttpClient.

3. Реалізація на C#

using System;

// 1. Complex subsystem services
public class InventoryService
{
    public bool CheckStock(string id)
    {
        Console.WriteLine($"[Inventory] Product {id} is in stock.");
        return true;
    }
}

public class PaymentService
{
    public bool Charge(string email, decimal amount)
    {
        Console.WriteLine($"[Payment] Charged {amount:C}.");
        return true;
    }
}

public class LogisticsService
{
    public string CreateShippingOrder(string id, string addr)
    {
        Console.WriteLine("[Logistics] Shipping order created.");
        return "TTN-123";
    }
}

// 2. High-level Facade
public class OrderFacade
{
    private readonly InventoryService _inventory = new();
    private readonly PaymentService _payment = new();
    private readonly LogisticsService _logistics = new();

    public bool PlaceOrder(string productId, decimal amount, string email, string address)
    {
        if (!_inventory.CheckStock(productId))
            return false;

        if (!_payment.Charge(email, amount))
            return false;

        _logistics.CreateShippingOrder(productId, address);

        Console.WriteLine("Order placed successfully!");
        return true;
    }
}

class Program
{
    static void Main()
    {
        var facade = new OrderFacade();
        facade.PlaceOrder("LAPTOP", 2500m, "alex@test.com", "Kyiv");
    }
}

/* Результат виконання: **************************************/

[Inventory] Product LAPTOP is in stock.
[Payment] Charged 2 500,00 ₴.
[Logistics] Shipping order created.
Order placed successfully!

(Формат валюти залежить від системної локалі, наприклад: 2 500,00 ₴ або $2,500.00)

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви, що ти замовляєш їжу в додатку Glovo чи Bolt Food. Ти натискаєш одну кнопку «Оформити замовлення». Тобі не потрібно самостійно дзвонити на кухню ресторану, потім окремо переказувати гроші кухарю, потім шукати кур'єра на мопеді й передавати йому адресу доставки. Усім цим складним оркеструванням займається додаток. Додаток — це і є Фасад.

1. Як влаштований код
Клієнт (Main) │ викликає лише ОДИН простий метод: ▼ OrderFacade (Фасад) ├── 1. InventoryService.CheckStock(...) ──► Перевірка залишків на складі ├── 2. PaymentService.Charge(...) ──► Списання коштів із картки └── 3. LogisticsService.CreateShippingOrder(..) ──► Виклик кур'єра

Головна ідея: клієнту дають одну велику зручну кнопку замість 10 дрібних рубильників.

2. Розбираємо код по частинах

Частина 1. Сервіси складної підсистеми

У нас є три незалежні класи: InventoryService (склад), PaymentService (банківський еквайринг) та LogisticsService (служба доставки). Кожен із них має власні методи, правила повернення результатів і параметри.

Частина 2. Клас OrderFacade

Фасад тримає екземпляри всіх трьох сервісів у приватних полях. Поглянь на метод PlaceOrder:

public bool PlaceOrder(string productId, decimal amount, string email, string address)
{
    if (!_inventory.CheckStock(productId)) 
        return false;
    
    if (!_payment.Charge(email, amount)) 
        return false;
    
    _logistics.CreateShippingOrder(productId, address);

    Console.WriteLine("Order placed successfully!");
    return true;
}

Фасад повністю бере на себе контроль правильної послідовності: якщо товару немає на складі, банк навіть не викликається; якщо картку відхилено — кур'єра ніхто не викликає.

3. Що відбувається в Main() крок за кроком
Крок 1 — Звернення клієнта:
Клієнт створює var facade = new OrderFacade(); і викликає facade.PlaceOrder("LAPTOP", 2500m, "alex@test.com", "Kyiv");.
Крок 2 — Виконання підсистем:
Фасад по черзі запускає весь конвеєр, виводячи в консоль:
[Inventory] Product LAPTOP is in stock.
[Payment] Charged 2 500,00 ₴.
[Logistics] Shipping order created.
Order placed successfully!
4. У чому різниця між Facade та Adapter?
  • Adapter: перетворює один несумісний інтерфейс на інший, щоб змусити два класи порозумітися.
  • Facade: створює новий спрощений інтерфейс над цілою групою класів, щоб клієнту було легко керувати складною системою. При цьому фасад не блокує прямий доступ: якщо комусь дійсно знадобиться викликати PaymentService напряму, це не заборонено.

4. Плюси та мінуси

  • Переваги: радикально спрощує роботу з громіздкими підсистемами; суттєво зменшує зачеплення (coupling) між компонентами.
  • Недоліки: при неконтрольованому додаванні нової логіки фасад ризикує перетворитися на God Object.

Патерн 11: Flyweight (Легковаговик)

Структурний (Structural)
↑ До змісту

1. Призначення

Заощаджує гігабайти оперативної пам'яті, розділяючи стан мільйонів однакових дрібних об'єктів на внутрішній (спільний, незмінний) та зовнішній (контекстний, унікальний для кожного випадку).

2. Коли застосовувати

  • У пам'яті одночасно створюються сотні тисяч або мільйони однакових елементів (дерева чи трава в ігровій карті, символи у великому текстовому редакторі, частинки диму).
  • Більшість полів цих об'єктів дублюють однакові важкі дані (текстури, колір, назва), які можна винести в спільний єдиний екземпляр.
Приклади у .NET: Таблиця інтернування рядків у середовищі CLR (string.Intern): однакові рядкові літерали посилаються на один і той самий об'єкт у пам'яті.

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Intrinsic state: shared immutable flyweight
public class TreeType
{
    public string Name { get; }
    public string Color { get; }

    public TreeType(string name, string color)
    {
        Name = name;
        Color = color;
    }

    public void Draw(int x, int y) => Console.WriteLine($"Tree '{Name}' ({Color}) at ({x}, {y})");
}

// 2. Flyweight Factory: caches shared instances
public static class TreeFactory
{
    private static readonly Dictionary<string, TreeType> _types = new();

    public static TreeType GetTreeType(string name, string color)
    {
        string key = $"{name}_{color}";
        if (!_types.TryGetValue(key, out var type))
        {
            type = new TreeType(name, color);
            _types[key] = type;
        }
        return type;
    }
}

// 3. Extrinsic state: unique coordinates context
public class Tree
{
    private readonly int _x;
    private readonly int _y;
    private readonly TreeType _type;

    public Tree(int x, int y, TreeType type)
    {
        _x = x;
        _y = y;
        _type = type;
    }

    public void Draw() => _type.Draw(_x, _y);
}

class Program
{
    static void Main()
    {
        var forest = new List<Tree>();
        var oakType = TreeFactory.GetTreeType("Oak", "Green");

        for (int i = 0; i < 1000; i++)
        {
            forest.Add(new Tree(i, i * 2, oakType));
        }
    }
}

/* Результат виконання: **************************************/

У наведеному коді в методі Main немає викликів Console.WriteLine() або методу .Draw(), 
тому на консоль нічого не виведеться (вивід порожній).

(Якщо додати в кінець Main, наприклад, виклик forest[0].Draw();, результат буде таким):

Tree 'Oak' (Green) at (0, 0)

/*************************************************************/

4. Плюси та мінуси

  • Переваги: колосальна економія оперативної пам'яті процесу при роботі з великими масивами графічних або текстових сутностей.
  • Недоліки: витрати тактової частоти CPU на постійний пошук у словнику пулу; код стає менш очевидним через штучний поділ полів об'єкта.

Патерн 12: Proxy (Замісник)*

Структурний (Structural)
↑ До змісту

1. Призначення

Надає об'єкт-сурогат, який перехоплює виклики до реального сервісу з метою контролю доступу до нього: лінивої ініціалізації, кешування важких запитів, перевірки прав доступу тощо.

2. Коли застосовувати

  • Virtual Proxy: відкладене завантаження «важкого» об'єкта лише в той момент, коли до нього дійсно вперше звернулися.
  • Caching Proxy: збереження відповідей на часті дорогі запити без повторних походів у базу чи мережу.
  • Protection Proxy: перевірка ролей та прав користувача перед виконанням небезпечної операції.
Приклади у .NET: Ліниве завантаження навігаційних властивостей в Entity Framework Core (UseLazyLoadingProxies на базі генератора проксі Castle DynamicProxy), gRPC та WCF клієнти.

3. Реалізація на C#

using System;
using System.Collections.Generic;

// 1. Service contract
public interface IVideoDownloader
{
    void DownloadVideo(string videoId);
}

// 2. Real heavy service
public class YouTubeDownloader : IVideoDownloader
{
    public YouTubeDownloader() => Console.WriteLine("[YouTube] Heavy network connection initialized...");

    public void DownloadVideo(string id) => Console.WriteLine($"[YouTube] Downloading video #{id}...");
}

// 3. Proxy: lazy loading and caching
public class CachedYouTubeProxy : IVideoDownloader
{
    private YouTubeDownloader _service;
    private readonly HashSet<string> _cache = new();

    public void DownloadVideo(string id)
    {
        _service ??= new YouTubeDownloader();

        if (_cache.Contains(id))
        {
            Console.WriteLine($"[Proxy] Video #{id} served from local cache!");
            return;
        }

        _service.DownloadVideo(id);
        _cache.Add(id);
    }
}

class Program
{
    static void Main()
    {
        IVideoDownloader downloader = new CachedYouTubeProxy();
        downloader.DownloadVideo("patterns");
        downloader.DownloadVideo("patterns");
    }
}

/* Результат виконання: **************************************/

[YouTube] Heavy network connection initialized...
[YouTube] Downloading video #patterns...
[Proxy] Video #patterns served from local cache!

/*************************************************************/
🔍 Детальний розбір: як влаштований і працює цей код

Уяви банківську платіжну картку. Вона не є пачкою готівки. Картка — це лише пластиковий проксі твого банківського рахунку. Ти розплачуєшся карткою так само, як готівкою (інтерфейс однаковий), але картка перед списанням перевіряє, чи вистачає коштів, веде журнал витрат і захищена PIN-кодом. Патерн Proxy стоїть перед реальним сервісом і контролює кожне звернення до нього.

1. Як влаштований код
Клієнт (Main) │ викликає DownloadVideo(...) через інтерфейс IVideoDownloader ▼ CachedYouTubeProxy (Замісник) ├── 1. Лінива ініціалізація: створює сервіс лише при першому реальному виклику ├── 2. Кешування: перевіряє _cache.Contains(id) └── 3. Якщо в кеші немає — делегує виклик у ▼ YouTubeDownloader (Реальний дорогий сервіс)

Головна ідея: клієнт думає, що спілкується безпосередньо з сервісом, але насправді всі запити фільтрує та прискорює проксі.

2. Розбираємо код по частинах

Частина 1. Інтерфейс IVideoDownloader

Контракт містить метод DownloadVideo(string videoId). Реальний клас і проксі реалізують цей інтерфейс однаково.

Частина 2. Важкий сервіс YouTubeDownloader

Конструктор сервісу містить повідомлення про важке підключення до мережі. Якби ми створили його без проксі, ми б одразу витратили ресурси, навіть якби відео так ніхто й не завантажив.

Частина 3. Проксі CachedYouTubeProxy

Зверни увагу на дві важливі оптимізації всередині методу завантаження:

_service ??= new YouTubeDownloader(); // 1. Ліниве створення

1. Оператор ??= ініціалізує реальний сервіс лише при першому виклику. До цього моменту сервіс взагалі не існує в пам'яті.

if (_cache.Contains(id))
{
    Console.WriteLine($"[Proxy] Video #{id} served from local cache!");
    return; // 2. Миттєва віддача з кешу без походів у мережу
}

2. Хеш-таблиця _cache зберігає вже завантажені ID. Якщо відео вже скачували раніше, проксі перехоплює запит і не навантажує мережевий канал повторно.

3. Що відбувається в Main() крок за кроком
Крок 1 — Перший виклик завантаження:
Клієнт викликає downloader.DownloadVideo("patterns"). Проксі бачить, що сервіс ще порожній, тому конструює його (виводиться повідомлення про важке підключення) і скачує відео через мережу:
[YouTube] Heavy network connection initialized...
[YouTube] Downloading video #patterns...
Після цього ID додається в кеш.
Крок 2 — Другий виклик завантаження:
Клієнт знову викликає downloader.DownloadVideo("patterns"). Проксі знаходить ID у кеші й миттєво віддає відповідь без звернення до реального сервісу:
[Proxy] Video #patterns served from local cache!
4. У чому різниця між Proxy та Decorator?

На технічних співбесідах це питання звучить постійно, адже їхні UML-діаграми виглядають абсолютно однаково:

  • Decorator: зберігає інтерфейс і додає нову бізнес-поведінку. Клієнт зазвичай сам вручну конструює ланцюжок із кількох декораторів.
  • Proxy: зберігає інтерфейс і контролює доступ до одного конкретного об'єкта (кеш, права доступу, ліниве створення). Проксі зазвичай сам керує життєвим циклом свого прихованого сервісу, і клієнт навіть не здогадується про його наявність.

4. Плюси та мінуси

  • Переваги: значна економія ресурсів за рахунок лінивого старту та кешування; прозорий контроль доступу та безпеки без зміни вихідного коду сервісу.
  • Недоліки: невелике збільшення часу виконання запиту (latency) через наявність додаткового проміжного шару.
