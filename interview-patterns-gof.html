Топ патернів для співбесіди: питання-пастки та інсайти

Interview Cheat Sheet
↑ До змісту

На технічних інтерв'ю рідко просять написати патерн «з нуля». Найчастіше перевіряють розуміння корнер-кейсів, антипатернів та вміння порівнювати схожі архітектурні рішення. Нижче зібрано найпопулярніші запитання-пастки:

1. Singleton: Captive Dependency (Захоплена залежність)

Питання: Що станеться, якщо в ASP.NET Core зареєструвати Singleton, який у конструкторі приймає Scoped-сервіс (наприклад, DbContext)?
  • Пастка: Singleton живе протягом усього часу роботи програми. Через це впроваджений Scoped-екземпляр ніколи не утилізується і стає «захопленим» (Captive).
  • Наслідки: Неконтрольований витік пам'яті (кеш сутностей у DbContext лише зростатиме), застарілі дані (stale data) та падіння через багатопотоковий доступ (DbContext не є thread-safe).
  • Правильна відповідь: Якщо синглтону дійсно потрібен сервіс зі scoped-життєвим циклом, слід інжектувати IServiceScopeFactory і створювати область видимості вручну через using var scope = _scopeFactory.CreateScope().

2. «Битва трьох обгорток»: Adapter vs Decorator vs Proxy

Питання: Усі три структурні патерни огортають інший об'єкт. Як розрізнити, де який застосовувати?
  • Adapter: Змінює інтерфейс. Мета — змусити два несумісні інтерфейси працювати разом (наприклад, перетворити сторонній XML API у внутрішній інтерфейс сервісу).
  • Decorator: Зберігає інтерфейс, але розширює або видозмінює поведінку об'єкта (наприклад, додає кешування, шифрування чи логування до потоку даних).
  • Proxy: Зберігає інтерфейс, але контролює доступ до цільового об'єкта (лінива ініціалізація, перевірка авторизації або клієнт віддаленого сервісу) без зміни бізнес-логіки.

3. Simple Factory vs Factory Method vs Abstract Factory

Питання: Чи є клас зі статичним методом Create(string type) та конструкцією switch/case патерном Factory Method?
  • Пастка: Ні, це ідіома «Проста фабрика» (Simple Factory). Вона порушує Open/Closed Principle, адже додавання нового продукту вимагає модифікації блоку switch.
  • Factory Method: Базується на успадкуванні та поліморфізмі. Базовий клас оголошує метод, а конкретні підкласи вирішують, який саме екземпляр створити.
  • Abstract Factory: Базується на композиції. Створює цілі родини взаємопов'язаних продуктів (наприклад, Кнопка + Чекбокс для певної ОС), гарантуючи їх взаємну сумісність.

4. Observer vs Publish-Subscribe та проблема «Lapsed Listener»

Питання: Чи є Observer тим самим, що й Pub-Sub? Який витік пам'яті найчастіше виникає при роботі з подіями в C#?
  • Різниця: В Observer суб'єкт безпосередньо зберігає список підписників у пам'яті (прямий сильний зв'язок). У Publish-Subscribe з'являється незалежний посередник (Event Bus, Kafka, RabbitMQ), тому видавець і підписник повністю ізольовані.
  • Lapsed Listener Problem: Якщо короткоживучий об'єкт підписався на подію довгоживучого об'єкта (наприклад, publisher.PriceChanged += OnPriceChanged) і не відписався через -=, Garbage Collector не зможе зібрати підписника. Довгоживучий видавець утримуватиме посилання на нього, що викликає витік пам'яті.

5. Strategy vs State: однаковий UML, різний намір

Питання: Діаграми класів патернів Strategy та State майже ідентичні. У чому полягає фундаментальна різниця?
  • Strategy: Клієнтський код зазвичай самостійно обирає та передає стратегію в контекст. Окремі стратегії нічого не знають одна про одну та не перемикають себе.
  • State: Переходи між станами відбуваються всередині самого контексту або в класах станів. Класи станів зазвичай знають про можливі наступні стани (наприклад, перехід замовлення: NewState → PaidState → ShippedState).

6. Visitor: Навіщо потрібна подвійна диспетчеризація (Double Dispatch)?

Питання: Чому не можна просто викликати visitor.Visit(element) замість двокрокового виклику element.Accept(visitor)?
  • Пастка: У C# вибір перевантаженого методу (метод з однаковою назвою, але різними типами аргументів) відбувається на етапі компіляції (Static Dispatch) за типом змінної, а не за її значенням у рантаймі.
  • Вирішення: Якщо викликати visitor.Visit(element), де змінна має базовий тип IElement, викличеться базовий метод. Метод element.Accept(v) робить перший віртуальний виклик, а всередині викликає v.Visit(this), де ключове слово this має точний тип конкретного класу на етапі виконання.

7. Template Method vs Strategy: спадкування проти композиції

Питання: Чому в сучасній архітектурі рекомендують віддавати перевагу Strategy над Template Method?
  • Template Method використовує наслідування (підхід «білий ящик»), що створює жорстку залежність підкласів від базового класу. Змінити алгоритм під час виконання (runtime) неможливо.
  • Strategy базується на композиції інтерфейсів (підхід «чорний ящик»), що повністю втілює фундаментальний принцип проєктування «Composition over inheritance» і дозволяє перемикати поведінку на льоту.

Архітектурні патерни: питання-пастки та інсайти

Architecture
↑ До змісту

Питання щодо патернів рівня архітектури (Enterprise Patterns) ставлять практично на кожній співбесіді рівня Middle+ та Senior. Вони перевіряють розуміння надійності розподілених систем, транзакційних меж та взаємодії сервісів.

1. Repository та Unit of Work: поверх чи замість Entity Framework Core?

Питання: Чи варто писати власні Generic Repository та Unit of Work поверх EF Core? У чому полягає пастка «Leaky Abstraction»?
  • Пастка: DbContext в EF Core вже є повноцінною реалізацією Unit of Work, а DbSet<T> — реалізацією патерну Repository. Написання поверхневих обгорток на кшталт IRepository<T> із методами GetAll(), Add(), Save() часто призводить до марного антипатерну дублювання коду.
  • Проблема IQueryable (Leaky Abstraction): Якщо репозиторій повертає IQueryable<T>, логіка побудови SQL витікає у бізнес-шар, нівелюючи сенс ізоляції. Якщо ж повертати IEnumerable<T> або List<T> — втрачається оптимізація запитів на стороні БД (пагінація, фільтрація).
  • Коли дійсно потрібен: У підході DDD (Domain-Driven Design), де репозиторій створюється виключно під корені агрегатів (Aggregate Roots) для інкапсуляції бізнес-правил завантаження сутностей, або для повної абстракції від зовнішніх NoSQL/сторонніх API джерел.

2. CQRS (Command Query Responsibility Segregation): міфи та реальність

Питання: Чи вимагає патерн CQRS обов'язкової наявності двох різних баз даних (Read DB / Write DB) та Event Sourcing?
  • Пастка: Поширена помилка вважати, що CQRS неможливий без складної інфраструктури (Event Sourcing, Kafka, двох окремих БД).
  • Правильна відповідь: Базовий CQRS — це лише розділення коду на дві різні моделі в межах однієї програми та однієї БД:
    • Commands: Змінюють стан системи, проходять валідацію, працюють із доменною моделлю через EF Core і нічого не повертають (або повертають ідентифікатор).
    • Queries: Лише зчитують дані, нічого не змінюють, оминають важкі доменні сутності й одразу мапляться у пласкі DTO через швидкі інструменти (Dapper або AsNoTracking() в EF Core).
  • Окремі бази даних, черги та кінцева узгодженість (Eventual Consistency) потрібні лише за екстремальних навантажень, коли операцій читання в сотні разів більше, ніж запису.

3. Transactional Outbox Pattern: вирішення Dual-Write Problem

Питання: Що станеться при виконанні коду:
await _dbContext.SaveChangesAsync();
await _messageBus.Publish(new OrderCreatedEvent());
Як патерн Outbox гарантує надійність доставки?
  • Пастка (Dual-Write Problem): Дві операції не зв'язані єдиною розподіленою транзакцією. Якщо база даних зафіксувала замовлення, але брокер повідомлень (RabbitMQ/Kafka) був тимчасово недоступний або в процесу зникло живлення — подія буде назавжди втрачена, а інші мікросервіси ніколи про неї не дізнаються.
  • Рішення через Outbox: Повідомлення зберігається у тій самій базі даних у спеціальну таблицю (наприклад, OutboxMessages) у межах однієї локальної ACID-транзакції разом із бізнес-даними.
  • Окремий фоновий процес (наприклад, BackgroundService або MassTransit Outbox Worker) періодично зчитує невідправлені записи з таблиці, публікує їх у брокер і позначає відправленими, гарантуючи семантику At-Least-Once Delivery.

4. Saga Pattern: Orchestration vs Choreography

Питання: Як організувати розподілену транзакцію між кількома мікросервісами без використання двофазного коміту (2PC)?
  • Концепція: Сага розбиває розподілену транзакцію на послідовність незалежних локальних транзакцій. Якщо одна з операцій падає (наприклад, немає грошей на картці), запускаються компенсаційні транзакції (Compensating Transactions) для відкату попередніх дій (повернення товару на склад).
  • Choreography (Хореографія): Сервіси самостійно слухають події сусідніх сервісів і реагують на них. Плюс — немає єдиної точки відмови. Мінус — утворюється «павутина» залежностей, за якою важко відстежити ланцюжок виконання при ускладненні системи.
  • Orchestration (Оркестрація): Створюється єдиний центральний координатор (Saga Orchestrator / State Machine), який явно надсилає команди кожному сервісу і відстежує його статус (наприклад, через бібліотеку MassTransit State Machine). Рекомендований підхід для складних бізнес-процесів із більш ніж 3–4 кроками.

5. Circuit Breaker (Запобіжник)

Питання: Як запобігти лавинному ефекту відмови (Cascading Failure), коли один із залежних зовнішніх сервісів починає зависати чи відмовляти?
  • Принцип роботи: Патерн перехоплює виклики до ненадійного сервісу та має 3 стани:
    • Closed (Вимкнено): Запити проходять у звичайному режимі. Якщо відсоток помилок перевищує поріг, запобіжник перемикається у стан Open.
    • Open (Увімкнено): Усі наступні запити миттєво відхиляються без спроби виклику зовнішнього сервісу (Fast Fail), не витрачаючи пули потоків і пам'ять. Запускається таймер очікування.
    • Half-Open (Напіввідкрито): Після закінчення таймера пропускається невелика пробна кількість запитів. Якщо вони пройшли успішно — стан повертається до Closed, якщо знову впали — повертається до Open.
  • Реалізація в .NET: Стандартний стек — бібліотека Polly або вбудований у .NET 8+ пакет Microsoft.Extensions.Resilience.

6. Specification Pattern: порятунок від God-репозиторіїв

Питання: Як уникнути появи репозиторіїв із десятками методів на кшталт GetActiveUsersByCountryAndAge(string country, int age)?
  • Проблема: Додавання нових комбінацій критеріїв пошуку постійно роздуває інтерфейс репозиторію та дублює LINQ-вирази по всьому коду.
  • Рішення: Патерн Specification інкапсулює бізнес-правило відбору сутностей в окремий невеликий клас, який формує Expression<Func<T, bool>>.
  • Специфікації можна поєднувати за допомогою логічних операторів (And, Or, Not), наприклад: var spec = new ActiveUsersSpec().And(new MinAgeSpec(18));. Репозиторій отримує лише один універсальний метод: ListAsync(ISpecification<T> spec).

Патерн 1: Singleton (Одинак)

Породжувальний (Creational)
↑ До змісту

1. Призначення

Гарантує, що клас має лише один екземпляр у межах програми, і надає глобальну точку доступу до цього екземпляра.

2. Коли застосовувати

  • Потрібен спільний ресурс (керування підключенням до апаратного пристрою, пулом ресурсів, кешем чи глобальною конфігурацією).
  • Необхідно суворо обмежити створення об'єктів лише однією копією.
Примітка для .NET: У сучасному C# замість написання «класичного» Singleton зазвичай використовують механізм Dependency Injection (services.AddSingleton<TInterface, TImplementation>()). Проте розуміти канонічну реалізацію все одно необхідно.

3. Реалізація на C#

Найбільш ідіоматичний, потокобезпечний (thread-safe) та «лінивий» (lazy) спосіб реалізувати Singleton у C# — використати клас Lazy<T>.

using System;

// 'sealed' запобігає успадкуванню, що могло б порушити логіку одинака
public sealed class ConfigurationManager
{
    // Lazy<T> гарантує потокобезпечність та створення об'єкта лише при першому зверненні
    private static readonly Lazy<ConfigurationManager> _instance = 
        new Lazy<ConfigurationManager>(() => new ConfigurationManager());

    // 1. Приватний конструктор забороняє створення екземпляра через 'new ConfigurationManager()' ззовні
    private ConfigurationManager()
    {
        Console.WriteLine("--> Ініціалізація ConfigurationManager (відбувається лише один раз).");
    }

    // 2. Глобальна точка доступу до екземпляра
    public static ConfigurationManager Instance => _instance.Value;

    // Стан або методи сервісу
    public string AppName { get; set; } = "MyApplication";

    public void PrintSettings()
    {
        Console.WriteLine($"Назва додатку: {AppName}");
    }
}

class Program
{
    static void Main()
    {
        // Перше звернення: об'єкт створиться
        ConfigurationManager config1 = ConfigurationManager.Instance;
        config1.PrintSettings();

        // Змінюємо дані через перше посилання
        config1.AppName = "UpdatedApplication";

        // Друге звернення: використовується вже створений об'єкт
        ConfigurationManager config2 = ConfigurationManager.Instance;
        config2.PrintSettings(); // Виведе: Назва додатку: UpdatedApplication

        // Перевірка посилань
        bool areSame = ReferenceEquals(config1, config2);
        Console.WriteLine($"Чи це один і той самий екземпляр? {areSame}"); // True
    }
}

4. Плюси та мінуси

  • Переваги:
    • Гарантована наявність лише одного об'єкта.
    • Економія пам'яті (ініціалізація тільки тоді, коли об'єкт дійсно потрібен).
  • Недоліки:
    • Порушує Single Responsibility Principle (клас відповідає і за свою роботу, і за контроль власного життєвого циклу).
    • Ускладнює написання unit-тестів (створює приховані залежності та глобальний стан).

Патерн 2: Factory Method (Фабричний метод)

Породжувальний (Creational)
↑ До змісту

1. Призначення

Визначає спільний інтерфейс для створення об’єктів у базовому класі, але дозволяє підкласам змінювати тип створюваних об’єктів.

Важливий нюанс: Фабричний метод часто плутають із «Простою фабрикою» (клас зі switch/case або статичним методом Create()). Класичний GoF-патерн Factory Method базується саме на успадкуванні та поліморфізмі: базовий клас делегує інстанціювання підкласам.

2. Коли застосовувати

  • Заздалегідь невідомо, які конкретно типи об’єктів знадобляться вашому коду.
  • Ви хочете надати клієнтам бібліотеки чи фреймворку можливість розширювати внутрішні компоненти (додавати нові типи продуктів без зміни існуючого коду).
  • Потрібно дотримуватись принципів Single Responsibility та Open/Closed.
Приклади у .NET: DbProviderFactory.CreateConnection(), метод CreateLogger() в ILoggerProvider.

3. Реалізація на C#

using System;

// 1. Загальний інтерфейс продукту
public interface INotification
{
    void Send(string message);
}

// 2. Конкретні продукти
public class EmailNotification : INotification
{
    public void Send(string message)
    {
        Console.WriteLine($"[Email] Надіслано листа: \"{message}\"");
    }
}

public class SmsNotification : INotification
{
    public void Send(string message)
    {
        Console.WriteLine($"[SMS] Надіслано повідомлення на телефон: \"{message}\"");
    }
}

// 3. Базовий клас-творець (Creator)
public abstract class NotificationService
{
    // Оце і є Фабричний метод (Factory Method)
    public abstract INotification CreateNotification();

    public void SendAlert(string message)
    {
        INotification notification = CreateNotification();
        notification.Send(message);
    }
}

// 4. Конкретні творці
public class EmailNotificationService : NotificationService
{
    public override INotification CreateNotification()

4. Плюси та мінуси

  • Переваги:
    • Усуває жорстке зв'язування між творцем і конкретними продуктами (Loose Coupling).
    • Полегшує додавання нових типів (достатньо створити новий клас продукту і новий сервіс, не чіпаючи існуючий код).
  • Недоліки:
    • Може призводити до розростання ієрархії класів: під кожен новий продукт доводиться створювати відповідний клас-творець.

Патерн 3: Abstract Factory (Абстрактна фабрика)

Породжувальний (Creational)
↑ До змісту

1. Призначення

Надає інтерфейс для створення цілих родин взаємопов'язаних або залежних об'єктів, не прив’язуючись до їхніх конкретних класів.

У чому різниця з Factory Method?
  • Factory Method створює один продукт за допомогою успадкування (один метод у базовому класі).
  • Abstract Factory створює родину продуктів через композицію (Кнопка + Чекбокс для Windows або для macOS).

2. Коли застосовувати

  • Програма повинна працювати з різними сімействами продуктів, які не мають змішуватися між собою.
  • Потрібно надати бібліотеку компонентів, приховавши деталі їх реалізації.
Приклади у .NET: Постачальники даних ADO.NET (DbProviderFactory, що створює одночасно DbConnection, DbCommand, DbDataAdapter для єдиного рушія БД).

  • Переваги:
    • Гарантована сумісність усіх створюваних продуктів.
    • Ізолює клієнтський код від конкретних класів реалізації.
    • Полегшує заміну цілих родин компонентів у runtime або через конфігурацію DI.
  • Недоліки:
    • Ускладнює структуру проєкту великою кількістю інтерфейсів.
    • Складно додавати нові типи продуктів: додавання нового продукту вимагає оновлення інтерфейсу фабрики та всіх її реалізацій.

Патерн 4: Builder (Будівельник)

Породжувальний (Creational)
↑ До змісту

1. Призначення

Відокремлює процес конструювання складного об'єкта від його представлення, дозволяючи покроково створювати різні варіації об'єкта за допомогою однакового процесу побудови.

2. Коли застосовувати

  • Антипатерн «Телескопічний конструктор»: конструктор із 10+ параметрами, де більшість необов'язкові.
  • Створення об'єкта складається з багатьох послідовних або опціональних кроків.
  • Потрібно створювати незмінні (immutable) складні об'єкти.
Знайомий контекст у .NET: StringBuilder, WebApplication.CreateBuilder(), ConfigurationBuilder, DbContextOptionsBuilder.

Патерн 5: Prototype (Прототип)

Породжувальний (Creational)
↑ До змісту

1. Призначення

Дозволяє копіювати існуючі об'єкти, не прив'язуючись до деталей їхніх конкретних класів і не викликаючи їхні конструктори заново.

2. Коли застосовувати

  • Створення об'єкта через new є ресурсомістким (важкі обчислення, запити в БД).
  • Необхідно створювати копії об'єктів, тип яких відомий клієнту лише через інтерфейс.
  • У системі є набір попередньо налаштованих шаблонів.

3. Поверхневе чи Глибоке копіювання?

  • Поверхнева копія (Shallow Copy): копіює значення примітивних типів. Для посилальних копіюються лише посилання.
  • Глибока копія (Deep Copy): створює повноцінні незалежні дублікати об'єкта та всіх його вкладених властивостей.
Порада для C#: Інтерфейс ICloneable не рекомендується використовувати через його нетипізованість (object). Краще оголошувати типізований інтерфейс IPrototype<T> або застосовувати record with { ... } у сучасному C#.

4. Реалізація на C#

using System;

public interface IPrototype<T>
{
    T Clone();
}

public class Author
{
    public string Name { get; set; }
    public Author(string name) => Name = name;
}

public class Document : IPrototype<Document>
{
    public string Title { get; set; }
    public string Content { get; set; }
    public Author Author { get; set; }

    public Document(string title, string content, Author author)
    {
        Title = title;
        Content = content;
        Author = author;
    }

    public Document Clone()
    {
        Document clone = (Document)this.MemberwiseClone();
        // Глибоке копіювання посилального типу
        clone.Author = new Author(this.Author.Name);
        return clone;
    }

    public void DisplayInfo()
    {
        Console.WriteLine($"Документ: '{Title}', Автор: {Author.Name}, Зміст: '{Content}'");
    }
}

class Program
{
    static void Main()
    {
        var originalDoc = new Document("Шаблон", "Стандартний зміст...", new Author("Олександр"));
        Document clonedDoc = originalDoc.Clone();

        clonedDoc.Title = "Звіт за Q3";
        clonedDoc.Author.Name = "Ірина"; // Зміна в клоні не зачіпає оригінал

        Console.WriteLine("Клон:");
        clonedDoc.DisplayInfo();

        Console.WriteLine("Оригінал:");
        originalDoc.DisplayInfo();
    }
}

5. Плюси та мінуси

  • Переваги: швидке копіювання в runtime; уникнення дублювання логіки ініціалізації.
  • Недоліки: реалізація глибокого копіювання графів об'єктів з циклічними посиланнями може бути складною.

Патерн 6: Adapter (Адаптер)

Структурний (Structural)
↑ До змісту

1. Призначення

Дозволяє об'єктам із несумісними інтерфейсами працювати разом, відіграючи роль «перехідника»-обгортки.

2. Коли застосовувати

  • Потрібно інтегрувати сторонню бібліотеку чи застарілий (legacy) клас, інтерфейс якого не збігається з вимогами вашої системи.
  • Необхідно узгодити несумісні формати даних (наприклад, копійки vs гривні, JSON vs XML) без втручання у вихідний код обох сторін.
Приклади у .NET: StreamReader(Stream) (адаптує байтовий потік до символьного зчитування), DbDataAdapter в ADO.NET для узгодження з DataSet.

  • Переваги: розділяє логіку конвертації від бізнес-коду (SRP); дозволяє підключати нові адаптери без змін у клієнті (OCP).
  • Недоліки: збільшує кількість допоміжних класів у проєкті.

Патерн 7: Bridge (Міст)

Структурний (Structural)
↑ До змісту

1. Призначення

Розділяє великий клас на дві окремі ієрархії — Абстракцію та Реалізацію, дозволяючи змінювати їх незалежно і запобігаючи комбінаторному вибуху класів ($M \times N$).

2. Коли застосовувати

  • Клас розвивається у двох незалежних площинах (наприклад: Пульти керування та Пристрої, або Вікна ОС та Графічні рушії DirectX/OpenGL).

Приклади у .NET: DbConnection, де абстракція підключення розділена з конкретними драйверами платформи (SQL Server, PostgreSQL, SQLite).

Патерн 8: Composite (Компонувальник)

Структурний (Structural)
↑ До змісту

1. Призначення

Згруповує об'єкти в деревоподібну структуру («частина — ціле»), дозволяючи клієнту однаково працювати як з окремими елементами, так і з їх групами.

2. Коли застосовувати

  • Потрібно реалізувати ієрархічні деревоподібні структури (файлові менеджери, вкладені кошики товарів, організаційні структури компанії).
  • Клієнт повинен однаково маніпулювати як одиночним простим елементом, так і цілим складним вузлом із нащадками.
Приклади у .NET: Дерево візуальних компонентів WPF/MAUI (UIElement / Panel), ієрархічна конфігурація IConfiguration з підсекціями.

3. Реалізація на C#

using System;
using System.Collections.Generic;
using System.Linq;

public interface IItem
{
    string Name { get; }
    decimal GetPrice();
    void Display(int depth = 0);
}

// Листок (Leaf)
public class Product : IItem
{
    public string Name { get; }
    private readonly decimal _price;
    public Product(string name, decimal price) { Name = name; _price = price; }
    public decimal GetPrice() => _price;
    public void Display(int depth = 0) => Console.WriteLine($"{new string(' ', depth * 2)}- {Name} ({_price:C})");
}

// Контейнер (Composite)
public class Box : IItem
{
    private readonly List<IItem> _children = new();
    public string Name { get; }
    public Box(string name) => Name = name;

    public void Add(IItem item) => _children.Add(item);
    public decimal GetPrice() => _children.Sum(i => i.GetPrice());

    public void Display(int depth = 0)
    {
        Console.WriteLine($"{new string(' ', depth * 2)}+ [{Name}]");
        foreach (var item in _children) item.Display(depth + 1);
    }
}

class Program
{
    static void Main()
    {
        var box = new Box("Головна посилка");
        box.Add(new Product("Телефон", 800m));

        var subBox = new Box("Аксесуари");
        subBox.Add(new Product("Чохол", 20m));
        box.Add(subBox);

        box.Display();
        Console.WriteLine($"Разом: {box.GetPrice():C}");
    }
}

4. Плюси та мінуси

  • Переваги: спрощує роботу з деревами об'єктів завдяки поліморфізму; легке додавання нових компонентів.
  • Недоліки: складно суворо обмежити типи дочірніх об'єктів на етапі компіляції.

Патерн 9: Decorator (Декоратор)

Структурний (Structural)
↑ До змісту

1. Призначення

Дозволяє динамічно додавати об'єктам нові обов'язки та поведінку, загортаючи їх у класи-обгортки без використання наслідування.

2. Коли застосовувати

  • Потрібно динамічно додавати чи комбінувати поведінку (кешування, логування, стиснення, шифрування, валідацію) без зміни базового класу.
  • Успадкування недоцільне або неможливе (наприклад, для запечатаних sealed класів).
Приклади у .NET: Ланцюжки потоків у просторі System.IO: new CryptoStream(new GZipStream(new FileStream(...))), реєстрація декораторів у DI через Scrutor.

        // Багатошарова обгортка: Email + SMS + Telegram
        INotifier notifier = new TelegramDecorator(
            new SmsDecorator(
                new EmailNotifier()

4. Плюси та мінуси

  • Переваги: динамічна комбінація функціоналу в рантаймі; дотримання Single Responsibility.
  • Недоліки: порядок огортання має суттєве значення; важче відлагоджувати велику кількість обгорток.

Патерн 10: Facade (Фасад)

Структурний (Structural)
↑ До змісту

1. Призначення

Надає простий, високорівневий уніфікований інтерфейс до складної підсистеми, що складається з багатьох класів.

2. Коли застосовувати

  • Клієнту потрібен простий типовий сценарій роботи з великою складною бібліотекою або кількома мікросервісами.
  • Потрібно зменшити зачеплення (coupling) між клієнтським кодом та внутрішніми сервісами підсистеми.
Приклади у .NET: DbContext в EF Core (фасад над кешем відстеження сутностей, пулом з'єднань, генератором SQL-запитів), HttpClient.

3. Реалізація на C#

using System;

public class InventoryService

        return true;
    }
}

{

4. Плюси та мінуси

  • Переваги: ізолює клієнтський код від деталей десятків сервісів; знижує поріг входження.
  • Недоліки: ризик перетворення фасаду на God Object при надмірному розширенні.

Патерн 11: Flyweight (Легковаговик)

Структурний (Structural)
↑ До змісту

1. Призначення

Економить оперативну пам'ять, розділяючи стан величезної кількості об'єктів на внутрішній (спільний, незмінний) та зовнішній (контекстний, передається ззовні).

2. Коли застосовувати

  • Програма створює сотні тисяч або мільйони дрібних однотипних об'єктів (символи в текстовому редакторі, дерева в ігровій карті, частинки пилу чи графічні пікселі).
  • Більшість полів об'єктів дублюють однакові незмінні дані, які можна винести в спільний пул.
Приклади у .NET: Таблиця інтернування рядків у CLR (string.Intern): однакові рядкові літерали посилаються на єдиний екземпляр у пам'яті.

3. Реалізація на C#

using System;
using System.Collections.Generic;

// Спільний стан (Flyweight)
public class TreeType
{
    public string Name { get; }
    public string Color { get; }
    public TreeType(string name, string color) { Name = name; Color = color; }
    public void Draw(int x, int y) => Console.WriteLine($"Дерево '{Name}' ({Color}) у ({x}, {y})");
}

// Фабрика пулу спільних екземплярів
public static class TreeFactory
{
    private static readonly Dictionary<string, TreeType> _types = new();
    public static TreeType GetTreeType(string name, string color)
    {
        string key = $"{name}_{color}";
        if (!_types.TryGetValue(key, out var type))
        {
            type = new TreeType(name, color);
            _types[key] = type;
        }
        return type;
    }
}

// Контекст з унікальними координатами
public class Tree
{
    private readonly int _x, _y;
    private readonly TreeType _type;
    public Tree(int x, int y, TreeType type) { _x = x; _y = y; _type = type; }
    public void Draw() => _type.Draw(_x, _y);
}

class Program
{
    static void Main()
    {
        var forest = new List<Tree>();
        var oakType = TreeFactory.GetTreeType("Дуб", "Зелений");

        for (int i = 0; i < 1000; i++)
        {
            forest.Add(new Tree(i, i * 2, oakType)); // Усі 1000 посилаються на 1 об'єкт oakType!
        }
    }
}

4. Плюси та мінуси

  • Переваги: радикальна економія RAM при великій кількості однотипних даних.
  • Недоліки: витрати CPU на пошук у пулі; ускладнення коду через поділ стану.

Патерн 12: Proxy (Замісник)

Структурний (Structural)
↑ До змісту

1. Призначення

Надає об'єкт-сурогат іншого сервісу для контролю доступу: відкладеної (лінивої) ініціалізації, кешування, перевірки прав тощо.

2. Коли застосовувати

  • Virtual Proxy: ліниве завантаження ресурсомісткого об'єкта лише в момент першого реального звернення.
  • Caching Proxy: збереження результатів важких запитів для прискорення повторних звернень.
  • Protection Proxy: перевірка ролей користувача та прав доступу перед делегуванням виклику цільовому сервісу.
Приклади у .NET: Ліниве завантаження зв'язаних сутностей в EF Core (UseLazyLoadingProxies через Castle DynamicProxy), WCF та gRPC клієнтські проксі.

3. Реалізація на C#

using System;
using System.Collections.Generic;

public interface IVideoDownloader
{
    void DownloadVideo(string videoId);
}

public class YouTubeDownloader : IVideoDownloader
{
    public YouTubeDownloader() => Console.WriteLine("[YouTube] Важке підключення...");
    public void DownloadVideo(string id) => Console.WriteLine($"[YouTube] Завантаження відео #{id}...");
}

// Кешуючий та лінивий проксі
public class CachedYouTubeProxy : IVideoDownloader
{
    private YouTubeDownloader _service;
    private readonly HashSet<string> _cache = new();

    public void DownloadVideo(string id)
    {
        _service ??= new YouTubeDownloader(); // Лінива ініціалізація

        if (_cache.Contains(id))
        {
            Console.WriteLine($"[Proxy] Відео #{id} отримано з локального кешу!");
            return;
        }

        _service.DownloadVideo(id);
        _cache.Add(id);
    }
}

class Program
{
    static void Main()
    {
        IVideoDownloader downloader = new CachedYouTubeProxy();
        downloader.DownloadVideo("patterns"); // Скачає з мережі
        downloader.DownloadVideo("patterns"); // Візьме з кешу
    }
}

4. Плюси та мінуси

  • Переваги: оптимізація ресурсів (ліниве завантаження); прозорий контроль доступу.
  • Недоліки: додатковий оверхед часу виконання при багатьох проміжних проксі.

Патерн 13: Chain of Responsibility (Ланцюжок обов'язків)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє передавати запити послідовно через ланцюжок обробників. Кожен обробник вирішує: обробити запит, передати далі чи перервати ланцюжок.

2. Коли застосовувати

  • Запит повинен пройти серію послідовних незалежних перевірок (автентифікація, перевірка лімітів швидкості Rate Limiting, валідація, кешування).
  • Склад і порядок виконання обробників мають гнучко налаштовуватися під час ініціалізації програми.
Приклади у .NET: Конвеєр Middleware в ASP.NET Core (app.UseAuthentication(), app.UseAuthorization() тощо), ланцюжки DelegatingHandler у HttpClientFactory.

3. Реалізація на C#

using System;

public class SupportTicket
{
    public string Description { get; set; }
    public int SeverityLevel { get; set; } // 1 - Простий, 2 - Складний
    public SupportTicket(string desc, int level) { Description = desc; SeverityLevel = level; }
}

public abstract class BaseHandler
{
    private BaseHandler _next;
    public BaseHandler SetNext(BaseHandler next) { _next = next; return next; }

    public virtual void Handle(SupportTicket ticket)
    {
        if (_next != null) _next.Handle(ticket);
        else Console.WriteLine($"[!] Не вдалося обробити: {ticket.Description}");
    }
}

public class BotHandler : BaseHandler
{
    public override void Handle(SupportTicket ticket)
    {
        if (ticket.SeverityLevel == 1)
            Console.WriteLine($"[Бот] Вирішено: {ticket.Description}");
        else
            base.Handle(ticket);
    }
}

public class EngineerHandler : BaseHandler
{
    public override void Handle(SupportTicket ticket)
    {
        if (ticket.SeverityLevel == 2)
            Console.WriteLine($"[Інженер] Вирішено баг: {ticket.Description}");
        else
            base.Handle(ticket);
    }
}

class Program
{
    static void Main()
    {
        var bot = new BotHandler();
        var engineer = new EngineerHandler();
        bot.SetNext(engineer);

        bot.Handle(new SupportTicket("Забув пароль", 1));
        bot.Handle(new SupportTicket("База даних впала", 2));
    }
}

4. Плюси та мінуси

  • Переваги: розв'язує відправника та одержувачів; дозволяє змінювати порядок перевірок на льоту.
  • Недоліки: запит може дійти до кінця ланцюжка і залишитися необробленим.

Патерн 14: Command (Команда)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Інкапсулює дію як самостійний об'єкт. Це дозволяє ставити запити в чергу, логувати їх та забезпечувати скасування дій (Undo/Redo).

2. Коли застосовувати

  • Потрібно реалізувати операції скасування (Undo) та повторення (Redo) в текстових або графічних редакторах.
  • Потрібно складати запити в чергу для фонової відкладеної обробки (Job Queues, черги повідомлень).
Приклади у .NET: Інтерфейс ICommand у WPF / .NET MAUI (зв'язування дій кнопок у MVVM), об'єкти команд у архітектурі CQRS через MediatR.

3. Реалізація на C#

using System;
using System.Collections.Generic;

public class BankAccount
{
    public decimal Balance { get; private set; }
    public void Deposit(decimal amt) => Balance += amt;
    public void Withdraw(decimal amt) => Balance -= amt;
}

public interface ICommand
{
    void Execute();
    void Undo();
}

public class DepositCommand : ICommand
{
    private readonly BankAccount _acc;
    private readonly decimal _amt;
    public DepositCommand(BankAccount acc, decimal amt) { _acc = acc; _amt = amt; }
    public void Execute() => _acc.Deposit(_amt);
    public void Undo() => _acc.Withdraw(_amt);
}

public class TransactionManager
{
    private readonly Stack<ICommand> _history = new();
    public void Execute(ICommand cmd)
    {
        cmd.Execute();
        _history.Push(cmd);
    }
    public void Undo()
    {
        if (_history.Count > 0) _history.Pop().Undo();
    }
}

class Program
{
    static void Main()
    {
        var acc = new BankAccount();
        var manager = new TransactionManager();

        manager.Execute(new DepositCommand(acc, 500m));
        Console.WriteLine($"Баланс: {acc.Balance:C}"); // 500

        manager.Undo();
        Console.WriteLine($"Баланс після Undo: {acc.Balance:C}"); // 0
    }
}

4. Плюси та мінуси

  • Переваги: проста реалізація Undo/Redo; повне відокремлення ініціатора операції від її виконавця.
  • Недоліки: розмноження класів команд під кожну операцію.

Патерн 15: Iterator (Ітератор)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дає можливість послідовно обходити елементи колекції, не розкриваючи її внутрішнього влаштування.

2. Коли застосовувати

  • Потрібно приховати складну внутрішню структуру колекції (дерева, зв'язані списки, хэш-таблиці) від клієнтського коду.
  • Потрібно підтримувати одночасно кілька різних алгоритмів обходу (прямий, зворотний, у глибину, у ширину) для тієї самої колекції.
У .NET: Реалізований через інтерфейси IEnumerable<T>, IEnumerator<T>, цикл foreach та синтаксис yield return.

3. Реалізація на C#

using System;
using System.Collections;
using System.Collections.Generic;

public class Playlist : IEnumerable<string>
{
    private readonly List<string> _songs = new();
    public void Add(string song) => _songs.Add(song);

    public IEnumerator<string> GetEnumerator()
    {
        foreach (var s in _songs) yield return s;
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();

    public IEnumerable<string> Backwards()
    {
        for (int i = _songs.Count - 1; i >= 0; i--) yield return _songs[i];
    }
}

class Program
{
    static void Main()
    {
        var list = new Playlist { "Song 1", "Song 2", "Song 3" };

        foreach (var song in list.Backwards())
        {
            Console.WriteLine(song); // Song 3, Song 2, Song 1
        }
    }
}

4. Плюси та мінуси

  • Переваги: незалежні паралельні обходи одних даних; підтримка різних алгоритмів обходу.
  • Недоліки: для примітивних структур може бути зайвим.

Патерн 16: Mediator (Посередник)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Змушує компоненти взаємодіяти не напряму, а через єдиний об'єкт-посередник, переводячи зв'язки типу $M:N$ у просту форму $1:N$.

2. Коли застосовувати

  • Між багатьма класами системи утворилася заплутана павутина взаємних викликів та залежностей.
  • Потрібно повторно використовувати UI-компоненти або сервіси, не зв'язуючи їх намертво з конкретними сусідами.
Приклади у .NET: Бібліотека MediatR для розділення контролерів і хендлерів бізнес-логіки за принципом CQRS.

3. Реалізація на C#

using System;

public interface IMediator { void Notify(object sender, string ev); }

public class Button
{
    private IMediator _m;
    public bool IsEnabled { get; set; }
    public void SetMediator(IMediator m) => _m = m;
}

public class Checkbox
{
    private IMediator _m;
    public bool Checked { get; private set; }
    public void SetMediator(IMediator m) => _m = m;
    public void Toggle() { Checked = !Checked; _m.Notify(this, "toggle"); }
}

public class DialogMediator : IMediator
{
    private readonly Button _btn;
    private readonly Checkbox _cb;

    public DialogMediator(Button btn, Checkbox cb)
    {
        _btn = btn; _btn.SetMediator(this);
        _cb = cb; _cb.SetMediator(this);
    }

    public void Notify(object sender, string ev)
    {
        if (ev == "toggle") _btn.IsEnabled = _cb.Checked;
    }
}

4. Плюси та мінуси

  • Переваги: усуває хаос взаємних посилань між компонентами (SRP).
  • Недоліки: посередник із часом може перетворитися на перевантажений God Object.

Патерн 17: Memento (Знімок)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє фіксувати та відновлювати минулий внутрішній стан об'єкта, не порушуючи його інкапсуляцію.

2. Коли застосовувати

  • Потрібно зберігати знімки стану (checkpoints) гри чи документа для подальшого відкату назад.
  • Прямий доступ до внутрішніх полів об'єкта порушив би його інкапсуляцію та розкрив приватні структури.
Приклади у .NET: Механізм відстеження змін у EF Core: EntityEntry.OriginalValues фіксує початковий знімок стану при завантаженні з БД.

3. Реалізація на C#

using System;
using System.Collections.Generic;

public interface IMemento { }

public class Editor
{
    private string _text = "";
    public void Type(string words) => _text += words;
    public string Text => _text;

    public IMemento Save() => new Memento(_text);
    public void Restore(IMemento m) { if (m is Memento s) _text = s.State; }

    private class Memento : IMemento
    {
        public string State { get; }
        public Memento(string state) => State = state;
    }
}

class Program
{
    static void Main()
    {
        var editor = new Editor();
        var history = new Stack<IMemento>();

        editor.Type("Версія 1");
        history.Push(editor.Save());

        editor.Type(" + помилка");
        editor.Restore(history.Pop()); // Відновлює "Версія 1"
        Console.WriteLine(editor.Text);
    }
}

4. Плюси та мінуси

  • Переваги: зберігає приватні поля незмінними для зовнішнього світу.
  • Недоліки: споживає багато RAM при частих знімках великих об'єктів.

Патерн 18: Observer (Спостерігач)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Організовує механізм підписки, завдяки якому об'єкти автоматично дізнаються про зміни стану суб'єкта.

2. Коли застосовувати

  • Зміна стану одного об'єкта вимагає автоматичного оновлення інших невідомих заздалегідь об'єктів.
  • Реалізація архітектури керування подіями (Event-Driven Architecture) та моделей Publisher-Subscriber.
Приклади у .NET: Конструкція event та делегати C#, INotifyPropertyChanged у WPF/MAUI, інтерфейси IObservable<T> та IObserver<T> у Reactive Extensions (Rx.NET).

3. Реалізація на C#

using System;
using System.Collections.Generic;

public class Product
{
    private decimal _price;
    public event Action<decimal> PriceChanged; // Ідіоматичний підхід у C#

    public decimal Price
    {
        get => _price;
        set
        {
            if (_price != value)
            {
                _price = value;
                PriceChanged?.Invoke(_price);
            }
        }
    }
}

class Program
{
    static void Main()
    {
        var product = new Product();
        product.PriceChanged += price => Console.WriteLine($"Нова ціна: {price:C}");
        product.Price = 120m;
    }
}

4. Плюси та мінуси

  • Переваги: слабке зв'язування джерела з підписниками; динамічна підписка.
  • Недоліки: ризик витоку пам'яті через забуту відписку (Lapsed Listener Problem).

Патерн 19: State (Стан)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє об'єкту змінювати свою поведінку залежно від внутрішнього стану, замінюючи громіздкі switch/case скінченним автоматом поліморфних класів.

2. Коли застосовувати

  • Об'єкт поводиться кардинально по-різному залежно від внутрішнього статусу (наприклад, Замовлення: Нове, Оплачене, Доставлене, Скасоване).
  • Методи містять величезні каскади умов if-else або switch за числовими статусами.
Приклади у .NET: Бібліотека Stateless для наочного опису скінченних автоматів (State Machines) на C#.

3. Реалізація на C#

using System;

public interface IOrderState
{
    void Pay(OrderContext ctx);
    void Ship(OrderContext ctx);
}

public class OrderContext
{
    private IOrderState _state = new NewState();
    public void SetState(IOrderState state) => _state = state;
    public void Pay() => _state.Pay(this);
    public void Ship() => _state.Ship(this);
}

public class NewState : IOrderState
{
    public void Pay(OrderContext ctx) { Console.WriteLine("Оплачено."); ctx.SetState(new PaidState()); }
    public void Ship(OrderContext ctx) => Console.WriteLine("Помилка: не можна відправити неоплачене!");
}

public class PaidState : IOrderState
{
    public void Pay(OrderContext ctx) => Console.WriteLine("Вже сплачено.");
    public void Ship(OrderContext ctx) => Console.WriteLine("Відправлено кур'єром.");
}

class Program
{
    static void Main()
    {
        var order = new OrderContext();

        // 1. Спроба відправити нове, ще неоплачене замовлення
        Console.WriteLine("1. Спроба відправити:");
        order.Ship();

        // 2. Оплачуємо замовлення (стан зміниться на PaidState)
        Console.WriteLine("\n2. Оплата замовлення:");
        order.Pay();

        // 3. Спроба оплатити повторно
        Console.WriteLine("\n3. Повторна спроба оплати:");
        order.Pay();

        // 4. Відправка оплаченого замовлення
        Console.WriteLine("\n4. Відправка замовлення:");
        order.Ship();
    }
}

4. Плюси та мінуси

  • Переваги: прибирає спагеті-код умовних переходів; локалізує поведінку кожного стану.
  • Недоліки: може бути надмірним ускладненням для систем із 2-3 простими статусами.

Патерн 20: Strategy (Стратегія)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Визначає сімейство взаємозамінних алгоритмів і дозволяє перемикати їх у контексті безпосередньо під час виконання програми.

2. Коли застосовувати

  • Потрібно використовувати різні варіації алгоритму (способи розрахунку податків, алгоритми сортування, маршрутизації чи стиснення файлів).
  • Необхідно підміняти алгоритм прямо під час виконання програми відповідно до налаштувань користувача.
Приклади у .NET: Інтерфейси IComparer<T> та IEqualityComparer<T> у методах LINQ OrderBy та Array.Sort.

3. Реалізація на C#

using System;

public interface IShippingStrategy
{
    decimal Calculate(decimal total);
}

{
    public decimal Calculate(decimal total) => 50m;
}

{
    public decimal Calculate(decimal total) => 150m;
}

{
    private IShippingStrategy _strategy;
    public OrderCalculator(IShippingStrategy s) => _strategy = s;
    public void SetStrategy(IShippingStrategy s) => _strategy = s;

{
    static void Main()
    {
        decimal subtotal = 1000m;
        Console.WriteLine($"Базова вартість замовлення: {subtotal} грн\n");

        var calculator = new OrderCalculator(new PostalShipping());
        decimal postalTotal = calculator.GetTotal(subtotal);
        Console.WriteLine($"Разом із поштовою доставкою: {postalTotal} грн");

        // 2. Змінюємо стратегію на кур'єрську доставку (+150 грн)
        calculator.SetStrategy(new CourierShipping());

        Console.WriteLine($"Разом із кур'єрською доставкою: {courierTotal} грн");
    }
}

4. Плюси та мінуси

  • Переваги: гнучка заміна алгоритмів у runtime; ізоляція математики від бізнес-моделі (OCP).
  • Недоліки: клієнт повинен знати різницю між стратегіями для їхнього вибору.

Патерн 21: Template Method (Шаблонний метод)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Задає каркас алгоритму в базовому класі, дозволяючи підкласам змінювати окремі кроки без втручання в загальну структуру.

2. Коли застосовувати

  • Алгоритм складається з суворої фіксованої послідовності кроків, але деякі з кроків повинні мати специфічну реалізацію в нащадках.
  • Потрібно уникнути дублювання загального каркаса коду обробки даних (дотримання DRY).
Приклади у .NET: Стандартний патерн звільнення ресурсів Dispose(bool disposing) у базових типах .NET BCL.

Патерн 22: Visitor (Відвідувач)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Дозволяє додавати нові операції до класів, не змінюючи їхній вихідний код, за допомогою подвійної диспетчеризації (Double Dispatch).

2. Коли застосовувати

  • Потрібно виконувати різні непов'язані операції над складною структурою вузлів дерева (наприклад, синтаксичні дерева компілятора, експорт у різні формати).
  • Ієрархія класів елементів стабільна і рідко змінюється, а нові операції над ними додаються часто.
Приклади у .NET: ExpressionVisitor у просторі System.Linq.Expressions (застосовується в Entity Framework Core для розбору дерев виразів та трансляції їх у SQL).

Патерн 23: Interpreter (Інтерпретатор)

Поведінковий (Behavioral)
↑ До змісту

1. Призначення

Визначає граматику простої мови чи виразу та будує деревоподібне представлення (AST) для його обчислення.

2. Коли застосовувати

  • Потрібно створити простий внутрішній парсер предметно-орієнтованої мови (DSL) для фільтрації, пошукових запитів або логічних правил.
  • Граматика мови проста і представлена у вигляді дерева виразів.
Приклади у .NET: Клас System.Text.RegularExpressions.Regex (інтерпретатор синтаксису регулярних виразів).

3. Реалізація на C#

using System;
using System.Collections.Generic;

public interface IExpression
{
    int Interpret(Dictionary<string, int> context);
}

public class NumberExpression : IExpression
{
    private readonly int _num;
    public NumberExpression(int n) => _num = n;
    public int Interpret(Dictionary<string, int> ctx) => _num;
}

public class AddExpression : IExpression
{
    private readonly IExpression _left, _right;
    public AddExpression(IExpression l, IExpression r) { _left = l; _right = r; }
    public int Interpret(Dictionary<string, int> ctx) => _left.Interpret(ctx) + _right.Interpret(ctx);
}

class Program
{
    static void Main()
    {
        // 5 + 10
        IExpression expr = new AddExpression(new NumberExpression(5), new NumberExpression(10));
        Console.WriteLine($"Результат: {expr.Interpret(null)}"); // 15
    }
}

4. Плюси та мінуси

  • Переваги: легке розширення граматики новими правилами; чудово підходить для предметно-орієнтованих мов (DSL).
  • Недоліки: складно підтримувати для мов із великою граматикою.
