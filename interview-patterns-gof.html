Топ патернів для співбесіди: питання-пастки та інсайти

Interview Cheat Sheet
↑ До змісту

На технічних інтерв'ю рідко просять написати патерн «з нуля». Найчастіше перевіряють розуміння корнер-кейсів, антипатернів та вміння порівнювати схожі архітектурні рішення. Нижче зібрано найпопулярніші запитання-пастки:

1. Singleton: Captive Dependency (Захоплена залежність)

Питання: Що станеться, якщо в ASP.NET Core зареєструвати Singleton, який у конструкторі приймає Scoped-сервіс (наприклад, DbContext)?
  • Пастка: Singleton живе протягом усього часу роботи програми. Через це впроваджений Scoped-екземпляр ніколи не утилізується і стає «захопленим» (Captive).
  • Наслідки: Неконтрольований витік пам'яті (кеш сутностей у DbContext лише зростатиме), застарілі дані (stale data) та падіння через багатопотоковий доступ (DbContext не є thread-safe).
  • Правильна відповідь: Якщо синглтону дійсно потрібен сервіс зі scoped-життєвим циклом, слід інжектувати IServiceScopeFactory і створювати область видимості вручну через using var scope = _scopeFactory.CreateScope();.

2. «Битва трьох обгорток»: Adapter vs Decorator vs Proxy

Питання: Усі три структурні патерни огортають інший об'єкт. Як розрізнити, де який застосовувати?
  • Adapter: Змінює інтерфейс. Мета — змусити два несумісні інтерфейси працювати разом (наприклад, перетворити сторонній XML API у внутрішній інтерфейс сервісу).
  • Decorator: Зберігає інтерфейс, але розширює або видозмінює поведінку об'єкта (наприклад, додає кешування, шифрування чи логування до потоку даних).
  • Proxy: Зберігає інтерфейс, але контролює доступ до цільового об'єкта (лінива ініціалізація, перевірка авторизації або клієнт віддаленого сервісу) без зміни бізнес-логіки.

3. Simple Factory vs Factory Method vs Abstract Factory

Питання: Чи є клас зі статичним методом Create(string type) та конструкцією switch/case патерном Factory Method?
  • Пастка: Ні, це ідіома «Проста фабрика» (Simple Factory). Вона порушує Open/Closed Principle, адже додавання нового продукту вимагає модифікації блоку switch.
  • Factory Method: Базується на успадкуванні та поліморфізмі. Базовий клас оголошує метод, а конкретні підкласи вирішують, який саме екземпляр створити.
  • Abstract Factory: Базується на композиції. Створює цілі родини взаємопов'язаних продуктів (наприклад, Кнопка + Чекбокс для певної ОС), гарантуючи їх взаємну сумісність.

4. Observer vs Publish-Subscribe та проблема «Lapsed Listener»

Питання: Чи є Observer тим самим, що й Pub-Sub? Який витік пам'яті найчастіше виникає при роботі з подіями в C#?
  • Різниця: В Observer суб'єкт безпосередньо зберігає список підписників у пам'яті (прямий сильний зв'язок). У Publish-Subscribe з'являється незалежний посередник (Event Bus, Kafka, RabbitMQ), тому видавець і підписник повністю ізольовані.
  • Lapsed Listener Problem: Якщо короткоживучий об'єкт підписався на подію довгоживучого об'єкта (наприклад, publisher.PriceChanged += OnPriceChanged) і не відписався через -=, Garbage Collector не зможе зібрати підписника. Довгоживучий видавець утримуватиме посилання на нього, що викликає витік пам'яті.

5. Strategy vs State: однаковий UML, різний намір

Питання: Діаграми класів патернів Strategy та State майже ідентичні. У чому полягає фундаментальна різниця?
  • Strategy: Клієнтський код зазвичай самостійно обирає та передає стратегію в контекст. Окремі стратегії нічого не знають одна про одну та не перемикають себе.
  • State: Переходи між станами відбуваються всередині самого контексту або в класах станів. Класи станів зазвичай знають про можливі наступні стани (наприклад, перехід замовлення: NewState → PaidState → ShippedState).

6. Visitor: Навіщо потрібна подвійна диспетчеризація (Double Dispatch)?

Питання: Чому не можна просто викликати visitor.Visit(element) замість двокрокового виклику element.Accept(visitor)?
  • Пастка: У C# вибір перевантаженого методу (метод з однаковою назвою, але різними типами аргументів) відбувається на етапі компіляції (Static Dispatch) за типом змінної, а не за її значенням у рантаймі.
  • Вирішення: Якщо викликати visitor.Visit(element), де змінна має базовий тип IElement, викличеться базовий метод. Метод element.Accept(v) робить перший віртуальний виклик, а всередині викликає v.Visit(this), де ключове слово this має точний тип конкретного класу на етапі виконання.

7. Template Method vs Strategy: спадкування проти композиції

Питання: Чому в сучасній архітектурі рекомендують віддавати перевагу Strategy над Template Method?
  • Template Method використовує наслідування (підхід «білий ящик»), що створює жорстку залежність підкласів від базового класу. Змінити алгоритм під час виконання (runtime) неможливо.
  • Strategy базується на композиції інтерфейсів (підхід «чорний ящик»), що повністю втілює фундаментальний принцип проєктування «Composition over inheritance» і дозволяє перемикати поведінку на льоту.

Архітектурні патерни: питання-пастки та інсайти

Architecture
↑ До змісту

Питання щодо патернів рівня архітектури (Enterprise Patterns) ставлять практично на кожній співбесіді рівня Middle+ та Senior. Вони перевіряють розуміння надійності розподілених систем, транзакційних меж та взаємодії сервісів.

1. Repository та Unit of Work: поверх чи замість Entity Framework Core?

Питання: Чи варто писати власні Generic Repository та Unit of Work поверх EF Core? У чому полягає пастка «Leaky Abstraction»?
  • Пастка: DbContext в EF Core вже є повноцінною реалізацією Unit of Work, а DbSet<T> — реалізацією патерну Repository. Написання поверхневих обгорток на кшталт IRepository<T> із методами GetAll(), Add(), Save() часто призводить до марного антипатерну дублювання коду.
  • Проблема IQueryable (Leaky Abstraction): Якщо репозиторій повертає IQueryable<T>, логіка побудови SQL витікає у бізнес-шар, нівелюючи сенс ізоляції. Якщо ж повертати IEnumerable<T> або List<T> — втрачається оптимізація запитів на стороні БД (пагінація, фільтрація).
  • Коли дійсно потрібен: У підході DDD (Domain-Driven Design), де репозиторій створюється виключно під корені агрегатів (Aggregate Roots) для інкапсуляції бізнес-правил завантаження сутностей, або для повної абстракції від зовнішніх NoSQL/сторонніх API джерел.

2. CQRS (Command Query Responsibility Segregation): міфи та реальність

Питання: Чи вимагає патерн CQRS обов'язкової наявності двох різних баз даних (Read DB / Write DB) та Event Sourcing?
  • Пастка: Поширена помилка вважати, що CQRS неможливий без складної інфраструктури (Event Sourcing, Kafka, двох окремих БД).
  • Правильна відповідь: Базовий CQRS — це лише розділення коду на дві різні моделі в межах однієї програми та однієї БД:
    • Commands: Змінюють стан системи, проходять валідацію, працюють із доменною моделлю через EF Core і нічого не повертають (або повертають ідентифікатор).
    • Queries: Лише зчитують дані, нічого не змінюють, оминають важкі доменні сутності й одразу мапляться у пласкі DTO через швидкі інструменти (Dapper або AsNoTracking() в EF Core).
  • Окремі бази даних, черги та кінцева узгодженість (Eventual Consistency) потрібні лише за екстремальних навантажень, коли операцій читання в сотні разів більше, ніж запису.

3. Transactional Outbox Pattern: вирішення Dual-Write Problem

Питання: Що станеться при виконанні коду:
await _dbContext.SaveChangesAsync();
await _messageBus.Publish(new OrderCreatedEvent());
Як патерн Outbox гарантує надійність доставки?
  • Пастка (Dual-Write Problem): Дві операції не зв'язані єдиною розподіленою транзакцією. Якщо база даних зафіксувала замовлення, але брокер повідомлень (RabbitMQ/Kafka) був тимчасово недоступний або в процесу зникло живлення — подія буде назавжди втрачена, а інші мікросервіси ніколи про неї не дізнаються.
  • Рішення через Outbox: Повідомлення зберігається у тій самій базі даних у спеціальну таблицю (наприклад, OutboxMessages) у межах однієї локальної ACID-транзакції разом із бізнес-даними.
  • Окремий фоновий процес (наприклад, BackgroundService або MassTransit Outbox Worker) періодично зчитує невідправлені записи з таблиці, публікує їх у брокер і позначає відправленими, гарантуючи семантику At-Least-Once Delivery.

4. Saga Pattern: Orchestration vs Choreography

Питання: Як організувати розподілену транзакцію між кількома мікросервісами без використання двофазного коміту (2PC)?
  • Концепція: Сага розбиває розподілену транзакцію на послідовність незалежних локальних транзакцій. Якщо одна з операцій падає (наприклад, немає грошей на картці), запускаються компенсаційні транзакції (Compensating Transactions) для відкату попередніх дій (повернення товару на склад).
  • Choreography (Хореографія): Сервіси самостійно слухають події сусідніх сервісів і реагують на них. Плюс — немає єдиної точки відмови. Мінус — утворюється «павутина» залежностей, за якою важко відстежити ланцюжок виконання при ускладненні системи.
  • Orchestration (Оркестрація): Створюється єдиний центральний координатор (Saga Orchestrator / State Machine), який явно надсилає команди кожному сервісу і відстежує його статус (наприклад, через бібліотеку MassTransit State Machine). Рекомендований підхід для складних бізнес-процесів із більш ніж 3–4 кроками.

5. Circuit Breaker (Запобіжник)

Питання: Як запобігти лавинному ефекту відмови (Cascading Failure), коли один із залежних зовнішніх сервісів починає зависати чи відмовляти?
  • Принцип роботи: Патерн перехоплює виклики до ненадійного сервісу та має 3 стани:
    • Closed (Вимкнено): Запити проходять у звичайному режимі. Якщо відсоток помилок перевищує поріг, запобіжник перемикається у стан Open.
    • Open (Увімкнено): Усі наступні запити миттєво відхиляються без спроби виклику зовнішнього сервісу (Fast Fail), не витрачаючи пули потоків і пам'ять. Запускається таймер очікування.
    • Half-Open (Напіввідкрито): Після закінчення таймера пропускається невелика пробна кількість запитів. Якщо вони пройшли успішно — стан повертається до Closed, якщо знову впали — повертається до Open.
  • Реалізація в .NET: Стандартний стек — бібліотека Polly або вбудований у .NET пакет Microsoft.Extensions.Resilience.

6. Specification Pattern: порятунок від God-репозиторіїв

Питання: Як уникнути появи репозиторіїв із десятками методів на кшталт GetActiveUsersByCountryAndAge(string country, int age)?
  • Проблема: Додавання нових комбінацій критеріїв пошуку постійно роздуває інтерфейс репозиторію та дублює LINQ-вирази по всьому коду.
  • Рішення: Патерн Specification інкапсулює бізнес-правило відбору сутностей в окремий невеликий клас, який формує Expression<Func<T, bool>>.
  • Специфікації можна поєднувати за допомогою логічних операторів (And, Or, Not), наприклад: var spec = new ActiveUsersSpec().And(new MinAgeSpec(18));. Репозиторій отримує лише один універсальний метод: ListAsync(ISpecification<T> spec).
